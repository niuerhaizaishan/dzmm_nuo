## 三、P0 高优先级（建议优先执行）

### 1. 数据零备份（数据安全，最痛）

**现状**：`profiles.json`（425K 档案）、`state.json`（发情值/状态机）、`novels/`（小说产出）是核心业务数据，全部单机单文件，无任何备份。

**风险**：磁盘故障 / 误删 / 容器重建误覆盖 = 数据永久丢失，无法恢复。

**方案（三选一，越靠前越稳）**：
- **A. 阿里云 OSS 定时同步**（推荐）：装 `ossutil`，cron 每小时/每日 `tar` 打包 `state.json profiles.json novels/ .dzmm_token.json .dzmm_login.json` 上传 OSS。
- **B. 本地每日快照**：cron 每日 `tar czf /opt/backups/dzmm-$(date +%F).tar.gz -C /opt/dzmm state.json profiles.json novels .dzmm_token.json .dzmm_login.json`，保留 30 天。
- **C. 手动 + 本地拉取**：最低限度，定期 `deploy.ps1 -Action sync` 到 Windows 本机（`D:\Deepseek\dzmm_cloud` 已是镜像，但要记得拉）。

**涉及文件**：宿主机 cron / OSS 配置。

**执行要点**：备份必须含 `.dzmm_token.json`（登录态，丢失需重新人工过验证码登录）。

---

### 2. noVNC 公网暴露 + 弱密码（安全）

**现状**：`websockify` 监听 `0.0.0.0:6080`，密码 `[已轮换，口令仅存服务器受限配置]` 全网公开可撞。任何扫到 6080 端口的人都可能远程桌面进 bot 的浏览器画面。

**风险**：撞库后可见 bot 登录态、群聊内容、token。

**方案（三选一，越靠前越安全）**：
- **A. 阿里云安全组限制源 IP**（推荐）：安全组把 6080 端口只对办公/家庭 IP 放行，其余拒绝。
- **B. SSH 隧道**：6080 不再对公网开放（防火墙关闭），访问时 `ssh -L 6080:127.0.0.1:6080 root@47.237.152.187`，浏览器开 `http://127.0.0.1:6080/vnc.html`。
- **C. 改强密码**：改 `.env` 的 `VNC_PASS` 为强密码，`systemctl restart dzmm-vnc` 生效（注意同步容器侧环境变量，已通过 compose 注入）。

**涉及文件**：阿里云控制台安全组 / `start_vnc.sh` / `.env`。

## 四、P1 中优先级

### 3. `token.emergency` 反复重启空转（可靠性）

**现状**：`renew_token.py` 连续 3 次续期失败即写 `token.emergency` 信号；`bot.py` 主循环检测到即退出交给 entrypoint 重启。一次 captcha 曾触发 10 次 emergency（今天下午实测），形成「renew 写信号 → bot 重启 → 又失败」空转循环。今日已为 captcha 场景加了 `bot.paused` 哨兵，但 **unauthorized 场景**的空转仍未解决。

**方案**：给 emergency 信号加冷却——`renew_token.py` 的 `record_fail()` 里记录「上次写 emergency 的时间戳」（存 `renew_fail_state.json`），30 分钟内不重复写；成功续期后清零。

**涉及文件**：`renew_token.py`。

---

### 4. 告警通道静默失败无兜底（可靠性）

**现状**：`wx_alert.send_weixin` → `feishu_alert.send_feishu`，失败是静默的（返回 False 但调用方 `except: pass`）。一旦飞书 webhook 失效，心跳、巡检、captcha、登录失败**所有告警一起失联且无人知晓**。

**方案**：加"告警的告警"——`heartbeat.py` 连续 N 次发送失败时，在 `bot.log` 写醒目标记（如 `[ALERT-CHANNEL-DOWN]`），或增加第二通道（短信/邮件/另一个 webhook）。

**涉及文件**：`feishu_alert.py` / `heartbeat.py`。

---

### 5. `auto_recover.py` 容器内 AppleScript 死代码（代码质量）

**现状**：云端 `CONTAINER_MODE=1`，但 `auto_recover.py` 的登录阶梯仍先尝试 `auto_relogin.login_flow()`（AppleScript，Linux 上 `osascript` 必抛异常），每次都白走一次异常才转 headless。

**方案**：`main()` 里加 `if not env_config.in_container():` 才尝试 AppleScript，容器环境直接 headless。

**涉及文件**：`auto_recover.py`。

---

## 五、P2 低优先级

### 6. `get_messages_all` 重复拉取无缓存（性能）

**现状**：`/查`、`/羞辱`、`/发骚` 等命令处理链里，多个函数各自独立调 `get_messages_all`（每次 HTTP 拉 200 条），一次命令可能触发 2-3 次重复 API 调用。

**方案**：加模块级缓存 dict（key=cid，30 秒 TTL），或主循环一次拉取后传参复用。

**涉及文件**：`dzmm.py` / `bot.py`。

---

### 7. `bot.py` 3749 行单体 + 状态机样板重复（可维护性）

**现状**：命令路由 + 5 个状态机 + 发送 + 数据全堆一个文件；`fasao/diaojiao/perf/story/vote` 五个状态机的 `_get_xxx_state/_set_xxx_state` 是几乎相同的 load→get→save 样板。

**方案**（低风险路线）：先抽一个通用 `state_get(cid, key)` / `state_set(cid, key, val)` 存取器消除样板；状态机拆分为独立模块再逐步进行。

**涉及文件**：`bot.py`。

---

### 8. 发情值增量魔数散落（可维护性）

**现状**：`+8 / +10 / +15 / +20` 分散在十来个函数里（投票、剧情、羞辱、发骚、调教、高潮…），改规则要到处找。

**方案**：集中为 `HEAT_*` 常量（如 `HEAT_VOTE_STARTER=8`、`HEAT_SCENE=10`、`HEAT_INSULT=15`、`HEAT_CLIMAX_BONUS=20`）。

**涉及文件**：`bot.py`。

---

### 9. prompt 内联在 `brains.py`（可维护性）

**现状**：30+ 个长 prompt 写死在代码里，调 prompt 要改代码 + 重新 build + 部署。

**方案**：抽到独立 `.md`/`.txt` 配置文件，启动时加载。可选：加个 `/reload_prompt` 热更新。

**涉及文件**：`brains.py`。

---

### 10. 测试覆盖不足（质量保障）

**现状**：只有 4 个集成测试（`test_hot_refresh / test_http_send / test_ls / test_send`），核心逻辑（命令识别 `is_*_cmd`、状态机流转、发情值结算 `_add_heat/_climax_hits/_judge_pending`）无单元测试，改动回归全靠人工。

**方案**：先给「命令识别」和「发情值结算」补最小单测（纯函数，易测）。

**涉及文件**：新增 `tests/`。

---

### 11. 杂项清理（运维）

**现状**：`/opt/dzmm` 下 16 个 `build*.log` 历史遗留、`backup-code-*.tar.gz` 无保留策略会累积。

**方案**：清理 `build*.log`；给 `deploy.ps1` 的备份加保留策略（如只留最近 10 份）。

**涉及文件**：宿主机 `/opt/dzmm`、`deploy.ps1`。
