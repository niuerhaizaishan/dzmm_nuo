# 茶水间双人办公室剧情与消息归档

状态：仅本地实现，默认关闭。未部署、未提交、未配置真实集成密钥，未调用生产接口。

## 规则和命令

- 仅顶层茶水间、有效人设 `nuo`、`features.office=true` 时处理专用命令。
- `/允许潜规则`、`/拒绝潜规则`：本人修改个人开关，默认拒绝，持久保存。作为目标需要允许；发起者的开关只控制别人能否向其发起。
- `/潜规则状态`：个人开关、今日剩余次数、是否有会话。
- `/潜规则 @目标 [剧情方向]`：发送者是发起者。也支持工号 `#0001`、平台 UUID、唯一名称；名字包含空格时用双引号。显示名称由员工匹配接口唯一解析，不从近期聊天猜人。
- 双方必须是本群非机器人、已入职、同部门，发起者 `rank_level` 严格高于目标。部门比较唯一 ID，不能比较名称；游戏次数不是职级排序。
- `/潜规则继续 [方向]`：仅双方，重新读取成员、部门和职级；最多续写三次。
- `/潜规则结束`：仅双方；拒绝开关也会结束本人参与的会话，取消未投递结果。
- 每个发起者按北京时间每天一次。首段发送前事务预占，确认成功后使用；续写不额外扣次。不使用游戏额度、商店次数或摸鱼币。
- 一人同时参与一场，不锁住整个群。不同人员可同时存在多场会话；进程最多同时处理四个生成任务。
- 首段和续写正文每段 400～600 个非空白字符，独立办公室剧情模板依据双方性别调整称谓及代词，未知用姓名。参考原场景的“人物→场景→方向→上下文”组织结构，写双方自愿、非露骨的互动；原 `/发骚` 提示词不改动。

跨部门和对方职级更高的文案采用已确认版本：

> 自己部门还不够你忙的嘛，居然惦记起隔壁部门了～不许越界！

> 胆子挺大呀，领导都敢点？小小糯替你把申请撤回了，快去努力升职～

同级提示：

> 工牌摆一起，谁也管不了谁呀～只能向职级比自己低的同部门成员发起哦。

## 计时、取消与失败恢复

首段成功后 300 秒无有效互动自动结束。续写成功后重新计时；生成中有独立的 120 秒持久化处理截止时间，模型调用预算 45 秒、外层等待 50 秒，不会无限挂起。

普通聊天、无权限操作、查询状态均不刷新计时。续写生成失败恢复原空闲截止时间。拒绝、结束、关闭功能、旧 operation 的迟到结果不能复活会话。

生成前、准备发送时、等待账号发送锁结束后检查许可与会话状态。消息一旦已经交给平台则无法保证撤回；用户在网络等待期间拒绝，会关闭会话且不允许后续续写，但已投递内容不会自动删除。

SQLite 事务负责参与者互斥和每日额度；“群＋原指令消息 ID”负责去重。重启后读持久化截止时间处理旧会话；正在生成但中断的任务到期释放未发送首段的预占额度。

长消息整条走账号 Socket.IO，`content.reference` 引用各自的原指令。Outbox 保存完整正文、引用、单条标记，使用独立 `office_reply` 类型，禁止被普通文本重试器重放。最终发送 guard 在 Socket.IO 动作锁内运行，避免排队期间的拒绝被绕过。ACK 后读回核对消息 ID、作者、全文与引用。

账号未连接或平台明确拒绝：保留原文、最多尝试三次，不重新生成、不拆分。全部明确失败时释放未发送首段额度；网络超时、ACK 不明或读回不符：保留待核对状态和额度，禁止盲目重发。原生引用是否被真实茶水间完整保留尚待联调，不能将模拟测试当作线上验证。

超时通知引用最后一条有效指令。通知发送前持久领取，结果不明不重复发送；生成超时/投递待核对使用不同文案，不误报为纯空闲超时。

## 员工接口待接入合同

文档已有 `POST /users/match`。仅它的唯一匹配结果可以用于名称/工号解析；`ambiguous` 要求重新指定，不能任选候选。

现有 `game-quota` 只有职级名，没有部门、职级排序和性别。资料接口仍是**待确认合同**，不会默认假定 `/profile` 已经存在。

未来服务端环境配置（以下仅占位说明，本轮不写入实际环境）：

```text
DZMM_INTEGRATION_BASE_URL=https://your-ddzm-host/api/integration
DZMM_INTEGRATION_API_KEY=<server-only-key>
DZMM_EMPLOYEE_PROFILE_PATH=/users/{platform_id}/profile
```

`DZMM_EMPLOYEE_PROFILE_PATH` 必须在接口方确认路径后填写。当前适配器期待以下平铺 JSON；如真实结构不同，后续修改适配器并通过合同测试后再接通：

```json
{
  "platform_id": "platform-uid",
  "display_name": "员工名称",
  "department_id": "department-id",
  "department_name": "部门名称",
  "rank_name": "职级名称",
  "rank_level": 3,
  "gender": "female",
  "employment_status": "active"
}
```

约定 `rank_level` 为整数且越大职级越高，`department_id` 为非空字符串。性别暂识别 `male/female`、`男/女`、`男生/女生`，其他取未知。若响应提供 `employment_status`，只接受 `active`；缺省暂按可查询的在职员工处理，最终以接口合同为准。

仅使用只读资料和匹配接口，不调用发币、扣币接口。不配置密钥/路径时明确提示不可开始；HTTPS 始终校验证书、禁止重定向携带密钥、异常只记录类型。进程内每分钟最多45次请求留出余量；跨实例总额度仍以服务端429为准。

## 数据与归档

- 玩法：`data/office.db`（可通过 `DZMM_OFFICE_DB` 指定），个人开关、原指令去重、额度、会话、生成全文、引用和通知记录。
- 群消息：沿用 `data/chat_archive.db`（可通过 `DZMM_CHAT_ARCHIVE_DB` 指定），归档开关仍为 `DZMM_CHAT_ARCHIVE=on`。代码扩展认证群及茶水间的允许范围，不修改现有开关。
- 旧库在下一次写入连接时事务重建单群 CHECK，复制并核对记录数，重建索引，失败回滚。仅测试临时库执行过迁移，本轮未迁移真实运行库。
- 所有收到的消息先归档再做命令/自回声过滤，群＋消息 ID 去重；图片等保留原始元数据，不下载附件。
- 后台 `/messages` 增加群选择，默认仍显示认证群，分页、筛选、发送者链接保持所选群。个人故事/画像等证据读取仍限原认证群，不因茶水间入库而自动扩大范围。
- 历史导入沿用 `runtime.chat_archive.import_jsonl(..., group_id=TEA_CID)`，只写归档、不执行历史指令。历史平台消息的全量抓取与补漏没有在本轮执行；实时采集也不等于已具备完整历史。
