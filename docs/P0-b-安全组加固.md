# P0-b 阿里云安全组加固：把 noVNC 收回内网

> 结论先说：**只有 `6080` 需要处理**。`5900` 实测从公网连不上（安全组已经挡住了）。

## 一、先看清现状（2026-09-25 实测）

从公网发起 TCP 连接的结果：

| 端口 | 服务 | 公网可达 | 说明 |
|---|---|---|---|
| 22 | sshd | ✅ 可达 | **绝对不能动** —— 这是唯一的入口，也是唯一的兜底通道 |
| **6080** | websockify（noVNC 网页） | ✅ **可达，返回登录页 HTTP 200** | ← **要处理的就是它**，密码是 `dzmm2026` |
| 5900 | x11vnc | ❌ 不可达（超时） | 虽然监听在 `0.0.0.0`，但被安全组挡住了 |
| 8090 | 运维后台 | ❌ 不可达 | 只映射到宿主机回环（P9 的设计） |

补充事实：

- 宿主机**没有** iptables/firewalld 过滤（`iptables -P INPUT ACCEPT`，firewalld 未运行）
  ⇒ 挡住 5900 的只能是**安全组**，也就是说"改安全组"确实是唯一的收敛点。
- 实例**没有公网 IPv6**（只有链路本地）⇒ `x11vnc` 那个 `[::]:5900` 监听不构成公网路径。
- 容器**不需要重启** —— VNC 三件套（Xvfb + x11vnc + websockify）是宿主机上的
  `dzmm-vnc.service`，跟 bot 容器是分开的。改安全组更是连服务都不用动。

## 二、你的出口 IP

```
117.129.62.15
```

这是刚才那条 SSH 连接的对端地址（`$SSH_CONNECTION` 的第一段），也就是"白名单里要填的那个 IP"。

在安全组里要写成 CIDR 形式：**`117.129.62.15/32`**（`/32` = 只这一个地址）。

> ⚠️ 这看起来是运营商动态地址。**它变了会怎样**：白名单不匹配 → 6080 打不开
> → **但 SSH(22) 还能连**，所以你不会被关在门外，用下面第五节的隧道照样能看 VNC。
> 只是验证码告警里那个链接会失效，需要你回来把规则里的 IP 改一下。

## 三、控制台操作步骤（推荐做法：保留告警链接）

1. 登录 **阿里云控制台** → 顶部搜索 `ECS` → 进入 **云服务器 ECS**
2. 左侧 **网络与安全** → **安全组**
3. 找到这台实例（`47.237.152.187`）所属的安全组 → 右侧 **配置规则**
4. 切到 **入方向** 标签页（**不要动"出方向"**）
5. 在列表里找到这一条：

   | 授权策略 | 优先级 | 协议类型 | 端口范围 | 授权对象 | 描述 |
   |---|---|---|---|---|---|
   | 允许 | 1 | 自定义 TCP | `6080/6080` | `0.0.0.0/0` | noVNC |

6. 点它右侧的 **修改** → 把 **授权对象** 从 `0.0.0.0/0` 改成 `117.129.62.15/32` → **保存**

就这样，**即时生效，不需要重启任何东西**。

### 几个会踩的坑

- **一个实例可能绑了多个安全组，规则是"并集"**。
  如果你有 2 个以上安全组，必须**逐个检查**：
  只要还有任何一个里存在 `6080/6080` + `0.0.0.0/0`，端口就仍然是全公网开放的。
  改完用第四节的方法验证一遍。
- **不要用「一键放通」/「快速添加」** —— 那些会顺手放开一堆端口。
- 如果 6080 那条规则是"快速创建实例时"自动生成的，可能名字里带 `HTTP` 之类，
  按端口范围找，不要按名字找。
- 只改"入方向"。出方向保持默认即可。

## 四、改完怎么验证

**从你自己的机器**（应该仍然能打开，因为你的 IP 在白名单里）：

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://47.237.152.187:6080/vnc.html
# 期望：200
```

**换一个不在白名单的网络**（比如手机关掉 WiFi 用流量）打开同一个地址：

```
http://47.237.152.187:6080/vnc.html
# 期望：打不开 / 一直转圈
```

两边结果不一样，就说明白名单生效了。需要的话我也可以从这边再发起一次
公网 TCP 探测帮你确认（`tools/p0b_recon.sh` 就是为此写的）。

## 五、白名单失效时的兜底：SSH 隧道（**不会丢功能**）

关键点：**把端口对外关掉，不等于用不了 VNC**。SSH 隧道照样能看。

```bash
# ① noVNC 网页（推荐，浏览器直接用，跟原来体验一样）
ssh -L 6080:127.0.0.1:6080 root@47.237.152.187
# 然后本地浏览器打开  http://127.0.0.1:6080/vnc.html
# 密码还是 dzmm2026

# ② 原生 VNC 客户端（如果装了 VNC Viewer / RealVNC）
ssh -L 5900:127.0.0.1:5900 root@47.237.152.187
# 然后 VNC 客户端连  127.0.0.1:5900
```

为什么这样能通：`websockify` 监听在 `0.0.0.0:6080`，所以本机 `127.0.0.1:6080` 也是通的；
`x11vnc` 同理。隧道把服务器本机的端口映射到你本机，**不经过安全组**。

⚠️ 注意：**验证码告警里那个链接**（`VNC_URL=http://47.237.152.187:6080/vnc.html`）
在方案一是有效的；如果你哪天把规则删了（方案二）、或者出口 IP 变了，
那个链接就会打不开 —— 这时用上面的隧道。想让它显示成"请用隧道"可以在
`.env` 里改 `VNC_URL`，但那要重启容器才能生效。

## 六、方案二：更彻底（彻底不外露）

不想依赖"我的 IP 不变"的话，直接把 `6080/6080` + `0.0.0.0/0` 那条规则**删掉**：

- 好处：与出口 IP 无关，任何网络都打不开；攻击面彻底归零。
- 代价：验证码告警里的链接永远失效，**每次都要走隧道**。
  手机上要装一个 SSH 客户端（如 Termius）才方便应急。

**我的建议**：先用方案一（改授权对象）。它把"全世界都能试密码"变成
"只有你能连"，同时保住告警链接这条应急路径。出口 IP 变了再回来改一下即可。

## 七、还有一件更值得做的事：换掉弱密码

`dzmm2026` 本身太弱。安全组收窄之后它的风险大幅下降（只有你能连），
但真正干净的做法是换个随机密码。

```bash
# 1) 改宿主机上的密码来源（VNC 服务读的就是这个文件）
#    编辑 /opt/dzmm/.env  →  VNC_PASS=<新的随机串>
# 2) 重启 VNC 三件套（**不影响 bot 容器**）
systemctl restart dzmm-vnc
# 3) 验证
ss -lntp | grep 5900        # 确认还在听
```

⚠️ **但有一个坑**：容器里的 `VNC_PASS` 是**启动时**读进环境的，
验证码/心跳告警里显示的密码来自容器环境 —— 只改宿主机 `.env` 而不重启容器，
告警里会继续显示**旧密码**，而这恰好会在你最需要它的时刻误导你。

所以要是换密码，顺序应该是：

1. 改 `/opt/dzmm/.env` 里的 `VNC_PASS`
2. `systemctl restart dzmm-vnc`（VNC 立刻用新密码）
3. `cd /opt/dzmm && docker compose up -d dzmm-bot`（重建容器读新值，bot 中断约 10 秒）
4. 确认启动自证行都在：`docker logs --tail 30 dzmm-bot`

第 3 步会短暂重启 bot。想做到零中断的话，也可以先只做第 1、2 步，
然后等下一次本来就计划重启容器时顺带生效 —— 但中间这段时间要记得
**告警里的密码是旧的**。
