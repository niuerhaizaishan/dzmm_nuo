# P12-AO：小小糯"叫错名字"——成员表被平台静默截断到 101 人

> 屋主 2026-09-29："**为什么有人@你的时候，小小糯有时候会叫错名字？**"

## 1. 现象

茶水间/认证群里 @ 她，有时候她回话时用的名字**不是这个人在群里的昵称**，
偶尔干脆是一串 uid（`bcec3c30`、`4f8d0b08` 这种）。"有时候"是关键词 —— 同一个人
有时对、有时错，说明不是人称/提示词问题，而是**名字来源本身不稳定**。

## 2. 排查：先排除两个想当然的假设

| 假设 | 验证 | 结果 |
|---|---|---|
| 同一个人在多个群里昵称不同 → 缓存串了 | 把 认证群 74 / 上班群 56 / 茶水间 101 / 玫瑰房 25 共 236 个 uid 的群昵称互相对账 | **0 个不一样** ❌ 不成立 |
| 提示词/人设里名字规则写错了 | 读 `CMD_PROMPT` 的称呼规则 + 实测生成 | 规则正常 ❌ 不成立 |

（`_name_cache` 是**全局按 uid 存**的，所以"跨群串名"本来是最像的凶嫌 —— 排掉它之后
才去找"名字从哪来"。）

## 3. 真因：`chatroom.getMembers` 默认只返回 101 人

`dzmm.get_members()` 原来这样调：

```python
data = api("chatroom.getMembers", {"json": {"chatroomId": chat_id}}, cookies)
```

**没传 `limit`**。平台不报错、不提示还有下一页，**直接静默截断到 101 个成员**：

```
原样（无 limit） → 101 人      茶水间实际 782 人
limit=1000      → 782 人  ✅
limit=2000      → 782 人
```

于是茶水间 **681 个人从来没进过昵称缓存**。这些人 @ 她时，`get_full_name` 在事件循环上
（P12-AA 起刻意不发 HTTP，避免堵循环）只能退化成：

```
昵称缓存 → 档案名（profiles 里的旧名）→ uid 前 8 位
```

这就是"叫错名字"的真身：**叫她正在回复的那个人，用的却是档案旧名或一串 uid**。

### 逐条对账（近 300 条真实消息，拿平台现名当基准）

| 群 | 成员数 | 近 300 条发言人 | 名字对不上 |
|---|---|---|---|
| 认证群 | 74（≤101，**全在缓存里**） | 14 | 5（其中 3 个是"不在成员表"的外来号） |
| 茶水间 | **782（只有 101 进缓存）** | 15 | **5 个被叫成一串 uid / 查不到名字** |

茶水间那 5 个（`bcec3c30`、`4f8d0b08`、`00cf2380`、`4daa2fb8`、`f39eb037`）
在 `limit=2000` 下**全部恢复真名**，一个不剩。

**认证群只有 74 人 ≤ 101，所以那边一直是对的** —— 这正是屋主感觉"有时候"的原因：
**只有掉出前 101 的人才会错**，跟"今天她心情/上下文"无关。

## 4. 次因（本轮**不修**，屋主定）

`get_name()` 的截断规则会把**名字里自带的括号**当成尾巴切：

```
辉（哦呀～❤️❤️❤️❤️❤️）（💍）Lv.3   →  辉（哦呀     ← 半截括号 + 半截名字
```

（`～` 在括号**内部**，先被当成后缀切掉了。）屋主选 B：**只补全成员名，截断规则不动**
（这种名字是个位数的人，且改截断规则要动所有群的称呼，收益/风险不划算）。

另外这些"对不上"是**设计意图**，不算错：

```
糯糯～（裳姐姐的骚贱小母狗❤）      →  糯糯
琰晏～                            →  琰晏
夕瓜［见习修女］（青巫妈妈的专属机仆🖤） →  夕瓜［见习修女］
```

## 5. 修法

| # | 改动 | 文件 |
|---|---|---|
| 1 | `get_members(chat_id, cookies=None, limit=MEMBER_FETCH_LIMIT)`，显式带 `limit=1000` | `dzmm.py` |
| 2 | 预载时若正好拿到 **101** 或 `MEMBER_FETCH_LIMIT` 人 → 记一条"成员表可能被截断"告警（一次），不再静默 | `runtime/identity.py` |

`limit` 是**功能参数不是优化参数**：不带它 = 大群里四分之三的人没有名字。

## 6. 测试

`tests/test_member_roster.py`：

- `test_get_members_sends_a_big_enough_limit` —— 请求体里必须带 ≥1000 的 limit；
- `test_load_member_names_keeps_every_member` —— 782 人全部进缓存，本地不再截断；
- `test_truncated_roster_is_reported` —— 又只拿回 101 人时日志里看得见。

## 7. 复盘

- **"接口没报错"不等于"数据是完整的"**：这个截断静默了不知道多久，靠"数一数"才发现
  （782 人群只回来 101 个）。**凡是一次性列表接口，都要问一句"到底全不全"**。
- **不要把"带 limit 分页"当优化**：它决定的是"四分之三的群友有没有名字"。
- **降级路径本身是合理的，但它会把问题伪装成人格问题**：`档案名 → uid 前 8 位` 这条
  链在冷缓存时是对的（总比堵死循环好），可一旦上游长期缺数据，它就从"兜底"变成"常态"，
  表现出来像"她记性差/叫错人"。**兜底被触发得太多时，要查上游，不要改兜底。**
- **"有时候错"是最有价值的线索**：它排除了"规则写错"（那会一直错），指向
  "数据有缺口的子集" —— 顺着这条去找 101 这个数字，比读十遍提示词有用。
