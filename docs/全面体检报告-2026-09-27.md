## 2. 运行时架构（数据流）

```
平台(dzmm.ai)
 ├─ 官方 Bot API  ← 出站：文本（含长消息/表情）
 ├─ Webhook(:8091,回环) → SioSubscriber 队列 ← 入站（平台直推，首选）
 ├─ Socket.IO 侧车账号 → 同一个队列         ← 入站（兜底）
 └─ HTTP 轮询兜底（低频对账）
            │
   _run_all：1 个 Sender + 1 份 state + 1 个 subscriber
            │  DZMM_PARALLEL_GROUPS=on → 每群一个 asyncio 任务
            ▼
   main_loop(cid) 循环（每轮 ~0.8s）
     ├─ subscriber.drain(cid) → 消息
     ├─ 指令分派链（49 分支，逐分支 _feat_on 闸门）
     ├─ @消息 / 房间分支 / 私聊
     ├─ 5 个状态机的时间驱动检查（发骚/调教/公演/剧情/投票）
     └─ 生成一律走 asyncio.to_thread（73 处），结果 → OutboxSender
            ▼
   OutboxSender → SQLite 出站队列（状态机：pending/sent/failed）
            → RoutingSender：群文本走官方 Bot；图片/私聊/需撤回走账号通道
```

| 层 | 存放 | 生效方式 |

## 5. 代码结构与并发（深挖）

### 5.1 `bot.py` 的分派链

- 分派链在 `main_loop` 内（`bot.py:2971–3290`），**49 个顶层分支**（1 `if` + 48 `elif`），
  与 `runtime/features.py` 的归属表**顺序一致**（有测试钉住）。
- 28 个分支把工作包进 `asyncio.to_thread`；`to_thread` 全文件 55 处 ✅ 方向正确。

### 5.2 仍然**堵事件循环**的调用（按影响排序）

| # | 位置 | 问题 | 触发条件 |
| --- | --- | --- | --- |
| 1 | `bot.py:3642 → 1240` | `_handle_climax` 里**直接调 LLM** `generate_heat_climax`，且前面 `get_messages_all` 也是平台读；整段无 `to_thread` | 认证群发情值满阈值（`heat_climax` 开） |
| 2 | `bot.py:2119`（`_handle_review`） | 同步 `requests.post(timeout=15, retries=2)` → **最长约 45 秒**占着事件循环 | 公演小说审核（`perf_review`） |
| 3 | `bot.py:3227 get_group_name()` | 平台 HTTP（5 分钟缓存，无 `to_thread`） | `/总结` |
| 4 | 16 处 `save_state(state)`、2 处 `load_state()` | 整 scope 磁盘写/读，未包 `to_thread` | 几乎每轮 |
| 5 | `bot.py:1259 → 1064`、`3769` | `_publish_rank` / `_rollback_last_id` 同步整状态读写 | 排行发布、生成失败回滚 |
| 6 | **`bot.py:3361`** | `_retrieve_memory(cid, q, …)` 未包 `to_thread` → `memory.py:117 _call_llm` **LLM 直接跑在事件循环上**（紧邻的 3365 行却包了） | 每条带记忆注入的 @ 消息 |
| 7 | `identity.py:308` | `get_full_name` 缓存未命中时做 `get_user` 阻塞 HTTP；被 `trend/recap/sign/dice` 的 async 函数直接调用 | 每见一个新成员 |
| 8 | `bot.py:4310 greet_once` | `generate_greeting` 直接调 LLM（同功能在 `_scheduled_pushes` 里是**包了**的，属遗漏） | cron 问候 |

> 影响：按群并行后只堵"那个群"，但单群在这一轮里**完全无法处理消息**（表现为"发指令十几秒没反应"）。

### 5.3 并发与共享状态（最需要重视的一类）

- `_run_all` 构造**一份** `state` 字典，然后交给所有按群任务（`bot.py:3842` →
  每群一个 `asyncio.create_task`）。全文件 `save_state(state)` **24 处**（其中
  **`main_loop` 内 16 处**：2804/2849/2963/3167/3328/3393/3402/3408/3419/3438/3451/
  3512/3561/3610/3640/3654），`= load_state()` 10 处。
- `state_store.save_state()` → `save_scope("group", 全部群)` —— **整 scope 重写**。
  两个群同时读改写 ⇒ **后写的把先写的那个群覆盖回去**（丢更新）。
  这正是 P8 重构想消灭的模式，但主循环里还留着整 scope 落盘。
- 其它无锁共享可变全局：`_ACTIVE_CID`（遗留镜像）、`_captcha_active/_notified`、
  `_cookie_cache`、`identity._BOT_NAMES/_BOT_UIDS`（每条消息都可能 `learn_bot_uid`）、
  `features._OVERRIDES` / `tuning._OVERRIDES`（热加载写、其他任务读）、
  以及**骰子局状态**（顶层键、不按群 —— 所有群共享一局）。
- 上下文（`ctx` / `personas._CID`）是 `ContextVar`，按任务隔离 ✅；但
  `_active_cid()` 的兜底会读**全局镜像**，而 `rank_summary`、`get_group_name`、
  `register_user`、`archive_query`、`summarize_chat`、`_insult_*` 等 10 个函数
  **靠"调用方已经 set 过 cid"这个隐含约定**工作 —— 是潜在的串台点（当前未触发）。

### 5.4 导入期副作用

`import bot` 会：读 `config.json`（**不合法直接 SystemExit**）、
**在导入期重写 `config.json` 并生成备份**（`migrate_config_file()` @`bot.py:264`）、
读 `~/.hermes/.env` 取 LLM key（`brains.py:52`）、写 `bot.log`。
→ 测试/工具"只是想 import 一下"也会改磁盘，给工具链带来风险。

## 8. 安全与凭据（本次体检最严重的发现）

### 8.1 镜像里烤进了凭据与成员 PII ⚠️ P0

- `docker-compose.prod.yml:13` 用 `build: .`，构建上下文 = 服务器 `/opt/dzmm`；
  `Dockerfile` 里是 `COPY . .`，而**仓库里没有 `.dockerignore`**。
- `/opt/dzmm` 下真实存在：`.env`(1394B)、`.env.bak-*`（4 份历史凭据）、
  `.dzmm_token.json`(3111B) + `.dzmm_token.json.bak-*`、`profiles.json`(666KB，成员档案)、
  `state.json`、`data/`(15MB)。
- **实测镜像内容**（`docker run --rm dzmm-bot:latest ls -la /app`）确认镜像里就有：
  `.env`、`.env.bak-*`、`.dzmm_token.json`、`.dzmm_token.json.bak-20260926-230732`、
  `profiles.json`、`state.json` —— 即**平台凭据 + 全体成员档案（含性别/签名/简介/XP）**。
- 另外镜像里还有大量垃圾：`%{http_code}n`、`._*`（macOS AppleDouble）、`__pycache__`、
  一次性脚本、旧 md 文件。

**修法（10 分钟）**：加 `.dockerignore`（至少排除 `.env*`、`.dzmm_*.json*`、`state.json`、
`profiles.json`、`profile_scan.json`、`data/`、`novels/`、`backup*`、`*.log`、`tests/`、
`tools/`、`docs/`、`__pycache__/`、`_tmp/`、`.git/`），重新 build，并用
`docker run --rm dzmm-bot:latest test -f /app/.env; echo $?` 验证返回非 0。

### 8.2 做得对的地方 ✅

- `.gitignore` 完整覆盖凭据/配置/运行数据（`.env`、`.dzmm_token.json`、`config/`、
  `state.json`、`profiles.json`、`data/`、`novels/`）；`git ls-files` 里**没有**任何真实凭据
  （只有模板 `config.example.json` 与代码）。
- Webhook 端口只绑 `127.0.0.1`，公网由 Caddy 终止 TLS 反代；Secret 白名单校验 + message_id 去重。
- 运维后台是账号密码登录 + CSRF + 失败锁定 + 会话仅内存；官方文档也提醒安全组只放行自己 IP。
- 出站队列"明确被拒才重试"的三态铁律（避免重复打扰）设计正确。

### 8.3 其它安全/运维提示

- 运维后台绑 `0.0.0.0:8090`（明文 http），靠安全组兜底 —— 建议改成只绑回环 + SSH 隧道，
  或前置 Caddy 加 HTTPS。
- 容器**无内存上限**、宿主**无 swap**：OOM 时内核会杀掉最大进程（chrome 或 python）。
- 服务器上积压 **49 份 `backup-code-*.tar.gz`**（每次部署一份，无保留策略）。
- `bot.log` 已 1.08 MB 且**不轮转**；compose 也没有给 docker json-file 设 `max-size`
  → 长期看是磁盘无界增长（当前磁盘 42% 占用，尚有余量）。
