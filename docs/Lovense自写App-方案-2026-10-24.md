# Lovense Lush 4 Mini × 小小糯：自写 App 方案（2026-10-24）

> 只出方案，不含代码。你确认后再动手。
> 前置文档：[Lovense接入-方案-2026-10-24.md](Lovense接入-方案-2026-10-24.md)（GitHub 复核与三条路线对比）。

## 1. 目标与约束

| 项 | 实际情况 |
| --- | --- |
| 玩具 | **Lovense Lush 4 Mini**，单马达，强度 0~100%（协议内部 0~20 步） |
| 手机 | Android；**官方 Lovense Remote 提示区域不可用，打不开** |
| 服务器 | 阿里云 ECS（Alibaba Cloud Linux 3），无蓝牙，3.5G 内存 |
| 使用者 | 自己用 → 许可证不构成约束（GPL 项目可直接改） |
| 硬性要求 | 手机尽量少装 App；服务器可远程控制；**任何异常都必须能自动停** |

## 2. 选定路线

**手机装 1 个自写 App（直连蓝牙 + 主动连服务器），不用 VPN、不用 Intiface、不经过第三方。**

```
小小糯（服务器）── WSS（出站）──▶ App ── BLE ──▶ Lush 4 Mini
        │                          │
        │  调度器：去重/限幅/自动停  │  本地兜底：硬上限/心跳超时即停
```

与另外两条路的取舍（理由已在前置文档，这里只列结论）：

| | 本方案（自写 App） | Intiface + VPN | lovense-remote |
| --- | --- | --- | --- |
| 手机 App 数 | **1** | 2 | 1 |
| 需 VPN/账号 | 不要 | 要 | 不要 |
| 经过第三方 | 不要 | 不要 | 要（localhost.run） |
| 手机端安全兜底 | **可写死** | 靠 Intiface | 不听我们策略 |
| 型号适配 | 单马达，只需一套命令 | 自动 | 自动 |
| 出 MVP | 2~3 天 | 已完成 | 协议未公开，需逆向 |

## 3. 分层设计

### 3.1 手机 App（Kotlin 原生，单 Activity + 前台服务）

职责边界（写死，不做扩展）：

- **只做执行**：扫 BLE、连设备、按下发强度执行、立即反映停止
- **不理解剧情/音乐**：不调用任何模型，不认识「剧情事件」
- **本地安全兜底**：即使服务器失联，也必须按本地规则停下
- **上报状态**：连接状态、电量、最后一条指令、错误原因

不做的事：不做 UI 美化、不做多设备管理、不做曲线编辑（后续需要再说）。

### 3.2 服务器侧

- **复用已有实现**（在分支 `feat/haptics-draft`，master 上没有）：指令调度器、强度/时长夹紧、`event_id` 去重、最小间隔限流、自动到时停止、控制页
- **新增**：`/haptics/ws`（WSS，Caddy 反代到 `127.0.0.1:8096`）、设备会话表（token ↔ 设备）、把「客户端」从 Buttplug 换成「我们的 App 协议」
- 开关逻辑不变：没有令牌 → 不启动；控制页只绑回环，走 SSH 隧道访问

### 3.3 App ↔ 服务器 协议（自定，极简 JSON）

| 消息 | 方向 | 字段 | 说明 |
| --- | --- | --- | --- |
| `hello` | App→S | `token`, `device_id`, `fw` | 首次连接，校验一次性 token |
| `state` | App→S | `connected`, `battery`, `uuid_set`, `rssi` | 心跳 + 状态，2 秒一次 |
| `cmd` | S→App | `event_id`, `level`(0~1), `duration_ms`, `expires_at` | 一条指令，自带过期与最大时长 |
| `ack` | App→S | `event_id`, `ok`, `applied`, `error` | 执行结果（区分「收到」与「真的执行了」） |
| `stop` | 双向 | `reason` | 幂等急停 |
| `ping`/`pong` | 双向 | — | 保活，兼作链路探测 |

规则：服务器只发**结构化参数**，不拼蓝牙命令；App 收到后先按本地上限夹紧再执行。

## 4. BLE 协议层（针对 Lush 4 Mini）

### 4.1 三套候选服务（来自 Buttplug 的 lovense 协议定义）

| 套 | 服务 UUID | 写（tx） | 读/通知（rx） |
| --- | --- | --- | --- |
| A | `0000fff0-0000-1000-8000-00805f9b34fb` | `0000fff2-…` | `0000fff1-…` |
| B | `6e400001-b5a3-f393-e0a9-e50e24dcca9e` | `6e400002-…` | `6e400003-…` |
| C | `50300001-0024-4bd4-bbd5-a6920e4c5653` | `50300002-…` | `50300003-…` |

设备蓝牙名以 `LVS-` 开头（如 `LVS-Lush4Mini` 之类）；**不要让玩具跟系统蓝牙配对**，由 App 主动扫描连接。

### 4.2 探测流程（App 首次运行时自动做一次，结果缓存）

1. 扫描 → 连接 → 请求 MTU（建议 247，失败就退回默认）
2. 遍历服务，按上表找可写特征；找不到就报「未知固件」
3. 试写 `Vibrate:20;`，两种写法都试：**原样 4~10 字节** 与 **补齐到 16 字节（尾部 0x00）**
4. 若启用通知，观察是否有回包；有回包则记录命令格式
5. 立刻发 `Vibrate:0;` 收尾，**不允许探测时留下持续输出**
6. 把命中的「服务套 + 填充方式」存本地，下次直接用

### 4.3 命令集（够用即可）

- `Vibrate:N;`（N=0..20）：设置强度，**0 即停**
- `Battery;`：电量（低频查询，30 秒一次即可）
- `DeviceType;`：设备类型码，用于确认是 Lush 家族（Buttplug 里 Lush = `S`）

### 4.4 已知不确定项

Lush 4 Mini 属较新固件，**可能是 C 套 UUID，且可能要求 16 字节填充**。文档没有定论，必须实机确认 —— 这正是阶段 0 要解决的全部问题。

## 5. 安全设计（这一节优先于功能）

| 层 | 机制 | 默认值 |
| --- | --- | --- |
| App 本地 | 强度硬上限 | **40%**（可在 App 内调低，不能调高过服务器上限） |
| App 本地 | 单条指令最大时长 | **3000 ms** |
| App 本地 | 心跳超时 | **2 秒无心跳 → 立即停**（不等服务器确认） |
| App 本地 | 停止入口 | 常驻通知栏「停止」按钮 + 音量键双击急停 |
| App 本地 | 探测/异常 | 任何异常路径先发 `Vibrate:0;` |
| App 本地 | 开机自启 | **关闭**（避免意外启动） |
| 服务器 | 强度/时长夹紧、限流、`event_id` 去重、自动停 | 见已有调度器 |
| 服务器 | 令牌一次性、绑定设备、可撤销 | 页面生成，用后作废 |

失败降级一律朝「停」的方向：BLE 断 → 停；WSS 断 → 停；App 被杀 → BLE 断 → 设备自身在无指令超时后停止（App 侧也保证最后一次写的是 0）。

手机 Chrome + Web Bluetooth 实连成功，协议已确定，后续实现不用再猜：

| 项 | 实测值 |
| --- | --- |
| 设备蓝牙名 | `LVS-C21`（C21 = Lush Mini；注意与 Buttplug 的 DeviceType 码不是一套编码） |
| 主服务 | `53300001-0023-4bd4-bbd5-a6920e4c5653`（第三代族，不是 fff0 / NUS / 5030-0024） |
| 写特征 | `53300002-0023-4bd4-bbd5-a6920e4c5653`（W + w 属性，用 writeWithoutResponse） |
| 通知特征 | `53300003-0023-4bd4-bbd5-a6920e4c5653`（N，回包是 ASCII 文本） |
| 强度命令 | `Vibrate:<0..20>;` 原样 ASCII，不需要补齐 16 字节（11 字节） |
| 停止命令 | `Vibrate:0;`（10 字节） |
| 设备回包 | `OK;`——可作为「指令真的被设备接受」的判据，不必只靠"没抛异常" |

`NotFound`；原因是 Lush Mini 用第三代服务族 `53300001-0023`。Chrome 的 Web Bluetooth 只能访问
`requestDevice` 时声明过的服务，所以探测页一次性声明了 36 个候选（4 个静态 + 32 个第三代变体）。

探测页：`tools/haptics/probe.html`，临时部署在 `https://www.nuonuo.pw/img/probe.html`，用完删除。

## 附录 C · 小小糯作为控制者（群指令 /震 /停）· 2026-10-25

### 用法
1. 手机打开 <https://www.nuonuo.pw/haptics/>，连设备、生成分享码
2. **勾上「允许小小糯控制」**（不勾机器人连不上）
3. 群里发：
   - `/震` → 30% / 800ms
   - `/震 50` → 50% / 800ms
   - `/震 50 2000` → 50% / 2000ms（强度 1~100%，时长 200~10000ms）
   - `/停` → 立刻停
4. 只有 `OWNER_UID`（糯糯～）能用；其他人收到「这个指令只有主人能用」。

### 服务端新增
- `POST /api/program/allow`：房主页开关（房主显式授权，默认关）
- `GET /api/program/session`：机器人问「现在哪个房间允许我控制」
- `GET /ws/program`：程序通道，凭 `DZMM_SHARE_PROGRAM_TOKEN`
- `_relay_cmd()`：房主/控制者/机器人共用同一套参数处理，避免三处逻辑分叉
- 客户端发 `bye` 表示正常收工；只有**异常断开**才补停止（否则每条指令刚下发就被自己停掉——实测踩过）

### 部署要点（这次踩到的坑，务必记住）
- **线上 `/opt/dzmm/runtime/dispatch.py` 比仓库里的旧**：仓库版 import `runtime.office`，而线上没有该模块。第一次直接把仓库版传上去，导致 A 实例启动即 `ImportError` 崩溃重启。
- 正确做法：从旧镜像里取回线上那份 dispatch.py（`docker run --rm --entrypoint cat dzmm-bot:pre-haptics-20261025 /app/runtime/dispatch.py`），只插入最小钩子（一行 import + 一段 if），再重建。
- **未来把分支全量部署到线上之前，必须先把 `runtime/office.py` 等缺失模块补齐**，否则会再次崩。
- 宿主机 `python3` 是 3.6，校验不了海象运算符；用容器里的 3.11 校验（`docker run --rm -v ... python:3.11-slim python -c "import ast; ast.parse(...)"`）。
- 回滚镜像：`dzmm-bot:pre-haptics-20261025`（`docker tag` 回 latest 再 `compose up -d dzmm-bot`）。
- 传错的那份 dispatch.py 备份在 `/opt/dzmm/backup-haptics-share-20261025/dispatch.my-upload.py`。

### 已验证
- 51 项单测通过
- 无手机端到端：脚本扮房主页 → 勾允许 → 机器人 `/震 40 800` → 房主收到 `cmd(0.4, 800)`；`/停` → 收到 `stop`；无多余补停

### 白名单（2026-10-25 追加）
`/震` `/停` 的权限 = **群主（OWNER_UID）OR 白名单**。白名单文件：`/app/data/haptics_allow.json`
（宿主 `/opt/dzmm/data/haptics_allow.json`）：

``json
{"uids": ["cf1b1360-7f3f-4ef8-9188-07d718fe9173"], "names": ["御褚"]}
``

- 每次指令都重读文件，**改完立即生效，不用重启机器人**
- 文件缺失或 JSON 坏掉 → 视为空表（宁可不给权限）
- uid 大小写不敏感；`names` 只是给人看的备注
- 加人：把对方 uid 加进 `uids`；撤权：删掉即可
