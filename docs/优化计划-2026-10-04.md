# DZMM Bot 优化计划

> 制定日期：2026-10-04（Asia/Shanghai）
> 状态：待执行，已合并“活页面判死”评估；本轮仅更新文档，没有修改业务代码、运行测试或部署。
> 依据：当前工作区代码、README、既有施工清单与 EXECUTION-LOG；未重新检查生产服务器。

## 1. 目标与原则

优化顺序：**安全边界 → 发布与运行可靠性 → 可观测性与性能 → 模块边界 → 文档交接**。

目标不是重写机器人，而是降低凭据泄漏、静默失败、重复投递和跨群回归风险，让后续功能调整更容易验证。

- 不改变已有群的人设、功能开关、指令优先级、上下文范围和默认话术。
- 不绕过官方 Bot 路由、账号风控、验证码暂停或会话锁。
- 出站结果不明时，不自动换通道重发；只有确定未投递的失败才进入既有安全重试路径。
- 一次变更解决一个问题；安全修复、业务行为调整和结构重构分开验收。
- 复用现有 SQLite、pytest、日志和后台，不引入 Redis、消息中间件或新的监控平台。
- 不自动删除镜像、备份、浏览器 profile 或旧凭据，不自动轮换密钥；生产动作单独确认。
- 历史文档的故障、指标和完成状态不是当前线上事实，执行前必须对照代码及现场证据。
- 会话优化先做取证，再按证据决定同步修复；不同时上线观测与认证行为改变，以免失去可比较的基线。

### 命名与授权边界

- **S1** 仅指原有 Phase 2“凭据挂目录”。2026-10-01 22:01 的历史记录为已上线，不重新实施迁移；旧挂载与双写收尾仍须现场核查。
- **活页面判死** 是新的候选优化，拆为 `AUTH-OBS`（取证）、`AUTH-SYNC`（防降级同步）、`AUTH-DEC`（页面证据参与恢复决策），不再复用 S1 名称。
- 当前仅合并计划，并不授权开始取证代码、同步修复、判死路径改动或线上观察任务。

## 2. 已有能力与当前问题

### 应保留的能力

- 主循环已迁入 runtime；按群并行是同进程 asyncio 任务，共享发送器、状态和订阅器。
- 群上下文已使用 ContextVar 隔离；SQLite 已有连接锁与 WAL。
- Outbox 已有持久化记录、同群串行、安全重试和失败可见性，不重新造队列。
- 配置 schema 已为 v4，有迁移、备份、热加载和原子保存；提示词已外置。
- 运维后台已有登录、失败限流、CSRF 和安全响应头，不退回早期裸面板方案。
- CI、未定义名字和静默异常守卫已建立；最近会话修复已有死残留 cookie 判断与 Singleton 锁清理。

### 会话方案的现状校正

- renew 的业务探针使用文件 cookie 调用业务接口，但不是仅凭文件过期时间就重启；已有业务验证、风控墙判断和内联密码重登。在当前未授权分支，重登 `skip` 不立即降级 emergency，其他升级分支也要分别检查。
- `_refresh_token()` 已按“先尝试浏览器抄回，再读文件并 add_cookies”的顺序运行。风险主要在节流、锁占用、写回失败和异步并发窗口，不是每次发送都必然覆盖新凭据。
- `_last_harvest` 在抢锁之前更新；锁失败也消耗节流窗口。抄回代码还未检查 `token_store.update_cookie()` 的返回值，因此现有“已抄回”日志不能单独证明写入成功。
- 主循环已有每 10 分钟定时抄回，不是完全没有静默期保护；官方 Bot 发送成功也不能证明账号浏览器会话有效。
- 用户提供的“约 130 次 / 35 天、最坏 17 次 / 天、最长 8.8 小时”仅作历史问题背景，未在本轮核验，不能直接作为 2026-10-03 修复后的基线。

### 阶段 2：会话取证、失败语义与发布可靠性（约两至三个工作日；同步修复按证据另计）

**AUTH-OBS：第 0 步，只观察，不改变认证决策**

目标：验证是否实际发生“覆盖前浏览器较新 → 抄回跳过或失败 → 文件旧值灌入 → 浏览器凭据倒退”的完整事件，而不是只统计页面与文件偶尔不同。

- 首批只改观测，不改变 `_refresh_token`、凭据写回、页面重载、续期和 emergency 的决策，不调整节流或锁策略。
- 观测必须覆盖 add_cookies 之前与之后，以及抄回节流、锁占用等提前返回路径；只在 `_harvest_token_locked()` 内记录会漏掉关键窗口。
- 记录采样时间、当前 bot 实例标识、目标 origin、cookie domain/path、两边凭据的脱敏指纹与 payload `expires_at`，并区分浏览器 cookie 自身的 `expires`。
- 使用明确名称 `browser_context_cookie`，不把 cookie 值当成 SPA 内存中的实际认证状态，不仅按同名 cookie 取第一项比较。
- 记录抄回原因与结果：无 context、节流、锁占用、无 cookie、解析失败、两边相同、无法排序、写回成功或失败；用返回结果和读后核验判断是否真正写回，不只复用旧日志。
- 可保存脱敏快照 `data/page_token_state.json`，必要时保留有限事件摘要；完整 token、refresh_token、密码和原始 cookie 不得落盘或出现在日志。
- 快照原子写入，日志限量，诊断异常不得使 `_refresh_token()` 返回失败或触发退出；不把“不改变认证逻辑”称为严格零运行开销。
- 每 10 分钟定时抄回只能提供粗粒度静默期样本；首批快照仅用于诊断，不能承诺它足够实时，更不能让 renew 读取它并据此放弃恢复。

**取证验收与决策门**

- 新增观测测试，并复用 `test_token_harvest.py`；覆盖节流、锁失败、写回失败、多域 cookie、无 context、相同及不可解析凭据。
- 证明观测前后原有认证、发送、热加载和恢复决策不变，状态文件失败不影响业务，产物没有敏感内容。
- 经确认上线后至少观察 24 小时，并记录发送、静默、锁竞争与续期窗口的覆盖情况。未命中不等于证伪：先判断是否观察到了目标场景。
- 首批不与 AUTH-SYNC 同时上线；与其他认证、挂载、重登策略变更分开。独立的 LLM/部署修复可以准备，但上线时间与 revision 必须记录。
- 命中完整事件后进入 AUTH-SYNC；若未命中或业务已改善，延长观察或转向其他原因，不直接扩大判死改动。

**AUTH-SYNC：第 1-1 步，证据成立后的候选修复**

不能简单按“文件相比上次变化了”决定灌入。必须先确定目标 cookie、会话来源和可信的更新关系，保留外部续期与显式重登路径。

| 情况 | 设计方向 |
|---|---|
| 两份凭据完全相同 | 不重复灌入认证 cookie；其他 cookie 的同步独立审查。 |
| 同一会话，浏览器凭据明确更新 | 保留浏览器新值，不让文件旧值覆盖；写回仍遵守原会话锁。 |
| 同一会话，文件凭据明确更新 | 灌入并保持必要的页面重载联动。 |
| 凭据不同但 expires_at 相同，或无法解析/识别来源 | 视为无法排序，不擅自选一份，更不改为永久跳过恢复。 |
| 文件来自一次明确的新登录 | 走明确的重登同步路径，不能仅因浏览器 expires_at 更晚就拒绝新会话。 |

- `expires_at` 是有效期，不是完整的凭据版本号；一次旧采样也不足以消除 SPA 自刷新和跨群共享 context 的并发窗口。
- 单文件修改可以减少代码冲突，但仍与 renew 共享凭据；合入前核对锁、版本与重载契约。
- 修改前补齐节流/锁竞争、写回失败、相同过期时间不同凭据、新登录、跨群并发和页面惰性重载的行为测试。
- 独立发布，验收凭据倒退事件消失、文件有效续期仍能同步、无新增假成功或重复发送；证据不足则保留取证，暂不修改同步策略。

**AUTH-DEC：第 1-2 步，暂缓恢复决策改动**

- 不以 `page_exp > now`、页面仍打开或聊天界面仍显示作为会话存活证明。
- 若以后实施，必须有当前实例、新鲜度限制，以及账号浏览器真实认证业务请求的成功证据；官方 Bot API 成功不能替代。
- 文件与浏览器证据冲突时优先有界复核，或同步后重新业务验证；不能永久禁止 emergency，也不能把 snapshot missing/stale 当成 unauth。
- 沿用 ok / unauth / error / captcha / locked / backoff 的区分，保留真实死会话的恢复兜底。
- 该步骤涉及 renew 与会话恢复契约，须单独设计、协调及批准，不属于首批执行范围。

**REL-01：生成层错误可分类**

- 区分鉴权、限流、服务端错误、超时、非 JSON、响应结构错误及合法空内容。
- 保留成功接口、人设注入、token 预算、续写拼接与现有业务语义。
- 错误日志记录分类、状态码和耗时，不记录 API key、完整提示词或群友原始档案。
- 先补可见性，不立即加自动重试；后续重试须限制次数、总时间和费用，不能重跑已有状态副作用的整条业务链。
- 对接现有消息回滚与用户提示，避免无声丢失，也避免同一条消息永久快速重试。

**REL-02：发布失败不再伪装成 SSH 故障**

- 区分连接失败与远端执行失败，保留准确退出码与脱敏错误摘要。
- 任意 `-Action exec` 默认不自动重试；只有明确安全的操作允许有限重试。
- 审查部署中的 `|| true`，关键备份失败不得显示成功或继续无保护发布。
- 顺序固定为上传完整性检查、构建、启动、健康闸门；关键步骤失败立即停止。
- 优先复用 `tools/active/deploy_gate.py`，不另造重复验收体系。

**OPS-01：会话与 S1 双写收尾**

- 核对 renew、mainloop、token_store 与宿主看护脚本的实际读写路径、锁关系和恢复分支。
- 固定“真死先热恢复”“恢复成功不重复 emergency”“死残留 cookie 不短路复用”等测试。
- 检查双写期间的 EBUSY、路径分叉及旧路径读取；形成完整稳定观察后，才另行确认撤旧挂载。
- 旧凭据先受控留作回滚，不直接删除；暂不大改恢复状态机，先证明日志与实际路径一致。

**验收**：AUTH-OBS 先独立通过观测等价性验收；AUTH-SYNC 仅在证据门满足后执行。模型故障测试覆盖 401/403、429、5xx、超时、非 JSON、缺字段和正常续写；部署测试覆盖连接失败、远端非零、上传缺文件、备份失败及不安全 exec 不重试。相关回归与全量测试通过，无新增死循环、错误降级或重复投递。

**回滚**：各任务独立发布；先移除有问题的诊断，不连带改变认证路径。同步变更退回前必须核对当前有效会话，代码回滚不得恢复过期 token 或覆盖当前运行配置。

### 阶段 3：测量驱动的性能优化（约一个半至两个工作日）

**OBS-01：补齐链路耗时**

- 在既有日志上增加消息追踪标识，不直接使用完整用户身份。
- 区分入站等待、判定、上下文读取、模型生成、出站锁等待与实际发送耗时。
- 记录事件循环延迟、线程池工作、恢复分支和最老待处理年龄；只收集有用途的数据。
- 正常日志采样、异常摘要保留，避免测量本身造成磁盘和 CPU 压力。

**PERF-01：只优化已证实的瓶颈**

- 核查热路径同步网络、文件及数据库操作是否阻塞事件循环；逐项隔离，并核对线程与 Playwright 对象边界，不盲目使用 to_thread。
- 若证明确有线程池互相挤占，再考虑独立且有限的并发预算，不直接扩大池规模。
- 仅对可失效、收益明确的重复读取加缓存，明确群/人隔离、TTL、容量及热加载失效条件。
- 不缓存轮换 token，不让缓存改变人设、成员身份或权限判断。

**验收**：固定输入和可控模型/平台替身进行前后对比，线上另行观察。暂定所选瓶颈路径本地 P95 降低至少 20%，阶段 0 后校准；这不是已经实现的承诺。未优化路径无显著退化，多群慢任务和突发测试中其他群仍可处理，同群顺序不变，资源有界，无新增重复发送、串群、持续积压或内存增长。

**回滚**：缓存与并发调整独立于业务行为，可退回原路径，保留账号发送限流和风控。

### 阶段 4：渐进收紧模块边界（约两至三个工作日）

1. 补足消息选择、触发优先级、功能关闭和未轮到消息 requeue 的行为测试。
2. 从主循环抽取纯判定与标准化逻辑，保持输入输出和分支顺序不变。
3. 在抽取点使用小范围显式依赖，避免继续传递整个 bot 模块，不一次替换全部 `B`。
4. 明确当前群上下文、进程风控、持久化与发送状态的所有权。
5. 逐项减少重复读口与隐式全局，保留 re-export 和测试兼容入口，验证后再撤。
6. 关键源码字符串断言先补成行为测试，再决定是否移除旧断言，不为重构直接删测试。

**验收**：等价行为、路由、并行和全量测试通过；未定义名字与静默异常守卫继续通过，不放宽阈值。身份、功能开关、顺序、群隔离、续写和中断恢复不变。不以行数下降为唯一标准，必须证明依赖明确且逻辑可独立测试。

**回滚**：每次抽取独立；不能证明等价的部分保留原实现。不同时更换 schema、存储后端、人设默认值或发送通道。

### 阶段 5：文档与交接收口（约半个工作日）

- 更新 README 的目录数量、实际启动模型、凭据路径、测试环境与命令。
- 旧施工清单归为已完成、待现场核实、本轮待办、不再适用，避免重复施工。
- 整理最小运维手册：发布、健康检查、会话失效、验证码、数据恢复和代码回滚。
- 每次发布记录 revision、测试结果、备份标识、健康闸门和观察结论。
- 文档仅使用占位符与脱敏实例，不复制真实密码、token 或群友资料。

**验收**：新维护者能按文档完成隔离环境启动、测试与定位，历史记录和当前事实清晰区分。

| 活页面取证/同步 | 新增脱敏观测与同步行为测试、`test_token_harvest.py`、`test_parallel_groups.py`、`test_session_persistence.py` |
| 会话恢复 | `test_session_lock.py`、`test_session_persistence.py`、`test_renew_session_probe.py`、`test_renew_hardening.py` |

| 边界重构 | `test_dispatch_smoke.py`、`test_commands.py`、`test_bot_routing_chain.py`、未定义名字和静默异常守卫 |

顺序：定向测试 → 全量 pytest → CI → 发布包检查 → 经确认部署 → 健康闸门 → 稳定观察。

建议观察政策（执行前确认）：一般小变更至少 30 分钟；会话、凭据挂载与共享状态变更至少 24 小时，并验证目标故障场景。时间经过不等于验收，低流量观察不能替代故障注入。

### 活页面方案的专项验收口径

- 24 小时主要用于机制取证，不用于证明长期频率已经达标。首阶段关注覆盖前后凭据关系、抄回跳过原因和诊断可靠性。
- 用户提出的 **emergency ≤0.5 次/天** 保留为候选长期目标；采用当前版本连续 7–14 天窗口，同时标记每次部署，不能直接混用修复前 35 天统计。
- 除 emergency 实际触发外，同时验收业务不可用时长、恢复耗时、重复重登、凭据倒退和写回失败。减少重启不能以失去真正的故障恢复为代价。
- 全程仅观察账号浏览器的认证证据，不以官方 Bot 发送成功或未来过期时间证明账号可用。

停止或回滚条件：重复投递、串群/身份错误、状态写入失败、关键配置失效、登录态恶化、不可解释积压，或稳定性显著劣于基线。

## 5. 工作量与执行边界

| 阶段 | 估计 | 前置条件 |
|---|---|---|
| 0 基线 | 0.5 个工作日 | 测试环境；线上核查需确认访问 |
| 1 安全 | 0.5–1 个工作日 | 本地可先修；产物核查单独确认 |
| 2 取证与可靠性 | 2–3 个工作日 | 基线建立，安全规则完成；AUTH-OBS 先独立上线 |
| 2 条件任务 AUTH-SYNC | 额外 1–2 个工作日 | 机制证据成立，同步/重载契约与行为测试明确 |
| 3 性能 | 1.5–2 个工作日 | 错误分类与耗时数据可用 |
| 4 边界 | 2–3 个工作日 | 关键行为测试与运行指标稳定 |
| 5 文档 | 0.5 个工作日 | 各阶段随改随更，最后收口 |

必做范围约 **7–10 个工作日**；若证据成立并纳入 AUTH-SYNC，总体约 **8–12 个工作日**。不含 24 小时取证等待、7–14 天长期观察、审批与外部故障处理；阶段 0 后校准，不构成固定完工日期。AUTH-DEC 暂不估时、不承诺实施。

本计划当前仅为文档合并，代码与测试变更均待后续明确授权，测试执行按当前审批方式确认。部署、读取生产敏感产物、迁移挂载、凭据轮换、历史产物删除和恢复覆盖需独立确认。默认不创建分支、不提交、不推送。
