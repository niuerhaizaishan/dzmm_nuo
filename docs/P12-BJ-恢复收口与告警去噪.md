## ① 告警按窗口去噪

一个坏窗口是 **4~8 小时**，原来每 5 分钟一条日志、每小时一条 EMERGENCY 微信（一个窗口十几条）。
现在用 `data/renew_bad_window.json` 记窗口起点：

- 进窗：一条（含"这轮是墙还是会话死"）；
- 出窗：一条（`OK: 续期恢复正常（本轮共坏 N 分钟）`）；
- 窗口内：只写日志文件，不发微信。

# P12-BK：查"418"时挖出来的两个真东西

## 发现 A：**平台的风控是"按 User-Agent 挑战"的** —— 宿主那个"418"是它自己造成的

同一个端点、同一时刻，只换 UA（`tools/probe_ua_wall.py`，容器内实跑）：

| UA | 首页 | `/api/auth/token`（带我们的 cookie） |
|---|---|---|
| `requests` 默认 | 200 ✅ | 200 有 token |
| `Mozilla/5.0 DZMM-Agent/1.0` | 200 ✅ | 200 有 token |
| Chrome 126 | 200 ✅ | 200 有 token |
| **`Python-urllib/3.11`** | **403** | **403（WAF 拦截页）** |

而 `monitor_recover.py` 的首页探测用的正是 **urllib 默认 UA** ⇒ 它三周来一直记"418"、
**永远看不到"风控解除"**、它的自动重登因此从未生效过。
把 UA 补上之后，同一个脚本立刻开始记 `首页=OK`（已上线验证）。

顺带确认：容器里的 `check_network()`（体检）与 `dzmm.api()` 用的是 `requests` 默认 UA ⇒ **不受影响**，
P12-BI 的墙判定也带了 Agent UA ⇒ 可信。

## 发现 B：token 刷新是**单向**的 —— SPA 自己轮换过之后，我们手里那份就是旧的

```
_refresh_token()  :  JSON ──→ 浏览器      ✅ 有
SPA 自己刷新       :  浏览器里换掉 refresh_token（**轮换制**，旧的随即作废） ✅ 平台行为
反向抄回           :  ✗ 没有任何代码        ← 缺口
```

于是 `renew_token` 拿旧 refresh_token 去续期 → 平台回"未授权" → 被判"会话真死"。
这与"坏几小时后自己又好"的形状吻合（页面某次刷新后我们才跟上）。

新增 `Sender._harvest_token()`（每次发送前调、内部 60 秒节流）：

- 读**浏览器 profile** 里的 `sb-rls-auth-token`，解两边 payload 的 `expires_at`；
- **只有浏览器那份更新才写回**（更旧/一样 ⇒ 一个字不动）；
- 任何异常都不影响发送；
- 写回后打一行 `🔑 浏览器里的 token 比 JSON 新 → 已抄回（SPA 自己刷新过）`。

- 每次墙窗口第一轮的探测结果会**落盘**成 `data/wall_probes.jsonl`（一行一个窗口：
  本节点首页状态、12 个镜像各自的 `home`/`token`、探测耗时）。落在 `data/`（挂载卷）里，
  容器重建不丢。
- 决策工具：`tools/analyze_wall_windows.py`（容器内 `python /app/analyze_wall_windows.py`）：

  | 攒到的样子 | 结论 |
  |---|---|
  | 墙里本节点不可用、**至少一个镜像 `home=200 + token-ok`** | **值得做自动切换**（切换 = 改 `.env DZMM_HOST` + 重启容器，`switch_node.switch_to` 有现成实现，含 cookie domain 与飞书告警） |
  | 墙里**所有域名都一样不可用** | **别做** —— 换了没用，还白搭一次容器重启 |
  | 样本不足（没抓到墙 / 本节点在墙里也可用） | 继续攒 |

  判读工具会直接把这三种结论打出来，不用人肉看日志。
