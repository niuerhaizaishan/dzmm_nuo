## 三、与原方案的三处实质分歧

### 分歧 1：不需要自己写安卓中继 App

原方案把「自建安卓中继」当成必经之路，估算 4~6 周主要花在这。但现状已经有三种现成载体：

- **Tailscale / WireGuard 打通网络** → 服务器直接连手机上的 Intiface（Buttplug v4，官方协议），**零安卓代码**
- `signal_bridge_android`（MIT）现成中继 App + 自写服务端
- `kerstz/lovense-remote`（GPL）或 `Chloe-Vibes`（MIT）直连 BLE，完全不装 Intiface

推荐第一条：协议用官方 Buttplug v4（有 `buttplug-py`），网络用私有 mesh，**第一版不需要写任何安卓代码**。

### 分歧 2：音乐模式不用从零做，也不该放服务器

原方案计划 5~7 天做「音乐分析 + 时间线」，并且倾向在服务器做。两点都不优：

- `Chloe-Vibes` 已经把这套做完了，而且文档化（MIT）：2048 点 FFT + Hann 窗、8 个感知频段（20/60/250/500/2000Hz…）、谱质心与半波整流谱通量、自适应阈值 onset 检测（43 帧窗口均值 + k·标准差）、tempo 跟踪、ADSR 包络、心跳停顿 2 秒强制停止。
- 服务器（3.5G 内存、无 numpy）做实时音频分析性价比极低；音乐必须**在出声设备本地**实时处理才有意义（网络抖动会把节拍变成噪声）。

结论：**音乐模式先直接用 Chloe-Vibes（0 开发）**，小小糯只负责「事件强调」（谁、什么时候、多强、多久）。等确实需要「同一套逻辑统一控制」时，再按它文档移植算法。

### 分歧 3：团本联动的前提不是触觉，是规则程序化

原方案把《月之瞳》规则结算和触觉一起做。实际上规则程序化是**独立价值**（现在 DM 提示词兼记位置/骰子/卡牌/密码，容易算错），而且原转录指出的 4 处歧义必须先定死：

1. 装置数量「48 台」vs「47 台」
2. 密码地图是格 5①/格 12②/格 9③，示例却写「格 6 拆除后出现密码③」
3. 「拆掉后该格变中立」与「同格再踩换下一台」的适用顺序
4. 两圈结束需累计移动步数，不能只看当前格号

**建议先做规则程序化（不带任何触觉），再接事件→触觉。** 这样触觉层拿到的是「已确认事件」，天然满足「回顾剧情不重放」。

## 四、推荐架构

```
┌─────────────── 小小糯（现有 Python 服务） ───────────────┐
│  webhook / 群消息 ──► 剧情理解（LLM，输出受约束的节奏意图）│
│  《月之瞳》规则程序 ──► 已确认事件（含目标玩家、事件号）  │
└──────────────────────┬──────────────────────────────────┘
                       │ 结构化指令（event_id / expires_at /
                       │            max_duration / 可取消 / 急停）
              ┌────────▼─────────┐
              │ 触觉调度器（新） │  合并剧情与音乐、限幅、平滑、去重
              └────────┬─────────┘
                       │ WSS（Caddy /lovense/ws，独立端口 8096）
        ┌──────────────▼───────────────┐
        │ 手机：Tailscale + Intiface   │  ← 蓝牙
        │ 或 ChloeVibes（音乐本地执行）│
        └──────────────┬───────────────┘
                       ▼
                  设备（Lovense）
```

设计要点：

- **独立进程**：触觉服务单独跑（`127.0.0.1:8096` + Caddy 路由），不塞进 `webhook_server.py`。群消息投递是热路径，设备控制要有独立重启能力。
- **指令只由调度器生成**：模型只输出「意图参数」，不能拼设备命令。`event_id` 去重、`expires_at` 过期即弃、每条有最大时长、新事件可取消旧事件。
- **三道停止**：手机端（App 自带 / 通知栏）、调度器（暂停、撤销绑定、断连）、服务端（会话超时）。断联 2 秒无心跳即停（Chloe-Vibes 的做法，值得照抄）。
- **音频不跨网**：节拍在本地跑；跨网只传「节奏配方」而不是每个节拍。
- **不做无界叠加**：任何模式下强度上限、最大连续时长、冷却都要有硬上限，写在手机端而不仅是服务端。
- **隐私**：只存事件 ID 与执行状态，不存原始私密聊天内容。

## 五、分阶段计划

| 阶段 | 内容 | 产出 | 工期 |
| --- | --- | --- | --- |
| **0. 可行性验证** | 手机装 Intiface Central → 连设备；同 Wi-Fi 下用 `buttplug-py` 跑通 扫描/低强度 1 秒/停止 | 确认设备能被识别、指令能执行、端到端延迟 | 0.5 天 |
| **1. 远程控制骨架** | 手机加 Tailscale（或 WireGuard），服务器连 `ws://<手机 tailnet IP>:12345`；新增 `runtime/haptics/`（调度器 + 客户端）、独立服务与 Caddy 路由、控制页（独立登录、绑定 token） | 服务器远程 test / pause / stop；断网自动停 | 3~5 天 |
| **2. 音乐模式** | 先直接用 ChloeVibes 做背景节奏（0 开发）；确实要统一时再移植算法（FFT/onset/ADSR）或前端 Web Audio 分析生成时间线 | 音乐播放时设备随拍点；暂停/切歌即停 | 0~3 天（取决于是否统一） |
| **3. 团本联动** | 先程序化《月之瞳》规则（地图/回合/骰子/密码/胜负）并修掉 4 处歧义；再接「已确认事件 → 触觉」映射表，控制页逐项开关 | 一局完整回放：两名玩家只收到各自提示，刷新/重连/重复消息不重复触发 | 5~8 天 |
| **4. 自适应节奏** | 剧情状态分析（紧张度/节奏/事件类型），平滑过渡、保留上一段节奏状态、玩家指令优先 | 紧张升级时节奏变密，转场时减弱，任何时候可停 | 3~5 天 |
| **5. 硬化** | 真机长跑、Doze/后台存活、重连、断网、设备掉线、并发两玩家 | 一周稳定性观察 + 验收清单 | 3~5 天 |

**关键路径**：阶段 0 半天，阶段 1 一周内可到「远程能控」。整体 2~3 周（原方案 4~6 周），省下来的时间主要来自「不写安卓 App」和「音乐不自己造」。

## 六、控制路线已落地（2026-10-24）

先把「控制」这条链路做完了，**不含剧情和音乐**（按你的要求：先把控制整明白）。

### 定下来的路线

```
小小糯（Python）→ Scheduler → ButtplugClient ──WSS/WS（出站）──▶ 手机 Intiface Central ──蓝牙──▶ 设备
```

- 服务端**只做出站连接**，不开放任何入站端口 —— 没有公网回调、没有二维码、没有中继协议要逆向。
- 网络用私有 mesh（Tailscale / WireGuard）打通，手机在 NAT 后面也能被连到。
- 协议用 Buttplug v4（Intiface 的原生协议），命令是 `OutputCmd`：`{"Vibrate": {"Value": n}}`，设备区间由 `DeviceAdded` 里的 `DeviceFeatures` 给出（Lovense 通常是 `[0, 20]`）。

### 已实现（`runtime/haptics/`）

| 文件 | 作用 |
| --- | --- |
| `protocol.py` | Buttplug v4 客户端：握手（校验版本 ≥ 4）、扫描、设备与能力解析、`OutputCmd`/`StopCmd`、按 `MaxPingTime` 心跳、断连即标记未连接。**不引入 websockets/pydantic**，只用 aiohttp |
| `scheduler.py` | 指令调度：强度/时长夹紧、`event_id` 去重、最小间隔限流、每指令自动到时停止、新指令替换旧计时器、幂等急停、统计计数 |
| `service.py` | 控制页 + API（`/api/status|connect|disconnect|pulse|stop|caps`），令牌鉴权（`X-Haptics-Token`），未配置令牌时只允许 `--mock` 启动 |
| `mock.py` | 假设备后端：没有硬件也能跑通整条链路、写回归 |
| `tools/active/haptics_probe.py` | 阶段 0 真机探针：连 Intiface → 列设备与维度 → 发一次脉冲 → 停止，并打印往返延迟 |

测试：`tests/test_haptics_{protocol,scheduler,service}.py` 共 31 项，全部通过。用「假 ws 对象」测协议层——仓库的 conftest 会导入 bot（带 Playwright/socket.io 线程），在这种环境里起真 WS 服务器再关停会互相卡住（纯 HTTP 测试不受影响），真实 socket 交给阶段 0 的探针。

本地已实测：`--mock` 起服务 → 页面正常 → 连接 → 50% 300ms 下发（设备值 10）→ 重复 `event_id` 被拒 → 停止到达设备；对假 Intiface 实跑探针，握手 2.3ms、下发与停止往返各 0.5ms（本机环回，真机要加上蓝牙与网络）。

### 怎么跑

```bash
# 本机无硬件自测（免令牌）
python -m runtime.haptics.service --mock --port 8096    # 打开 http://127.0.0.1:8096/

# 真机：先验证链路
python tools/active/haptics_probe.py ws://<手机地址>:12345 --level 0.25 --hold-ms 800

# 真机：起服务（令牌必填）
DZMM_HAPTICS_TOKEN=<自定令牌> python -m runtime.haptics.service --port 8096
# 页面上填令牌 + 设备地址，点连接 → 测试 → 停止
```

### 还没做的（等你确认再动）

1. **手机端安装**：Intiface Central（Play 或官网 APK）+ Tailscale。这一步没完成，链路就只能停在 mock。
2. **部署到 ECS**：加 `dzmm-haptics` 容器（`network_mode: host`，入口 `python -m runtime.haptics.service`，只绑 `127.0.0.1:8096`），控制页建议走 SSH 隧道而不是公网 —— 面板能开设备，比运维后台更该收紧。**在你决定暴露方式前我没有动服务器**。
3. **持久化上限**：`max_level` / `max_duration_ms` / `min_interval_ms` 目前是进程内参数，重启回默认；确定默认值后再写进配置。
4. **多设备/多玩家**：现在按「第一个设备」下发；团本两人场景要加设备绑定表（留给阶段 3）。

### 阶段 0 通过标准（必须实测）

- 探针能列出设备与 `Vibrate` 区间
- 一次 0.25 强度的 800ms 脉冲，设备有反应且**准点停下**
- 拔掉手机 Wi-Fi / 关掉 Intiface，服务在数秒内标记未连接，且不会留下持续输出

## 七、验收标准（第一版）

1. 官方 Lovense Remote 不可用时，设备仍能通过手机蓝牙连接
2. 服务器可远程发送测试、暂停、停止
3. 同一事件只执行一次；刷新、重连、重复消息不重复触发
4. 断网/服务异常后 2 秒内手机端自动停止
5. 音乐暂停、拖动、切歌后不继续执行旧任务
6. 任何时候都能在手机端停止，不依赖服务器
7. 团本中两名玩家只收到各自角色的事件提示
8. 强度上限、最大连续时长、冷却在上限侧生效

## 八、风险与前置验证

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| Intiface Central 装不上（区域/Play） | 整条链路不成立 | 阶段 0 最先验证；备用 `Chloe-Vibes`（直连 BLE）或 `kerstz/lovense-remote` |

| 延迟：LLM 决策 1~3 秒 | 剧情反应偏慢 | 事件由规则程序产出（毫秒级），模型只做风格与强度；音乐全本地 |
| `signal_bridge_remote` 无许可证 | 抄代码侵权 | 只用它的思路；要复用时改基于 MIT 的 `signal_bridge` / `signal_bridge_android` |
| `kerstz/lovense-remote` GPL-3.0 | 分发改版需开源 | 自用无碍；若要分发就换成自研或 MIT 方案 |
| 露骨情节/性反应数值映射 | 内容边界 | 不做这类设计；只做非露骨事件、音乐与自适应节奏 |

## 九、我能立刻开工的部分

不用等硬件也能写的（对着 mock 设备联调）：

1. `runtime/haptics/` 指令总线与调度器：`event_id` 去重、`expires_at`、最大时长、取消、急停、限幅、心跳
2. 独立 aiohttp 服务（8096）+ Caddy 路由 + 控制页（测试/暂停/停止/上限设置）
3. `buttplug-py` 客户端封装 + 一个假设备（内存实现），跑通端到端
4. 阶段 0 的验证脚本：扫设备 → 1 秒低强度 → 停止，带延迟测量

等手机就绪后，同一套代码换成真地址即可。
