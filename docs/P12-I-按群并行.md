# P12-I：回复延迟归因与"按群并行"

日期：2026-09-26 晚 · 触发：屋主反馈"rose 群和妹子认证群回复延迟都很高"

## 一、先说结论

**不是模型慢，是一台机器人只有一个处理线程。**

主循环是 `while True → for cid in GROUPS → await 每个生成/平台调用`，
任何一个群的**长任务**（发骚场景 `timeout=60`、写诗、回顾要读 600 条消息、
星象、入群筛查里的页面 reload）都会把**另一个群**一起按住 —— 所以"两个群都慢"。

## 二、量出来的数字

### 1）用平台时间戳算"群友发言 → 机器人回复"（12 小时，n=42）

| 群 | 类型 | n | 中位 | p90 | 最大 |
|---|---|---|---|---|---|
| 认证群 | 普通回复 | 24 | **4s** | 15s | 17s |
| 认证群 | 骰子 | 4 | 4s | 14s | 14s |
| 认证群 | 写诗 | 2 | **76s** | 76s | 76s |
| 认证群 | 回顾 | 2 | **59s** | 59s | 59s |
| 玫瑰房 | 普通回复 | 7 | **5s** | 23s | 23s |
| 玫瑰房 | 星象 | 3 | **72s** | 76s | 76s |

全部：中位 4s、p90 59s、最大 76s，**>10 秒的占 33%**。

### 2）模型本身不慢（同一条提示词直测）

```
玫瑰房 generate_reply  1.66s / 1.27s / 1.51s（154～265 字）
认证群 generate_reply  0.78s / 0.58s / 0.82s（41 字）
```

### 3）铁证：慢的那 70 秒里，机器人在忙**另一个群**

把最慢几组对齐到 `bot.log`：

```

   11:39:50   ♻️ reload 完成（已预热）
   11:39:55 🚫 已移出 小明
   11:39:46 🌹 [4a56be71] 房间消息: 运势      ← 玫瑰房这条一直等到
   11:40:58 🔮 [4a56be71] 星座: 运势          ← 72 秒后才被处理

[72s] 玫瑰房「白羊座运势」21:16:44 → 21:17:56
   21:16:48 ⚡ [bd7fe6a4] /结束
```

即：**同一个 76 秒同时出现在两个群上**，因为它们在排队等同一台机器人。

## 三、为什么不能简单地"起两个 main_loop"

- 每个实例都会 `Sender()` → **自己再开一个 Playwright 页面**。主机 1.8G，
  注释里写死了"跑不了两个 Playwright 机器人"。
- 每个实例各有 `state = load_state()` 副本 → 全量 `save_state(state)` 会**互相覆盖**
  （发情值/记忆/状态机有静默丢失风险，仓库里记着一次这种事故）。

所以做法是：**共享一份 sender / state / 订阅器**，把 `main_loop` 参数化成"只管一个群"，
再按群起 N 个实例。

## 四、改了什么

| 位置 | 改动 |
|---|---|
| `runtime/ctx.py` | "当前群"真源 `_active_cid` 改成 **`contextvars.ContextVar`**（普通全局在并行时必然串台） |
| `bot.py` | 新增 `_active_cid()`（上下文局部读口），16 个读点改走它；模块全局 `_ACTIVE_CID` 退化成**遗留镜像**（测试钉住：不许再有直接读全局的地方） |
| `bot.py::main_loop` | 参数化：`groups` 只放一个群 + 共享 `sender`/`state`/`subscriber` + `is_primary`；跨群/进程级块（热加载、验证码恢复、每日档案扫描、定时问候、骰子超时）**只在主实例跑** |
| `bot.py::_run_all` | 新建：建**唯一一份**共享资源，按 `DZMM_PARALLEL_GROUPS` 决定起 1 个还是 N 个实例；任一实例退出就收摊（不留"半个机器人"） |
| `docker-compose.prod.yml` | 透传 `DZMM_PARALLEL_GROUPS`（默认 `off`） |

**为什么用环境变量而不是 tuning**：它决定**进程结构**（起几个实例），运行期改不了；
放 env 里更诚实 —— 改了就是要重启。

## 五、部署与验证

1. 代码先上传、以**默认关**重启 → 日志确认 `P12-I: 按群并行=关（串行处理全部群）`、
   `start ... groups=2`、无报错（行为与改动前逐字相同）。
2. 再把 `/opt/dzmm/.env` 的 `DZMM_PARALLEL_GROUPS` 改成 `on` 并 recreate：
   ```
   22:51:37 P12-I: 按群并行=开，每群一个主循环实例（共 2 个）
   22:51:37 start  dry=False interval=0.8 groups=1
   22:51:37 start  dry=False interval=0.8 groups=1（从实例）
   ```
   内存 287MiB → **321MiB**（只多了一个循环，**没有第二个 Chromium**），CPU 5%。
3. 新增 `tests/test_parallel_groups.py`（8 条）：上下文局部、参数化签名、共享资源只建一份、
   全局块被 `is_primary` 包住、开关默认关、串行路径仍是单实例。

## 六、回滚（一条命令）

```sh
sed -i 's/^DZMM_PARALLEL_GROUPS=.*/DZMM_PARALLEL_GROUPS=off/' /opt/dzmm/.env
cd /opt/dzmm && docker compose up -d --force-recreate dzmm-bot
```

## 七、还欠一个真实对照

预期效果：**认证群在写诗/发骚时，玫瑰房照常 2-5 秒回**（反向同理）。

对照做法（20 秒）：先在认证群发一条慢命令（如 `/写诗 糯糯`），
**2 秒后**在玫瑰房发一句「薇丝在吗」。
- 改动前：这两条会串成一串，玫瑰房那条要等 60-70 秒（上面铁证就是这种）；
- 改动后：玫瑰房应该在 2-5 秒内回。

用 `tools/` 那套平台时间戳脚本可以直接量出来（见本文第二节第 1 条的口径）。
