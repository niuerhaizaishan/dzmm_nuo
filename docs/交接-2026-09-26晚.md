## 09-27 上午（最终）：Webhook 全线打通 + 揪出"感觉慢/不回复"的四个真因

两个群的 Webhook URL 都填了、两个 Secret 都进了 `.env`：

- 平台实测推送来自 `15.235.169.2`，Secret 校验通过、我们 200（5.9ms）

- 公网入口 `https://www.nuonuo.pw/bot/webhook`（其余 404），容器只绑 127.0.0.1:8091

### 四个真因（都修了，都有测试钉住）

1. **线程池饿死**（机器人静默 11 分钟、消息排队 5 分钟）：`wait_for(to_thread(…), 8s)`
   只放弃等待，线程还在跑（requests 自身 15s）；2 核机器默认池只有 5 个 worker，
   被卡住的读占满 ⇒ 之后连 LLM 生成都排队。修：超时交给 requests + 池子 16。
2. **冷却被"群消息文本"误触发**（回复要 70 秒）：`dzmm.api()` 对**每个**响应都扫
   `("captcha","验证码","人机验证","风控")`，而 `getMessages` 的 body 是**一整页群消息**
   ⇒ 群里有人（或机器人自己那条"平台风控中"公告）说到这些词就拉满 300 秒冷却。
   修：只在**出错**响应上扫。
3. **冷却期 sleep 10 秒**：`DEFAULT_WAIT_TIMEOUT=10`，一条回复要调几次平台 ⇒ 70 秒以上。
   修：新增 `COOLDOWN_WAIT_TIMEOUT=2`。
4. **补拉读风暴**：socket 抖动每次触发 HTTP 补拉（每 30s、每次 8~10s）。修：同群最少
   隔 60s + 冷却期不打接口 + 日志不再误称"平台超时"。

另补一个防"回两次"的洞：webhook 与 Socket.IO 会把同一条消息各送一遍（message_id 相同，
而主循环只按 last_id 去重）⇒ 队列入口跨来源去重。

**实测**：修复前 `投递 689s / 本机处理 92.7s`；修复后 **投递 ≈0s、处理 1~2s**
（10:37:25「今天完全水逆啊」→ 2 秒回复）。

## 09-27 上午（纠正 + 补齐）：被拒的消息不再永久丢

屋主一句"为什么 Bot 被拒那条直接丢？应该不会啊"问出了两件事：

**① 我错了两次，纠正：**
- **官方 Bot API 不是验证码的目标**。有史以来唯一的 `bot_rejected` 是
  `Bot is not a member of this chatroom`（P12-H 时薇丝-bot 还没进群）；
  验证码那条是**账号侧**的 `tRPC chatroom.getMessages: captcha_required`。
  我把两条记录混成一条，还"自证"了一次 —— 错的。
  官方 Bot API 是 token 的服务器间调用，不吃浏览器会话那套风控。

**② 但真问题更严重：任何发送失败都是永久失败。**
`OutboxSender.send()` 是同步内联的：失败就 `mark_failed`，而
- 没有轮询 pending 的后台 worker（模块注释原话）
- `lease()` 只认 `pending` / 租约过期的 `leased` ⇒ **`failed` 连租约都领不到**

也就是"确定没送到"的消息真的就没了。修法按代码里那条铁律
（平台未明确 ACK 时绝不换通道重发）分三类处理：

| 失败原因 | 判定 | 处理 |
|---|---|---|
| `rejected` | 平台明确拒绝，**确定未投递** | ✅ 在**官方通道上**重试（20s 一轮，最多 4 次） |
| `ambiguous` | 网络错误/非 200/缺 message_id，**可能已投递** | ❌ 绝不重发（留在 failed 里做审计） |
| `account_unknown` | 账号通道失败、不知情 | ❌ 不重发 |

新增：`RoutingSender.last_failure`、`OutboxStore.revive()`、
`OutboxSender.retry_worker()/retry_once()`、启动日志
`P12-J: 出站重试任务已启动（只重试明确被拒的…）`；
测试 `tests/test_outbox_retry.py` 6 条。

**所以 `DZMM_OFFICIAL_ONLY=on` 现在的含义变了**：不是"被拒就丢"，而是
"**不在账号通道上偷偷发，改成在官方通道上重试**"。
