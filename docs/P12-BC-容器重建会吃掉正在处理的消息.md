# P12-BC：**容器重建会吃掉"正在处理的那条消息"**（ROSE 房"又没反应了"）

> 屋主 2026-09-30 10:33："**怎么 ROSE 房又没反应了**"

## 1. 现场（读出来的事实）

```
玫瑰房最后一条   02:07:43(UTC) 亦书: 摩羯座      ← 没人回答
薇丝最后一条     01:05:48(UTC) 🌹 今日星象 · ♏ 天蝎座
玫瑰房 last_id   d4360903 = 上面那条"摩羯座"
```

`last_id` **正好等于那条没被回答的消息** —— 这就是"看起来处理过了、其实一个字都没发"的形状。
而 `02:07:07(UTC)` 我正在跑部署（`docker compose up -d` 重建容器），
消息就落在这个窗口里。

## 2. 根因：`last_id` 在**生成之前**推进，而容器重建是 SIGKILL

三处派发（cmd / @ / 房间消息）都是同一个写法：

```python
old_last_id = group_state.get("last_id", "")   # 记录旧值，生成失败时回滚
group_state["last_id"] = msgs[-1]["message_id"]  # ← 先推进，避免重复处理
```

异常时由 `except` 调 `_rollback_last_id()` 回滚 —— **但容器重建 = SIGKILL**，
`except` 根本来不及跑。于是：

1. `last_id` 停在最新那条上（已落盘）；
2. 那条消息的回复从未生成/发送；
3. 重启后主循环按"只处理 `last_id` 之后的消息"行事 ⇒ **它永远不会被再读**。

**这条不是玫瑰房特有**：任何群、任何一次 `docker compose up -d` 都可能吃掉一条。
今天为了修 P12-AZ/BA/BB 我部署了 5 次（10:01 / 10:07 / 10:15 / 10:25 / 10:38），
屋主感受到的"**又**没反应了"，就是这个窗口被撞上的必然结果。

## 3. 修法：`inflight` 落盘标记 + 启动恢复

| 步 | 做什么 |
|---|---|
| ① 处理前 | 推进 `last_id` 的同一处，落一个 `inflight = {mid, at}` 到本群 state（**标记指这一轮真正在处理的那条**：`_cmd_msg` / `_at_msg_obj` / `_room_obj`，不是批次尾巴） |
| ② 每轮跑完 | `last_id` 推到最新那一刻 `_clear_inflight()` |
| ③ 启动时 | `_recover_inflight()`：标记还在（且 < 1 小时）就**回群里读**，按群里的既成事实决定 |

判据（`INFLIGHT_PROBE_MSGS = 50`）：

| 读到的事实 | 处理 |
|---|---|
| 那条**之后**有我们发的话 | 已经回过了 ⇒ 只清标记（**绝不重放**，防重复） |
| 那条之后没有我们的话 | `last_id` 退回它前面一条 ⇒ 交回主循环重放（`🔁` 日志） |
| 它已滚出最近 50 条窗口 | 补不回来 ⇒ **留一行警告**（不许静默） |
| 标记 > 1 小时 | 只清不重放（重启不翻旧账） |

判据仍是这个项目的老规矩（P12-AN）：**"发出去了"只能由群里读回证明**。

## 4. 验收

- 单测：`tests/test_inflight_recovery.py`（10 条：三处派发都落标记且紧跟 `last_id` 推进、
  标记指被处理那条、轮末清标记、启动调用点在 `load_state()` 之后、
  没回过→重放、回过了→不重放、滚出窗口→留警告、标记太旧→不重放、无标记→no-op、
  读群失败不炸、`_mark_inflight` 落 mid+时间且空 mid 不写）；全量 **1368 收集 / 0 失败 / 4 跳过**；
- 部署 `10:38:07`（基础版）+ `10:42:18`（精确到被处理那条），`bot.py` md5 `a4195c76…` 本地 = 容器；
- 生产验证：容器里走一遍 `_mark_inflight() → load_state()` 能看到标记、`_clear_inflight()` 后消失，
  四个**真群都没有残留 inflight**（`{4a56be71: False, 4fc4a2fd: False, bd7fe6a4: False, f4ec4c21: False}`）；
  启动日志没有 `🔁` 行（本次没有待补的）。

## 5. 补不回来的那条

`摩羯座` 那条是在**标记机制上线之前**被吃掉的，所以自动恢复救不到它 ——
要补只能手动补发（或让群里再发一次星座）。

## 6. 复盘

- **"又没反应了"的"又"字是线索**：屋主已经见过好几次了。它不是新 bug，
  而是**我的部署动作**在反复制造同一种事故 —— 每次上线都可能在窗口里吃掉一条。
- **"先推进游标再干活"这类优化必须配崩溃兜底**：它挡的是"重复处理"，
  却把风险翻成了"静默漏处理"，而漏处理在群里表现为"机器人坏了"。
- 三个派发点各写一遍 `last_id` 推进，是这次必须改三处的原因；
  真要收拾干净得把这些"推进"收敛成一个函数（记 backlog）。
