## 一、现在是什么样（事实）

### 1.1 配置层只有"群和 Bot"两种东西

`config/config.json`（schema **v1**）现在只有：

```json
{
  "version": 1,
  "groups": [{"cid": "...", "alias": "...", "enabled": true,
              "mute": false, "screen": false, "push": false, "persona": ""}],
  "bots":   [{"key": "nuo_main", "name": "...", "cid": "...",
              "token_env": "DZMM_BOT_TOKEN", "persona": "nuo", "enabled": true}]
}
```

也就是说，**今天能配的只有 5 个布尔 + 人设选哪个名字**：

| 能配 | 含义 |
|---|---|
| `enabled` | 完全不管这个群 |
| `mute` | 只读不回 |
| `screen` | 入群筛查 |
| `push` | 定时推送（问候/排行/记忆汇报） |
| `persona` | 选一个人设**名字**（`nuo` / `rose_butler`） |

**功能开关（发骚、调教、骰子……）一个都配不了** —— 它们全部是"代码里写了就一直生效"。
人设也只能选名字，**文本本身在代码里**（`personas.py` 的 `PERSONAS` 字典 +
`brains.py` 里的提示词），页面上改不了。

### 1.2 人设今天的真实结构（已逐项核实）

```python
# personas.py
PERSONAS = {
    "nuo":         {"name_full": "小小糯～", "name_short": "小小糯", "extra": ""},
    "rose_butler": {"name_full": "小小糯～", "name_short": "小小糯",
                    "extra": ROSE_BUTLER_EXTRA},     # 1392 字符 / 50 行
}
ROOMS = {ROSE_CID: {"alias": "Rose（505）玫瑰房", "persona": "rose_butler",
                    "owners": {屋主, 操作者}, "greet_on_join": True,
                    "strike_limit": 3, "strike_reset_h": 12}}
PHRASES = { "nuo": {…21 个 key…}, "rose_butler": {…21 个 key…} }   # :263-317
```

关键事实（都影响"人设可配"怎么做）：

1. **人设注入只有唯一收口**：`brains.py:587` 的 `_call_llm()` 里做
   `system_prompt = apply_persona(system_prompt)`（`brains.py:594-598`），
   而它被 **40 个调用点**共用。⇒ 改人设的作用面是"所有 LLM 输出"，
   而且实现上只要动**一个**收口点。同一处还写死了 `temperature=0.7`
   与 `thinking=disabled` ⇒ 这两个参数也顺手可配。
2. **`apply_persona` 做的是纯文本替换 + 追加**（`personas.py:246-256`）：
   把 `小小糯～`/`小小糯` 替换成人设的 `name_full`/`name_short`，
   再把 `extra` 用 `"\n\n"` 追加到 system prompt 后面。
   **默认人设直接把 prompt 原样返回（零开销短路）**；`extra` 里
   **不含任何占位符**（是纯静态文本）。
3. **人设 = 三块**：`name_full` / `name_short` / `extra`（身份口吻）
   **+ `PHRASES` 21 个 key 的固定话术**（帮助、介绍、点名提示、记忆列表…）
   **+ `prompts/` 里 39 个提示词文件**。后两块才是"各功能怎么说"。
   `PHRASES` 里 `help_text`/`intro_text` 为 `None` 时回落到 `bot.py` 的常量。
4. **人设白名单硬编码在代码里**：`bot.py:75` 的 `("nuo", "rose_butler")`。
   ⇒ **今天"新增一个人设"必须改代码**；配置里的 `persona` 字段还不生效（§9.0-1）。
5. **"选谁"能配、"说什么"不能配，而且有三处真源**：
   `personas.py`（人设+话术）/ `brains.py`（39 个 prompt 常量）/
   `prompts/*.md`（39 个外置文件，`_p()` 包裹，缺文件退回代码默认）。
   还有**第 40 个提示词没外置**：`runtime/memory.py:34` 的 `MEMORY_FILTER_PROMPT`。
6. **可变槽位一共 6 个**（`personas.py` 内）：`{name}` `{item}` `{line}`
   `{who}` `{n}` `{k}`。提示词里那些 `<女主昵称>` 之类是给人看的描述，**不是** format 槽。
7. **房间玩法（`ROOMS`）是硬编码的**：屋主 uid、进群问候、警告上限、清零小时数
   全在代码里（页面上改不了）。

### 1.3 生效方式今天是"重启才生效"

`config_store` 有 `_cache` 和 `reload(force=True)`，主循环每轮也会重新读一些状态，
但**配置本身只在进程启动时读一次**。所以页面上的改动都要重启容器 ——
对"改个开关试试"这种操作来说太重。

### 1.4 已有的、必须复用的基础设施（不要重复造）

| 能力 | 在哪 | 说明 |
|---|---|---|
| 校验后写（不合法一个字都不写） | `config_store.save()` | 现成的 |
| 原子替换（`tmp` + `os.replace`） | 同上 | 单文件挂载会 EBUSY，现在是目录挂载 |
| 自动备份 + 保留 20 份 | 同上 | 回滚的基础 |
| 审计日志（谁/何时/改了什么） | `config/config_audit.log` | 页面上直接看 |
| 一键回滚 | `admin/config_ui.py` | 现成的 |
| 改动逐条列出 | 同上 | 防"整表提交把别的字段带歪" |
| 旧页面闸门（不许静默删配置） | `dashboard._post_edit` | 现成的 |
| 启动前配置校验 | `tools/deploy_gate.py` | 配置不合法 → bot 拒绝启动 |
| 试跑（不发送） | `bot.py --dry` | 可以拿来做"人设预览" |

**还有一个坑要先说清**：`runtime/settings.py` 是 P1 期照抄 DDZM 留下的**骨架**

**生产路径（`bot.py` 与 `runtime/` 各模块）一处都没用它**，是个死骨架子。
做这一期时必须明确：**要么并入新配置，要么标记废弃** ——
绝不允许出现第三份"看起来能配、实际不生效"的配置源。

## 二、设计目标（与"不做什么"）

### 要做

1. **每个功能都能按群开关**（`认证群开、玫瑰群关`这种），且**关掉就是真不生效**
   （不是"不回复"而是"根本不进入那段逻辑"，避免半开半关的怪状态）。
2. **关键参数可调**：冷却、概率、阈值、上限、时长之类运营真的会想动的东西。
3. **人设可编辑、可预览、可回滚**：身份/口吻/称呼 + 各功能的文案模板。
4. **改完尽量不用重启**。
5. 页面必须**看得懂**：每个开关都要有一句"关掉之后群友会怎样"。

### 不做（这一期明确排除）

- 不改任何功能的**内部语义与文案算法**（只加开关和参数，不动"怎么算的"）。
- 不做多用户/分级权限（现在只有一个运维账号）。
- 不做 A/B、不做按单个群友维度配置。
- 不引入第二个配置文件（**一份 `config.json` 是唯一真源**）。
- 不把 prompt 全文搬进 JSON（39 个提示词文件继续留在 `prompts/`，
  页面只配"人设层"和"开关/参数"，提示词工程仍走文件 + 重启）。

## 三、配置模型：三层覆盖 + 一份真源

### 3.1 结构（schema v2）

```json
{
  "version": 2,

  "groups": [{
    "cid": "bd7fe6a4-…",
    "alias": "认证妹子群",
    "enabled": true, "mute": false, "screen": true, "push": true,
    "persona": "nuo",
    "features": { "diaojiao": false },        // 只写"与全局默认不同"的
    "tuning":   { "heat.decay_per_hour": 3 }  // 只写"与全局默认不同"的
  }],

  "bots": [ ... 不变 ... ],

  "features": {                                // 运营视角的功能注册表
    "fasao":    { "on": true,  "label": "发骚",     "params": {} },
    "diaojiao":  { "on": false, "label": "调教",
                   "params": { "strike_limit": 3, "strike_reset_h": 12 } }
  },

  "personas": {                                // 人设（可编辑文本）
    "nuo": { "label": "小小糯（默认）", "name_full": "小小糯～",
             "name_short": "小小糯", "extra": "", "overridden": false }
  },

  "tuning": { "heat.decay_per_hour": 5 }        // 全局默认覆盖
}
```

### 3.2 四条硬性设计原则

1. **代码是默认值，配置只写"覆盖"。**
   每个功能的默认开关、每个参数的默认值，都由代码里的**声明式注册表**给出
   （`runtime/features.py` / `runtime/tuning.py`）。配置文件里没写 = 用代码默认。
   ⇒ 删掉配置文件 = 回到今天的行为，跟现有 `config_store` 的"文件不存在就退回
   defaults"完全一致；也让"新功能默认怎么表现"只在一个地方定义。

2. **功能必须在注册表里登记，且有唯一执行点。**
   注册表条目 = `key / 中文名 / 一句话说明 / 分类 / 默认值 / 参数定义（类型、单位、
   范围、默认）/ 关掉后的表现 / 依赖`。主循环与各处理函数通过**唯一一个判定**
   `features.on(cid, "fasao")` 决定是否进入；不允许各功能自己写一套判断
   （否则"关掉了但某个入口忘了判"就是必然事故）。

3. **参数走同一个读口。**
   所有可调数值改成 `tuning.get("heat.decay_per_hour", cid)`，不再有裸常量。
   ⇒ 页面、测试、`--dry` 试跑读的是同一份值。

4. **人设是"名字 + 文本"两件事，都要能配。**
   `groups[].persona` 选名字；`personas.<key>` 存放该人设的文本。
   代码里的默认文本保留为 fallback，页面显示"当前：代码默认 / 已覆盖"。

### 3.3 参数分级（哪些该给运营、哪些不该）

| 档 | 例子 | 页面表现 |
|---|---|---|
| **必配** | 发骚值衰减速度、各功能冷却、定时推送时刻、投票时长、骰子超时、入群验证码等待 | 直接露在功能卡片上 |
| **可配** | 概率、上限、文案条数、模型名/温度 | 折在"高级"里 |
| **不该配** | 内部重试次数、SQL 批次、锁超时、超时补偿窗口 | **不出现**在页面上（配错只会惹祸） |

### 3.4 生效方式

| 改动类型 | 生效方式 | 为什么 |
|---|---|---|
| 功能开关、参数、人设文本 | **热加载**（本轮起生效） | 读侧用不可变快照；`config_store` 已有 `reload(force=True)` |
| 群清单、Bot、token、路由 | **需要重启** | 它们决定进程怎么装配（socket 订阅哪些群、走哪条通道） |

两条配套规则（必须写在页面上）：

- **开关只影响"新的触发"**：已经开起来的会话（骰子局、发骚、投票）按原样走完，
  否则会出现"游戏开一半凭空消失"。超时回收逻辑照常运行，**不许留下永不结束的状态**。
- **一键回退**：`DZMM_FEATURES=off` ⇒ 忽略所有功能开关（全开）；
  `DZMM_TUNING=off` ⇒ 全用代码默认值。页面上配错了能秒退，不用回滚备份。

### 4.2 人设页

左侧人设列表（默认 / 房间…），右侧编辑器：

| 字段 | 说明 |
|---|---|
| 显示名 / 简称 | 群里自称、`@` 里的名字 |
| 身份与口吻（主体文本） | 就是今天的 `extra`，可编辑，带字数与占位符提示 |
| 称呼 | 对群友怎么叫（姐姐/客人/宝贝…），单独成项，因为它最容易改坏气氛 |
| 短语库（可选） | 问候语、警告语、点单菜单等**列表**，可增删每一行 |
| 变量槽位 | 显示这个文本里可用的 `{name}` `{who}` 等（清单由代码提供） |

配套：**预览**（用 `--dry` 真实生成一次、不发送）、**体检**（长度异常、
占位符写错、禁用词）、**一键回滚**。

### 4.3 必须解决的一个技术前提：CSP 与 JavaScript

现在页面的 CSP 是：

```
default-src 'none'; style-src 'unsafe-inline'; form-action 'self'
```

⇒ **完全禁止 JavaScript**（连外链脚本都禁）。矩阵页没有 JS 会很难用
（勾一下整页提交、参数展开要跳页）。

建议：放宽为 `default-src 'none'; style-src 'unsafe-inline';
script-src 'self'; form-action 'self'`，JS 放在**服务器上的独立文件**里
（不用内联、不用 CDN、不用 `eval`）。这是纯加法，仍然挡得住内联注入类 XSS，
但它是一次安全边界调整，要单独记录、单独评审。

**备选（完全不碰 CSP）**：矩阵保持纯 HTML 表单，一个"保存全部"按钮整页提交。
能用，但体验明显更差；我会先按这个做出来，再问你要不要上 JS。

## 五、分期（每期独立上线、独立回滚、独立验收）

> 原则沿用 P8：**先做"零行为变化"的重构，再做能被看见的功能**。
> 每一期都能单独停在上线状态，不需要等下一期。

| 期 | 内容 | 行为变化 | 验收方式 |
|---|---|---|---|
| **P12-A** | 功能注册表 `runtime/features.py`；把各功能入口登记进去，判定收敛到唯一一处；**新增状态复位接口 `reset_feature(cid, key)`** | **无**（复位只是新增能力，不改默认路径） | 同批输入下，各功能触发次数/输出与改动前**逐条一致**（P8 的计数断言手法）+ "登记项都有真实调用点"的扫描测试 |
| **P12-B** | 参数外置 `runtime/tuning.py`；**并把三处硬编码的按群集合（`TREND_CIDS`/`RECAP_CIDS`/`ROOM_CIDS`）改成配置** | **无**（默认值=当前常量/当前集合） | 前后数值与集合一致 + 边界值测试（0/负数/超大） |
| **P12-C** | `config_store` schema **v2** + v1→v2 自动迁移 + 新三块校验；**把不生效的 `persona` 字段接通（或删掉）** | 无（读到 v1 自动升级并备份） | 迁移测试 + 启动闸门 + 生产自证行不变 + "配置里每个字段都有消费点"的扫描测试 |
| **P12-D** | 页面：功能矩阵 + 参数表单 + **"关闭即复位"策略 + 每功能"强制复位"按钮**（含 CSP 决策） | 无（只是多了写入口） | 端到端脚本：只改一个开关 → 只那一项变 → 关掉一个"进行中"的玩法 → 该群**不被屏蔽** → 回滚 |
| **P12-E** | 页面：人设编辑器 + 预览 + 体检 | 人设文本一变，群里说话就变 | 先 dry 预览 → 灰度（先在玫瑰群改）→ 生产验收 |
| **P12-F** | 热加载：开关/参数/人设即时生效 + 页面"已生效/待重启"双状态 | 生效速度变化 | 改一个开关不重启即生效；结构性改动仍如实标"待重启" |

**新增的一项前置**：`perf`（公演）**今天没有超时**，中途被打断会让该群永久哑掉。
P12-A 顺手补上超时（属于"让开关能安全关闭"的必要条件）。

每期都带：**测试**（现有 512 项不许变红）+ **生产验收脚本** + **回滚开关**。

### 工作量锚点（我自己数出来的，可复现）

改造面的**硬指标**：命令判定函数共 **37 个** —— `bot.py` 里 14 个
（`is_continue_cmd` / `is_devil_cmd` / `is_dj_command_cmd` / `is_guide_cmd` /
`is_help_cmd` / `is_insult_cmd` / `is_intro_cmd` / `is_profile_cmd` / `is_rank_cmd` /
`is_register_cmd` / `is_review_cmd` / `is_rewrite_cmd` / `is_summary_cmd` / `is_sync_cmd`），
`runtime/` 下 23 个（分布在 `diaojiao/dice/fasao/fortune/identity/memory/perf/poem/
recap/story/trend/vote` 共 12 个模块里）。

这些函数**不等于**功能数（例如 `fasao` 一个功能有 3 个判定），按语义归并后
预计 **20~25 个功能**。这 37 个判定 + 各处的定时/事件入口，就是 P12-A 要逐一登记、
并把判定收敛到 `features.on()` 的清单 —— 也是为什么 A 期必须先做、且必须
"零行为变化"：改错一个判定的顺序，就是一类功能整体失灵。

## 六、风险登记册（这一期新增的）

| 风险 | 级别 | 缓解 |
|---|---|---|
| **关掉功能 → 状态残留 → 该群（或所有群）被永久屏蔽** ⚠️ 盘点后升级为最高风险 | **高** | 五个状态机都没有 reset 接口、`perf` 没有超时、骰子局是顶层键（会影响所有群）⇒ 关闭开关**必须顺手复位** + 页面给"强制复位"按钮 + 给 `perf` 补超时 |

## 七、改造时必须绕开的既有陷阱（都是这个仓库里真实存在的）

这几条不是"注意事项"，是**这个 codebase 已经埋着的雷**；P12 每一步都要对着它们检查。

1. **分派顺序就是行为。** 主循环里几十个判定依次判断，任一判定的哨兵值写错，
   就会有一类功能整体失灵或被"兜底"判定吃掉。
   现成的坑：`is_profile_cmd` 用 `""` 表示**"这不是命令"**，
   而 `is_register_cmd` / `is_rewrite_cmd` 用 `""` 表示**"是命令，但没有参数"** ——
   同一个返回值，两种相反语义；`is_dj_command_cmd` 是**依赖其他所有判定结果的兜底**。
   ⇒ P12-A 登记功能时，**判定函数一个都不许改写**，只在它们**之后**加开关闸门；
   并补一个"顺序断言"测试（把登记顺序与实际调用顺序逐条比）。

2. **人设是 contextvar，会残留。** `bot.py` 主循环每轮开头必须
   `set_persona_cid("")`（代码里有注释：**2026-09-17 事故** —— 研讨群的早安被写成
   玫瑰房管家口吻，因为上一轮最后一个群是 Rose 房间群）。
   ⇒ 人设一旦可配置，**每个群的判定/发送前都要显式设置人设、用完清掉**；
   这条要有测试：配置了 N 个不同人设的群，广播类文案（问候/记忆汇报）
   必须仍然用默认人设。

3. **`_ACTIVE_CID` 只有一个写点**（`tools/deploy_gate.py` 里有断言钉着）。
   ⇒ 功能闸门若需要知道"现在是哪个群"，一律走 `runtime/ctx.py`，
   **不许**再引入第二个写点。

4. **长文本有平台硬限制。** `runtime/outbound.py` 里写着 `BOT_GROUP_MAX_CHARS = 1000`
   与 `BOT_GROUP_MAX_NEWLINES`（≤10 行），注释原文：
   「普通账号受 1000 字符 / 10 换行限制，超限必须走官方 Bot」。
   人设和文案一旦能在页面上编辑，就可能被人写成超长文本。
   ⇒ 人设页的"体检"必须**按发送通道**检查长度与换行数，超限直接拦下
   （认证群走 Bot 通道没这个限制，但玫瑰群走账号，有）。

5. **两套"文本"不能混成一个源。** 现在 `prompts/`（39 个提示词文件，
   `_p()` 包裹、缺文件就退回代码默认）负责人设之外的提示词工程；
   页面上的人设只能管**人设层**。⇒ 明确边界，并在页面上标注
   "这条文案来自 prompts/ 文件，改它要动服务器"，别让人以为页面上能改全部。

6. **限流与令牌桶永远在。** 无论功能开关怎么配，`throttle_guard` +
   出站队列的按群串行都不许被绕过 —— 参数可调的只是"功能自己的冷却"，
   平台级的限流是另一层，**不暴露给运营**。

7. **单字符前缀匹配的历史行为。** `_find_uid_by_name` 用单字符前缀匹配，
   已知会命中「裳姐姐」（记录在案、**刻意没改**）。
   ⇒ 涉及"对某人做什么"的功能（调教/训斥/点名）做成可配时，
   要连带把"点名解析规则"作为只读说明写在页面上，避免用户以为是随机命中。
