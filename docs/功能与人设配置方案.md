## 一、现在是什么样（事实）

### 1.1 配置层只有"群和 Bot"两种东西

`config/config.json`（schema **v1**）现在只有：

```json
{
  "version": 1,
  "groups": [{"cid": "...", "alias": "...", "enabled": true,
              "mute": false, "screen": false, "push": false, "persona": ""}],
  "bots":   [{"key": "nuo_main", "name": "...", "cid": "...",
              "token_env": "DZMM_BOT_TOKEN", "persona": "nuo", "enabled": true}]
}
```

也就是说，**今天能配的只有 5 个布尔 + 人设选哪个名字**：

| 能配 | 含义 |
|---|---|
| `enabled` | 完全不管这个群 |
| `mute` | 只读不回 |
| `screen` | 入群筛查 |
| `push` | 定时推送（问候/排行/记忆汇报） |
| `persona` | 选一个人设**名字**（`nuo` / `rose_butler`） |

**功能开关（发骚、调教、骰子……）一个都配不了** —— 它们全部是"代码里写了就一直生效"。
人设也只能选名字，**文本本身在代码里**（`personas.py` 的 `PERSONAS` 字典 +
`brains.py` 里的提示词），页面上改不了。

### 1.2 人设今天的真实结构（已逐项核实）

```python
# personas.py
PERSONAS = {
    "nuo":         {"name_full": "小小糯～", "name_short": "小小糯", "extra": ""},
    "rose_butler": {"name_full": "小小糯～", "name_short": "小小糯",
                    "extra": ROSE_BUTLER_EXTRA},     # 1392 字符 / 50 行
}
ROOMS = {ROSE_CID: {"alias": "Rose（505）玫瑰房", "persona": "rose_butler",
                    "owners": {屋主, 操作者}, "greet_on_join": True,
                    "strike_limit": 3, "strike_reset_h": 12}}
PHRASES = { "nuo": {…21 个 key…}, "rose_butler": {…21 个 key…} }   # :263-317
```

关键事实（都影响"人设可配"怎么做）：

1. **人设注入只有唯一收口**：`brains.py:587` 的 `_call_llm()` 里做
   `system_prompt = apply_persona(system_prompt)`（`brains.py:594-598`），
   而它被 **40 个调用点**共用。⇒ 改人设的作用面是"所有 LLM 输出"，
   而且实现上只要动**一个**收口点。同一处还写死了 `temperature=0.7`
   与 `thinking=disabled` ⇒ 这两个参数也顺手可配。
2. **`apply_persona` 做的是纯文本替换 + 追加**（`personas.py:246-256`）：
   把 `小小糯～`/`小小糯` 替换成人设的 `name_full`/`name_short`，
   再把 `extra` 用 `"\n\n"` 追加到 system prompt 后面。
   **默认人设直接把 prompt 原样返回（零开销短路）**；`extra` 里
   **不含任何占位符**（是纯静态文本）。
3. **人设 = 三块**：`name_full` / `name_short` / `extra`（身份口吻）
   **+ `PHRASES` 21 个 key 的固定话术**（帮助、介绍、点名提示、记忆列表…）
   **+ `prompts/` 里 39 个提示词文件**。后两块才是"各功能怎么说"。
   `PHRASES` 里 `help_text`/`intro_text` 为 `None` 时回落到 `bot.py` 的常量。
4. **人设白名单硬编码在代码里**：`bot.py:75` 的 `("nuo", "rose_butler")`。
   ⇒ **今天"新增一个人设"必须改代码**；配置里的 `persona` 字段还不生效（§9.0-1）。
5. **"选谁"能配、"说什么"不能配，而且有三处真源**：
   `personas.py`（人设+话术）/ `brains.py`（39 个 prompt 常量）/
   `prompts/*.md`（39 个外置文件，`_p()` 包裹，缺文件退回代码默认）。
   还有**第 40 个提示词没外置**：`runtime/memory.py:34` 的 `MEMORY_FILTER_PROMPT`。
6. **可变槽位一共 6 个**（`personas.py` 内）：`{name}` `{item}` `{line}`
   `{who}` `{n}` `{k}`。提示词里那些 `<女主昵称>` 之类是给人看的描述，**不是** format 槽。
7. **房间玩法（`ROOMS`）是硬编码的**：屋主 uid、进群问候、警告上限、清零小时数
   全在代码里（页面上改不了）。

### 1.3 生效方式今天是"重启才生效"

`config_store` 有 `_cache` 和 `reload(force=True)`，主循环每轮也会重新读一些状态，
但**配置本身只在进程启动时读一次**。所以页面上的改动都要重启容器 ——
对"改个开关试试"这种操作来说太重。

| 能力 | 在哪 | 说明 |

## 二、设计目标（与"不做什么"）

### 要做

1. **每个功能都能按群开关**（`认证群开、玫瑰群关`这种），且**关掉就是真不生效**
   （不是"不回复"而是"根本不进入那段逻辑"，避免半开半关的怪状态）。
2. **关键参数可调**：冷却、概率、阈值、上限、时长之类运营真的会想动的东西。
3. **人设可编辑、可预览、可回滚**：身份/口吻/称呼 + 各功能的文案模板。
4. **改完尽量不用重启**。
5. 页面必须**看得懂**：每个开关都要有一句"关掉之后群友会怎样"。

### 不做（这一期明确排除）

- 不改任何功能的**内部语义与文案算法**（只加开关和参数，不动"怎么算的"）。
- 不做多用户/分级权限（现在只有一个运维账号）。
- 不做 A/B、不做按单个群友维度配置。
- 不引入第二个配置文件（**一份 `config.json` 是唯一真源**）。
- 不把 prompt 全文搬进 JSON（39 个提示词文件继续留在 `prompts/`，
  页面只配"人设层"和"开关/参数"，提示词工程仍走文件 + 重启）。

## 三、配置模型：三层覆盖 + 一份真源

### 3.1 结构（schema v2）

```json
{
  "version": 2,

  "groups": [{
    "cid": "bd7fe6a4-…",
    "alias": "认证妹子群",
    "enabled": true, "mute": false, "screen": true, "push": true,
    "persona": "nuo",
    "features": { "diaojiao": false },        // 只写"与全局默认不同"的
    "tuning":   { "heat.decay_per_hour": 3 }  // 只写"与全局默认不同"的
  }],

  "bots": [ ... 不变 ... ],

  "features": {                                // 运营视角的功能注册表
    "fasao":    { "on": true,  "label": "发骚",     "params": {} },
    "diaojiao":  { "on": false, "label": "调教",
                   "params": { "strike_limit": 3, "strike_reset_h": 12 } }
  },

  "personas": {                                // 人设（可编辑文本）
    "nuo": { "label": "小小糯（默认）", "name_full": "小小糯～",
             "name_short": "小小糯", "extra": "", "overridden": false }
  },

  "tuning": { "heat.decay_per_hour": 5 }        // 全局默认覆盖
}
```

### 3.2 四条硬性设计原则

1. **代码是默认值，配置只写"覆盖"。**
   每个功能的默认开关、每个参数的默认值，都由代码里的**声明式注册表**给出
   （`runtime/features.py` / `runtime/tuning.py`）。配置文件里没写 = 用代码默认。
   ⇒ 删掉配置文件 = 回到今天的行为，跟现有 `config_store` 的"文件不存在就退回
   defaults"完全一致；也让"新功能默认怎么表现"只在一个地方定义。

2. **功能必须在注册表里登记，且有唯一执行点。**
   注册表条目 = `key / 中文名 / 一句话说明 / 分类 / 默认值 / 参数定义（类型、单位、
   范围、默认）/ 关掉后的表现 / 依赖`。主循环与各处理函数通过**唯一一个判定**
   `features.on(cid, "fasao")` 决定是否进入；不允许各功能自己写一套判断
   （否则"关掉了但某个入口忘了判"就是必然事故）。

3. **参数走同一个读口。**
   所有可调数值改成 `tuning.get("heat.decay_per_hour", cid)`，不再有裸常量。
   ⇒ 页面、测试、`--dry` 试跑读的是同一份值。

4. **人设是"名字 + 文本"两件事，都要能配。**
   `groups[].persona` 选名字；`personas.<key>` 存放该人设的文本。
   代码里的默认文本保留为 fallback，页面显示"当前：代码默认 / 已覆盖"。

### 3.3 参数分级（哪些该给运营、哪些不该）

| 档 | 例子 | 页面表现 |
|---|---|---|
| **必配** | 发骚值衰减速度、各功能冷却、定时推送时刻、投票时长、骰子超时、入群验证码等待 | 直接露在功能卡片上 |
| **可配** | 概率、上限、文案条数、模型名/温度 | 折在"高级"里 |
| **不该配** | 内部重试次数、SQL 批次、锁超时、超时补偿窗口 | **不出现**在页面上（配错只会惹祸） |

### 3.4 生效方式

| 改动类型 | 生效方式 | 为什么 |
|---|---|---|
| 功能开关、参数、人设文本 | **热加载**（本轮起生效） | 读侧用不可变快照；`config_store` 已有 `reload(force=True)` |
| 群清单、Bot、token、路由 | **需要重启** | 它们决定进程怎么装配（socket 订阅哪些群、走哪条通道） |

两条配套规则（必须写在页面上）：

- **开关只影响"新的触发"**：已经开起来的会话（骰子局、发骚、投票）按原样走完，
  否则会出现"游戏开一半凭空消失"。超时回收逻辑照常运行，**不许留下永不结束的状态**。
- **一键回退**：`DZMM_FEATURES=off` ⇒ 忽略所有功能开关（全开）；
  `DZMM_TUNING=off` ⇒ 全用代码默认值。页面上配错了能秒退，不用回滚备份。

### 4.3 前端：**上 JS**（你已定），CSP 具体怎么改

现在页面的 CSP 逐字是（`admin/dashboard.py:1037`，全仓唯一一处）：

```
default-src 'none'; style-src 'unsafe-inline'; form-action 'self'
```

⇒ 无 `script-src` ⇒ 回落 `'none'` ⇒ **内联脚本、`onclick` 属性、外链脚本全被拦**；
`admin/` 全目录也确实**零 JavaScript**（纯 HTML 表单）。

**改成（逐个指令都说清为什么）**：

```
default-src 'none'                        # 默认全禁，逐项开口子
style-src 'unsafe-inline'                 # 保留：现有内联 <style>
script-src 'self'                         # ← 新增：只允许同源 JS 文件，禁内联、禁 CDN、禁 eval
img-src 'self' data:                      # 若以后要放小图标（当前无图）
form-action 'self'                        # 表单只能提交给自己
frame-ancestors 'none'                    # ← 新增：防点击劫持（当前全仓无 X-Frame-Options）
base-uri 'none'                           # ← 新增：防 <base> 改相对路径
```

同时补 `X-Frame-Options: DENY`（老浏览器兜底）与 `Permissions-Policy`（关掉摄像头/麦克风等）。
**303 重定向响应也要带全安全头**（现在 `_redirect()` 不带 CSP/nosniff/Referrer-Policy）。

**JS 的职责（只做体验，不做业务逻辑）**：

| 场景 | 没有 JS（降级） | 有 JS |
|---|---|---|
| 功能矩阵勾选 | 每一次勾选都要整页提交 | 本地记录改动，**只提交变化的那几项**，保存前弹 diff 确认 |
| 参数编辑 | 刷新后折叠状态丢失 | 展开/折叠、显示默认值与来源层（代码/全局/本群） |
| 人设编辑器 | 无字数提示 | 实时字数 / **换行数**（账号通道 10 行上限）/ 占位符清单提示 |
| 危险值 | 无提示 | 超范围、危险值（冷却 0、概率 1.0、块数上限调大）二次确认 |
| 预览 | 提交后跳页 | 原地展示 dry-run 结果 |

**铁律（写进代码规范，评审时对照）**：

1. **绝不内联脚本/事件属性** —— CSP 会拦，且这是 XSS 的主要入口；
2. 所有用户内容进 DOM 用 `textContent`，**永不用 `innerHTML`**；
3. 不要 `eval` / `new Function` / 动态 `<script>`；
4. JS 文件与 HTML 一起走**白名单路由**（新增 `GET /static/app.js`，
   只服务固定的几个文件名，不做目录遍历）；
5. **无 JS 也必须能完成全部操作**（渐进增强）—— 这样即使 CSP 收紧回去、
   或浏览器插件拦脚本，运维仍然救得回来；
6. CSRF token 从隐藏字段读（不放进 URL、不写进日志）。

**降级与回退**：JS 只影响交互，不影响正确性；若要临时回到"零 JS"，
只需把 CSP 里 `script-src 'self'` 去掉（页面会退回纯表单模式而**不会坏**）。

**为什么没有 `personas` 节**：人设**文本**的可编辑属于 P12-E。现在加一节
"能配但不生效"的字段，正是这一路在反复修的毛病（`persona` 字段、
`runtime/settings.py` 都是这个下场）。所以 P12-E 会把"文本 + 运行期生效"
一起做，届时再升 v3。

**迁移（v1 → v2）**：

- **读路径不写文件**：`load()` 只在**内存里**升级，免得"我只看了一眼、
  文件就被改了"。落盘由启动时的 `config_store.migrate_file()` 显式完成
  （先备份、再原子写），并在日志里自证：
  `P11: 配置已从 v1 升级到 v2（已备份 config-…json）`。
- v1 → v2 **只是版本号变化**：三块节本来就是可选的（不写 = 无覆盖），
  所以不需要往文件里塞空对象。
- 不认识的高版本**不猜**，直接报"不受支持"。

**新增的校验**（全部 `ConfigError`，**不许静默忽略**）：

| 项 | 规则 |
|---|---|
| 功能开关名 | 必须在 `runtime/features.py` 注册表里 |
| 参数名 | 必须在 `runtime/tuning.py` 的参数表里 |
| 参数值 | 走 `tuning._coerce()`：类型 + `lo`/`hi` 硬边界 |
| 按群集合名 | 必须是已登记的名字（`trend` / `recap`） |
| 集合里的 cid | **必须在 `groups` 里**（拼错就报错，否则它永远不生效） |
| 布尔字段 | **只认真布尔**：`bool("false")` 是 `True`，字符串 `"false"` 曾被静默当成打开 |

**端到端"真进运行期"**：起子进程 `import bot` 喂一份 v2 配置，断言
全局开关 / 按群开关 / 按群参数 / 全局参数 / 按群集合**全部生效**，
且"别的群不受影响"（`test_v2_config_reaches_runtime_end_to_end`）。

**生产验收（6 项全过）**：

```
0) 迁移前：version=1 群=5 键=['bots','groups','version']
1) 重启日志：P11: 配置已从 v1 升级到 v2（已备份 config-20260926-161956.json）
2) 磁盘文件：version=2 群=5
3) 最新备份里 version=1（= 升级前那一版，可回滚）
4) 与迁移前逐字段比对：群一字未动 / Bot 一字未动 / 只多了 version 变化
5) 面板：schema_version=2 source=file 群(配置)=5
6) 异常 0
```

**本轮抓到的三个问题**（都是"能配但不生效"这一类，值得记下来）：

1. **全局功能开关的键形状不一致**：`features.on()` 找 `"*|key"`，
   而配置与 `tuning` 用的是**裸 `"key"`** ⇒ 全局关闭配了却不生效。
   **端到端测试抓到的**（单元测试看不出来）。已统一成裸 `"key"`（兼容 `"*|"`）。
2. **页面保存会抹掉 v2 三节**：`parse_form` 只认群和 Bot，而它写出的 version
   是当前版本 ⇒ 一次"改个群别名"的保存就会把开关/参数/集合**整节删掉**。
   已改成 `parse_form(form, base=…)` 从当前配置**继承**这三节，
   并加了一条端到端防丢失测试。
3. **`log` 在启动早期还没定义**：升级自证行放在运行时导入之前 ⇒ `NameError`。
   **子进程测试抓到的**。已把落盘升级挪到运行时导入之后。

**顺带查清一个长期 flake**：`test_login_body_size_is_bounded` 偶发
`ConnectionAbortedError (WinError 10053)`。根因不是测试，而是**服务端**在
body 超限时**没读请求体就回 400 并关连接** —— Windows 于是发 RST，把还在写
body 的客户端打断。已加 `_drain()`（有上限地读掉再回响应），
该用例连跑 6 次无复现。这个 flake 在 P12-A/B 两轮各出现过一次，
一直被当成"环境抖动"——**这次查清了，不是环境**。

## 5.5 P12-D 验收记录（2026-09-26，已上线）

**做了什么**：新增 **`/features` 功能与参数页**（与 `/edit` 群与 Bot 页并列，
互不干扰），三块内容：

| 块 | 交互 |
|---|---|
| **功能矩阵** | 行=功能（按 7 类分组），列=群。每格**三态单选**：「跟随默认／开／关」；最左一列是**全局**开关。停用的群整列标注 |
| **参数** | 先列全局（留空=用代码默认），再按群列覆盖（留空=跟随）。每格显示默认值、单位、允许范围 |
| **按群集合** | `trend`/`recap` 的群多选（勾选=在该群生效） |
| **强制复位** | 每个"有状态"的功能 × 每个群一个按钮 → `POST /edit/reset` → 只清进行中状态、**不删数据**、记审计 |

**三态而不是两态**（关键设计）：功能开关在"全局/按群"两级都可以是**没配**
（跟随默认）。只给"开/关"两个按钮的话，用户没法表达"这一格回到默认"，
最后谁都不敢动。三个 radio 是纯 HTML —— **没有 JavaScript 也能用**。

**CSP 放开（你已批准的）**：

```
default-src 'none'; style-src 'unsafe-inline'; script-src 'self';
form-action 'self'; frame-ancestors 'none'; base-uri 'none'   + X-Frame-Options: DENY
```

JS 只做体验（改动计数、离开提醒、参数越界就地标红、提交前确认），
**无内联脚本、无 `onclick`、无 `eval`、只用 `textContent`**；
静态资源走**白名单路由**（只服务固定文件名，不做目录遍历）。
303 重定向也补上了安全头（原来漏了 —— 303 是最常见的一跳）。

**防"静默清空"**（本轮抓到的真问题）：复选框没勾时**什么都不提交**，
这与"这一节根本没渲染"长得一模一样。如果不区分，一份**老页面/脚本/半截提交**
就会把默认非空的集合（趋势/回顾只给认证群）**整片清空**。所以：

- 页面渲染时写隐藏标记 `feat_form=1`；没有它 ⇒ `parse_features` **一个字都不动**。
- 每个集合另有 `scope_seen[<name>]=1`：没渲染的集合不进结果。

**参数值要规范化**：文本框提交上来是字符串，直接落盘会得到
`"devil.cooldown": "601"`（数字写成字符串）。虽然读的时候会转、行为没错，
但对账/diff/手工改都更容易出错。现在 `parse_features` 会用
`tuning._coerce()` 把它们变成 int/float 再写。

**生产验收（`tools/p12d_check.sh`，8 步）**：

```
1) 未登录访问 /features      → 200 登录页（不泄漏）
2) 登录后渲染                → 64 个功能行 / 48 个参数行 / 2 个集合 / 防丢失标记 ✓
3) CSP + 静态资源            → script-src 'self'、frame-ancestors 'none'、
                               X-Frame-Options: DENY、/static/app.js 200、
                               /static/nope.js 404（白名单）
4) 无害覆盖（devil.cooldown 600→601，主动吐槽默认关所以线上无感）
                             → 200「已保存」+ 落盘 + 审计一行
5) 越界值（devil.base_prob=5）→ 400「未写入」，文件一字未动
6) 重启后自证               → `P12: 参数 共=48 已覆盖=1`（真生效）
7) 撤销覆盖（留空）          → 落盘回到无覆盖 → 重启后 `已覆盖=0`
8) 异常 0
```

**本轮踩到并在文档里钉死的部署陷阱**（第二个变体）：

| 改了什么 | 该用什么 | 用错的后果 |
|---|---|---|
| **挂载文件**（config.json） | `docker compose restart` | 用 `up -d` 是**无事发生**（compose 看不出挂载文件变了） |
| **代码/镜像** | `docker compose up -d --force-recreate` | 用 `restart` **不会换镜像**（还是老代码在跑） |

我这次就是漏了 recreate：镜像建好了、容器却没换，于是 `/features` 一直 404、
CSP 还是老的 —— 而**每一步看起来都"成功"**。判断依据只有一条：
`docker exec dzmm-bot grep -c '<新东西>' /app/...`（或看容器 StartedAt 与镜像）。

**顺带修掉两个真实的交付缺陷**：

1. **`admin/static/app.js` 从来没被上传过**：`deploy.ps1` 的扩展名白名单只有
   `py|sh|yml|yaml|service`，`.js` 不在里面。危险之处在于**它是静默失效的**
   —— 页面没有 JS 也能用，所以不会有人发现脚本 404。已把 `js|css` 加进去。
2. **`.js` 与 `static/` 目录**：Dockerfile 是 `COPY . .`，所以只要文件到了
   宿主机就会进镜像；问题 100% 出在上传白名单。

**第三个部署陷阱：SSH 链路会破坏某些 cipher/MAC 组合**（查清了，不是"服务器挂了"）：

| 现象 | 真相 |
|---|---|
| `ssh: Connection to … port 22: Connection timed out`，但 TCP 端口开着、8090 返回 200 | 握手在 KEXINIT 之后卡住 —— 不是服务器的问题 |
| `aes256-ctr` 报 `Corrupted MAC on input` | 链路上有东西在破坏流量 |
| `aes128-gcm@openssh.com` | **稳定可用**（AEAD 一次性认证，不吃这个亏） |

这个现象在前几轮各出现过一次，我按"等一两分钟自愈"处理，浪费了不少时间。
现在 `deploy.ps1` 把 cipher **固定**成 `aes128-gcm@openssh.com`（`ssh` 与 `scp`
都加了），并写清了原因。**教训：反复出现的"环境抖动"值得查到底 —— 这次查出来
是确定的 cipher 选择问题，两次都当成抖动就永远在同一个坑里打转。**

## 七、改造时必须绕开的既有陷阱（都是这个仓库里真实存在的）

这几条不是"注意事项"，是**这个 codebase 已经埋着的雷**；P12 每一步都要对着它们检查。

1. **分派顺序就是行为。** 主循环里几十个判定依次判断，任一判定的哨兵值写错，
   就会有一类功能整体失灵或被"兜底"判定吃掉。
   现成的坑：`is_profile_cmd` 用 `""` 表示**"这不是命令"**，
   而 `is_register_cmd` / `is_rewrite_cmd` 用 `""` 表示**"是命令，但没有参数"** ——
   同一个返回值，两种相反语义；`is_dj_command_cmd` 是**依赖其他所有判定结果的兜底**。
   ⇒ P12-A 登记功能时，**判定函数一个都不许改写**，只在它们**之后**加开关闸门；
   并补一个"顺序断言"测试（把登记顺序与实际调用顺序逐条比）。

2. **人设是 contextvar，会残留。** `bot.py` 主循环每轮开头必须
   `set_persona_cid("")`（代码里有注释：**2026-09-17 事故** —— 研讨群的早安被写成
   玫瑰房管家口吻，因为上一轮最后一个群是 Rose 房间群）。
   ⇒ 人设一旦可配置，**每个群的判定/发送前都要显式设置人设、用完清掉**；
   这条要有测试：配置了 N 个不同人设的群，广播类文案（问候/记忆汇报）
   必须仍然用默认人设。

3. **`_ACTIVE_CID` 只有一个写点**（`tools/deploy_gate.py` 里有断言钉着）。
   ⇒ 功能闸门若需要知道"现在是哪个群"，一律走 `runtime/ctx.py`，
   **不许**再引入第二个写点。

4. **长文本有平台硬限制。** `runtime/outbound.py` 里写着 `BOT_GROUP_MAX_CHARS = 1000`
   与 `BOT_GROUP_MAX_NEWLINES`（≤10 行），注释原文：
   「普通账号受 1000 字符 / 10 换行限制，超限必须走官方 Bot」。
   人设和文案一旦能在页面上编辑，就可能被人写成超长文本。
   ⇒ 人设页的"体检"必须**按发送通道**检查长度与换行数，超限直接拦下
   （认证群走 Bot 通道没这个限制，但玫瑰群走账号，有）。

5. **两套"文本"不能混成一个源。** 现在 `prompts/`（39 个提示词文件，
   `_p()` 包裹、缺文件就退回代码默认）负责人设之外的提示词工程；
   页面上的人设只能管**人设层**。⇒ 明确边界，并在页面上标注
   "这条文案来自 prompts/ 文件，改它要动服务器"，别让人以为页面上能改全部。

6. **限流与令牌桶永远在。** 无论功能开关怎么配，`throttle_guard` +
   出站队列的按群串行都不许被绕过 —— 参数可调的只是"功能自己的冷却"，
   平台级的限流是另一层，**不暴露给运营**。

7. **单字符前缀匹配的历史行为。** `_find_uid_by_name` 用单字符前缀匹配，
   已知会命中「裳姐姐」（记录在案、**刻意没改**）。
   ⇒ 涉及"对某人做什么"的功能（调教/训斥/点名）做成可配时，
   要连带把"点名解析规则"作为只读说明写在页面上，避免用户以为是随机命中。

## 十、C 方案（页面上改文案模板）深入分析

你选了 C，但要求"再分析一下"。这一节就是那份分析。结论先给：

> **C 值得做，而且对小小糯来说 C 不是"高级附加功能"，而是"改人设"的必要组成部分**
> （原因见 10.1）。但 **39 个提示词不能一视同仁**：按"改坏的后果"分成三档，
> 三档的编辑方式、校验手段、上线顺序都不同。**建议 C1 + C2 做，C3 只给"微调 + 强制契约自测"**。

### 10.1 为什么 C 是必须的：小小糯的"人设"散在三个地方

| 人设成分 | 在哪 | 体量 | 属于哪一档 |
|---|---|---|---|
| 身边/口吻短设定 | `personas.PERSONAS[x].extra` | 默认 0 字 / 房间 1392 字 | A |
| **日常对话的主人格** | `prompts/CMD_PROMPT.md` | 42 行 / **1344 字**（含 4 条 few-shot） | **C** |
| 固定话术（21 个 key） | `personas.PHRASES` | 帮助/介绍/点名/记忆列表… | B |
| 各功能怎么说话 | `prompts/*.md` 其余 38 个 | 120–3488 字不等 | C |

关键：**`CMD_PROMPT.md` 就是"小小糯平时怎么说话"的主人格**（`generate_reply` 用它，
是 @我 与兜底聊天的唯一提示词）。只做 A+B 而把 C 排除在外，
等于"能改自称和口癖、改不了它到底是个什么性格" —— 这正是你最想改的东西。
⇒ 所以 C 必须做；真正要分析的是**怎么安全地做**。

### 10.2 39 个提示词的风险分档（按"改坏的后果"）

**C1 自由文案类（24 个，安全）** —— 输出是自由文本，改坏了只是"话说得不好"：

`GREETING`（问候）、`CUTE_ROAST`／`DEVIL_ROAST`（吐槽）、`DIAOJIAO`／`DIAOJIAO_END`、
`INSULT`／`INSULT_CONTINUE`、`MEMORY_SUMMARY`、`SUMMARY`、`PERSON_SUMMARY`、`PROFILE`、
`ARCHIVE`、`POEM_THEME`、`XP`、`PERF_ENRICH`／`PERF_INSULT`／`PERF_COMMENT`／`PERF_ENDING`、
`SCENE`／`SCENE_CONTINUE`／`SCENE_REWRITE`／`SCENE_END`、`RANK`、`CMD_PROMPT`、`DEFEND`（死代码）。

**C2 格式敏感类（11 个，中风险）** —— 输出有**形状约束**，破坏了会被平台截断或把卡片撑坏：

| 提示词 | 硬约束（写死在提示词里的） | 破坏后果 |
|---|---|---|
| `HOROSCOPE` | 「只写一段、**绝不换行**、160–240 字」 | 换行撑坏运势卡 |
| `TREND` | 「一段、绝不换行、禁编造」 | 同上 |
| `FORTUNE` | 「只写一句、不换行」列进定长卡片 | 卡片错位 |
| `POEM`／`POEM_THEME` | 句数严格（词牌/七绝…） | 诗句数不符，观感崩 |
| `RECAP` | **固定 3 行**，每行以 💬／🎭／📌 开头 | 解析/排版失败 |
| `STORY_START`／`STEP`／`END` | **必须给【1】【2】【3】三选项**，行数上限 8/9/8 | **选项解析失败 → 剧情卡死** |
| `PERF_NOVEL`／`PERF_NOVEL_CONTINUE` | 20+ 条硬约束、章节编号不得重置、8000 tokens | 小说崩坏或超时 |
| `RANK` | 「前五名」 | 榜单错乱 |

**C3 结构化输出类（5 个，高风险）** —— 输出要被**程序解析**，破坏了不是"难看"而是"功能报错"：

| 提示词 | 契约 | 位置 |
|---|---|---|
| `HEAT_JUDGE` | 必须返回 `[{"name":…,"delta":…}]` JSON 数组、0–30 分档 | `brains.py:859` |
| `VOTE_OPTIONS` | 必须返回 JSON 数组（解析失败返回 `[]` ⇒ 投票没选项） | `brains.py:1081` |
| `MEMORY_FILTER` | JSON 挑选（**第 40 个，还没外置**，在 `runtime/memory.py:34`） | 未外置 |
| `STORY_*` | 严格 `【1】【2】【3】` 文本契约（严格说属 C2/C3 之间） | 见上 |
| `RECAP` | 三行 emoji 契约（同上） | 见上 |

### 10.3 让 C 变安全的三道机制（这是分析的重点）

**机制 1 — "保存即自测"（把失败从事后发现变成保存时拒绝）。**
这是 C 方案能不能落地的关键。每个 C2/C3 提示词配一个**契约校验器**：
保存前用**新提示词 + 一组固定示例输入**做一次真实调用，检查：

- C3：输出能否 `json.loads` / 能否解析出 `【1】【2】【3】` / 三行 emoji 是否齐；
- C2：行数、字数、是否含换行（能不能通过 `group_message_chunks` 的 1000 字符/10 换行）；
- 全部：**必须保留的片段**白名单（如 `HEAT_JUDGE` 里的字段名、`STORY` 的 `【1】`、
  `RECAP` 的 💬🎭📌）+ **占位变量**不得丢失。

校验不过 ⇒ **一个字都不写**（复用 `config_store.save()` 那条"校验后写"的既有纪律）。
代价：每次保存一次 LLM 调用（0.5–3 秒）；收益：**不可能把结构化功能改崩**。

**机制 2 — 可编辑层与代码默认分离，一键回退。**
沿用 `prompts/` 已有的机制（`_p()`：文件在且非空才用文件，否则退回代码默认），
页面只写文件、**永不改代码**；每个提示词旁边一个「恢复代码默认」（删文件或还原）。
再加 `DZMM_PROMPTS=off`（已有）作为全局秒退开关。

**机制 3 — 版本历史与差异（长文本必须比"整份配置备份"更细）。**
现状：配置备份是**整份 config.json 快照**，磁盘 20 份、页面只列 10 份、不能看差异 ——
改人设/文案会天天写，这个粒度不够用。方案：
`prompts_backups/<NAME>-<时间戳>.md` 保留**每份提示词的最近 N 版**，
页面上能"看我改了什么（逐行 diff）"和"回滚到某一版"。

### 10.4 C 的两个反直觉结论（建议据此决策）

1. **不要做"按群不同的提示词"。** 39 个提示词 × N 个群 = 组合爆炸，
   而且会让"同一个功能在不同群行为不同"这件事变得无法推理。
   ⇒ 文案模板**全局一份**；"按群不同"只通过**人设（A/B）**与**功能开关**实现。
   （房间群的特殊口吻本来就是靠 `rose_butler` 人设 + `ROOMS` 达成的，够用。）
2. **`CMD_PROMPT` 要单独对待。** 它体量最大（1344 字、含 4 条 few-shot）、影响面最广
   （@我 与所有兜底聊天），改它等于换人格。建议：**允许编辑，但强制 dry 预览 +
   记录 old/new 的 sha256 + 一键回退**，并且**只允许改"要求清单"段，不允许删 few-shot 段**
   （few-shot 是输出风格的实际控制点，删了会明显跑偏）。

### 10.5 落地顺序与工作量

| 阶段 | 内容 | 为什么这个顺序 |
|---|---|---|
| **C1** | 24 个自由文案可编辑 + 版本历史 + dry 预览 | 风险最低，先把"编辑/预览/回滚"这套体验跑顺 |
| **C2** | 11 个格式敏感 + 长度/行数/片段白名单校验 | 机制已就位，加校验规则即可 |
| **C3** | 5 个结构化输出 + 契约自测（JSON/三选项/emoji 三行） | 最难，但有了"保存即自测"就不再可怕 |
| **C-附** | 把第 40 个提示词 `MEMORY_FILTER` 也外置 | 现在只能改代码，属漏网 |

**热加载**：今天 `_p()` 在 import 时调用一次 ⇒ 改文案要重启进程。
C 阶段要顺带把 `_p()` 改成"按 mtime 缓存、变了就重载"，否则"改一句话重启一次"
会把体验毁掉（这条与 §3.4 的 P12-F 合并）。

**工时锚点**：C1 ≈ P12-E 的一半；C2/C3 的**主要成本在校验器**（每个契约要写
示例输入 + 解析断言，并配测试），不是一个通用功能。
