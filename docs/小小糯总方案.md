## 一、一页结论

**目标**：把小小糯从「单文件（`bot.py` 6364 行）会话自动化脚本」，改造成「DDZM-bot 范式的分层系统」，并在此过程中把**群消息通道换成官方 Bot API**。这两件事合成一个 program，不拆开做。

**最重要的一条结论**：

> **目标不是"消灭登录态"，而是"让登录态变得不关键"。**
>
> 因为私聊、撤回、图片、小说分享**注定只能走普通账号**（DDZM-bot 已实测），所以普通账号会永久存在。
> 正确的做法是：**高频、实时、易触发验证码的「群文本」交给 Bot API**；**低频、非实时的「私聊/撤回/图片/分享」留在侧车**——验证码掉线时可容忍。

**由此带来的关键简化（省掉一整块工作）**：

> **Webhook 不在关键路径上。**
> Bot API 的**发送是纯出站**（`POST /api/bot/send-message` + `X-Bot-Token`），**不需要任何公网入口**。
> 入站继续用现有 Socket.IO（DDZM-bot 的当前策略，且它明确**故意不接 Webhook**）。
> ⇒ **之前 Gate 0 卡住的「域名 / HTTPS 证书 / 80·443 / sslip.io」全部退出关键路径**，只在可选的 P10 才需要。

**形态**：**1 个 Bot（认证妹子群）** + 1 个普通账号侧车 + 出站队列；PostgreSQL 延后。

## 二、为什么必须合并成一个任务

两个计划不是并列关系，而是互为前置：

| 若分开做 | 会发生什么 |
|---|---|
| 先换传输、不做安全网 | 换完无法证明"少了个角落"——小小糯有 ~40 项功能，全凭人工比对 |
| 先换传输、不做出站队列 | 双身份发送必然重复投递（Bot 发了、账号又发一次） |
| 先重构结构、不换传输 | 把 Playwright/Socket.IO 内部打磨一遍，而它们正要被替换 —— 纯浪费 |
| 先换传输、不做 DB 化 | 出站队列需要租约/幂等/状态回写，JSON 单文件撑不住 |

**排序原则（借用 DDZM 的实践）**：**先建安全网 → 再换传输 → 最后治理结构**；且**不打磨即将被删除的代码**。

```
                       ┌─────────────────────────────────────────┐
                       │ outbound_messages（出站队列 / outbox）   │
                       │  state=pending  租约  attempt  幂等键     │

                       ┌─────────────────────────────────────────┐
```

| 模块 | 职责 | **不应该做什么** |
|---|---|---|
| `core/` | 业务规则、命令路由、状态机 | 不碰平台 Cookie、不直接发送 |

| `platform/session.py` | **唯一登录者**：浏览器 Profile / 取 Token / tRPC | 不处理业务 |

| `platform/sender_account.py` | 私聊/撤回/图片/分享出站 | 不做业务判断 |

## 四、五条铁律（不可违背）

1. **普通账号不可退休**——私聊 / 图片 / 小说分享只能走它（撤回能力也只在它身上，虽然小小糯当前没用它）。侧车永久存在。
2. **平台未明确 ACK 时，绝不换通道重发**——否则用户看到两条一样的消息（DDZM 明确列为原则）。
3. **业务代码不直接发送**——只写 `outbound_messages`，由 Worker 领租约发出。
4. **只有一处能登录**——其它模块**代码层面没有登录函数**（不是靠约定）。
5. **Webhook 与 Socket 不可同时处理同一个群**——若要接 Webhook，必须先做幂等 + 群职责划分（P10 闸门）。

## 五、发送路由表（硬编码，不靠运行时判断）

| 内容类型 | 通道 | 依据 |
|---|---|---|
| 群文本（短，≤1000 字符且 ≤10 换行） | **Bot API 优先**，失败回退账号 | DDZM 当前策略 |
| 群文本（长，>1000 字符或 >10 换行） | **Bot API**（账号发不出） | 普通账号有 1000/10 限制 |
| 私聊 | 普通账号 | Bot 不处理私聊 |
| 需撤回的消息 | 普通账号（**当前不适用**） | 只有账号能 `message:recall`；但实测小小糯**没有**撤回功能，故暂不构成约束 |
| 图片 | 普通账号 + `chatroom.uploadImage` | Bot API 不支持上传 |
| 小说/故事集分享 | 普通账号，`content.type=share` | `shareType=novel` |

### P3 出站队列：怎么做到"零调用点改动"

先测了发送的调用面：**22 处直接 `sender.send()` + 17 处 `_send()`，共 39 个点**。
但它们**全部汇聚到 `Sender.send(text, cid, allow_fallback=True)` 这一个口子**。

于是 P3 不动那 39 处，改成**用一个装饰器包住 sender**：

```python
sender = _wrap_with_outbox(Sender(), dry)     # main_loop 里仅此一行
```

`OutboxSender` 把 `send()` 换成「落库 → 领租约 → 调原 sender → 回写状态」，
其余属性（`start`/`navigate`/`close`…）经 `__getattr__` **原样透传**。
⇒ 调用方语义完全不变（仍同步返回 `bool`），**行为与现网逐项一致**。

**两条安全设计**

1. **防御性导入**：`deploy.ps1` 目前只上传顶层 `*.py`，`runtime/` 子包可能不在线上。
   缺包时静默退回直发并记一行日志，**绝不让 bot 起不来**。
2. **秒级回滚**：`DZMM_OUTBOX=off` 即退回直发；初始化异常也自动退回。

**落库字段**已按 P4 需要备好：`status / attempt_count / lease_worker_id / lease_token /
lease_expires_at / platform_sent_id / last_error / recall_after_seconds`。
P4 的异步 worker 直接复用，不用改表。

**未做（有意）**：自动重试与改道。DDZM 的接入指南明确
「平台未明确 ACK 时，绝不换通道重发」，所以失败只记状态，由上层决定。

## P5 · 唯一登录者 + 令牌桶

### P5.1 唯一登录者（会话锁）✅ 已实现并验证，**已上传生产、待重启生效**

**要解决什么**：现在有**四个**进程可能同时动凭据 ——

1. `entrypoint.sh` 的 `renew_token.py` 循环（每 5 分钟）
2. `check_bot_health.py` 主动派生 `headless_relogin.py`（refresh_token 将到期时）
3. `auto_recover.py` 的登录阶梯（bot 连续 unauthorized 时）
4. 容器重启时 `entrypoint.sh` 直接跑 `headless_relogin.py`

而平台的 **refresh_token 是轮换制**（`renew_token.py` 里就有
「已同步新 refresh_token（rotation）」）—— **两处同时续期会互相作废**，
表现就是随机 401 / 被踢下线。这正是 DDZM 文档强调的那条硬约束。

**为什么敢动**：两个 chokepoint 都是单点的（和 P3 的 `Sender.send` 同一个套路）——
所有**凭据写入**都走 `token_store.save_cookies`；会话锁只要包住"谁去登录/续期"即可。

**设计：失败开放（fail-open）**。锁只用来**减少并发**，绝不能因为它自己坏掉就让续期停摆——
那会把"偶发 401"升级成"必然掉线"。所以：机制异常 → 视为拿到锁；拿不到锁（别人在做）→
调用方**跳过本次**（不是失败）；`DZMM_SESSION_LOCK=off` 可整体关闭。

| 文件 | 改动 |
|---|---|
| `runtime/session.py` | 新增：`guard(reason, timeout)` 上下文管理器 + `note_credentials_written` / `version`。后端：Linux `fcntl.flock`（崩溃自动释放）；其它平台 `O_EXCL` + 陈旧超时 |
| `session_guard.py` | 新增统一入口；`runtime` 包缺失时退化为"永远拿到锁"（回到改动前行为） |
| `token_store.py` | `save_cookies` 写入后递增 session 版本（唯一凭据写入点） |
| `renew_token.py` | 拆出 `_renew_locked()`；`main()` 先取锁，拿不到就跳过（有 600 秒提前续期窗口，跳一次不会过期） |
| `headless_relogin.py` | 拆出 `_do_login()`；`main()` 取锁 + **锁内双重检查**（等锁期间别人可能已登好）；`--manual-captcha` 路径也持锁 |
| `auto_recover.py` | 拆出 `_recover_locked()`；`main()` 取锁，拿不到就跳过并告警 |

**验证**

| 层 | 结果 |
|---|---|
| 本机单测 | 18 通过 / **3 跳过**（跳过的正是 flock 后端——Windows 没有 `fcntl`） |
| 全套 | **252 通过 / 3 跳过** |
| **Linux 侧真跑**（`tools/session_lock_check.py`，在目标镜像内） | **12/12 通过**，含**跨进程互斥**：子进程持锁 → 父进程被挡；子进程退出 → 父进程可取 |

> ⚠️ 单列这一步的原因：**flock 是本机测不到的路径，而生产用的正是它**。
> 只在 Windows 上跑测试等于没验证 —— 所以必须去 Linux 上真跑一遍。

**途中修掉两个问题**

1. **代码 bug（跨平台）**：`O_EXCL` 后端释放锁时，我原先**先删文件再关 fd**。
   Windows 不允许删除仍打开的文件 → 静默删不掉 → 锁文件残留 → **后续永远取不到锁**。
   本地测试直接抓到了，改为**先关 fd 再删**。
2. **我的测试写错了**：Linux 检查脚本里，我在**仍持有外层锁**的情况下断言"第三次可取"——
   它当然应该被拒。断言写反了，已改正为"持锁期间第三次仍被拒"+"释放后可取"。

### P5.2 令牌桶 + 冷却 ✅ 已上线

## P7 · 数据层：JSON → SQLite ✅ 已上线

### 先更正一处我自己写错的判断

起草时我断言"**两个进程在无锁地写同一个 `state.json`**（bot 与健康巡检）"，
并据此论证要上数据库。**那是错的**：`check_bot_health.py` 里的
`load_state/save_state` 读写的是它**自己的** `check_health_state.json`（该文件第 24 行）。
我把"同名函数"当成了"同一个文件"。核实后：`state.json` 的写者**只有 `bot.py`**。

### 核实后的真实理由（三条）

| # | 问题 | 证据 |
|---|---|---|
| 1 | **写是非原子的 → 截断即静默清零** | `save_state` 用 `write_text` 直接覆盖（`profiles.py` 注释说明：这些文件是**文件 bind mount**，`os.replace` 会 `Device busy`）。写到一半被 kill（容器 recreate / OOM）→ 截断 JSON → 而 `load_state()` 解析失败时**静默返回 `{}`** → **全群发情值 / 高潮计数 / 状态机 / 记忆 / 投票一起无声清零**，且无任何告警 |
| 2 | **写放大** | `state.json` 约 50KB，`bot.py` 里约 **45 个写入点**，每次改动都重写整文件 |
| 3 | **`profiles.json` 有两个潜在写者** | `bot.py` 与手工脚本 `batch_register.py` 都走"读整个文件→改→写回"，同时跑会丢更新 |

### 与方案的偏离（有意）：用 SQLite，不用 PostgreSQL

- 现在只有**一个** bot 进程（"多群多 Bot、多服务"的设想已在范围收窄时去掉），PG 的跨机并发用不上；
- 宿主机 **2 核 / 1.8G**，再起一个 PG 容器是**多一个故障域、多一份内存**；
- 上面三条 SQLite 全部能解决，而且它落在 `./data` **目录挂载**上 —— 不存在 `os.replace` 的 EBUSY 问题。

若将来确实要多进程/多机，**`Store` 是唯一需要替换的东西**。

### 实现（沿用"零调用点改动"的套路）

| 文件 | 作用 |
|---|---|
| `runtime/store.py` | SQLite 内核：`kv(scope,key,value)` 三 scope（group / profile / meta）+ `BEGIN IMMEDIATE` 单事务 + WAL + 一次性 JSON 导入（幂等、**不删 JSON**）|
| `state_store.py` | 统一入口，**函数名与签名和原来完全一致** → `bot.py` 约 45 处、`profiles.py` 调用点**一处都不用改** |
| `bot.py` / `profiles.py` | 改为委托；保留 JSON 实现作为回滚后端 |
| `docker-compose.prod.yml` | 顺手补上**巡检/续期状态文件**的挂载（原先没挂 → 每次重建容器去重状态就丢、会重复告警）|

回滚：`DZMM_STORE=json` 立即退回 JSON 读写（文件保留不删）。
**注意**：回滚会丢掉切换之后写进 SQLite 的改动 —— 这是回滚的固有代价。

### 第 3 步：prompt 外置 ✅

`brains.py` 里有 **39 个** `*_PROMPT` 长文本（人设、发骚、调教、公演、算命、
运势、投票、剧情、羞辱、记忆总结…），改一个字都要动代码 + 重新构建镜像。

**设计：覆盖，不是搬家。**

```python
CMD_PROMPT = _p("CMD_PROMPT", """<原来的字面量原封不动留在这里>""")
```

- 代码里的字面量**保留为默认值**（`runtime/prompts.py::load`）
- `prompts/<NAME>.md` 存在且**非空**则覆盖 → 调 prompt 不用改代码、不用 rebuild
- 于是"prompt 外置"最常见的坑 —— **文件没了 → prompt 变空 → LLM 乱答** ——
  在这个设计下不可能发生：最坏情况就是退回今天的行为
- `DZMM_PROMPTS=off` 一键关掉外置；`DZMM_PROMPT_DIR` 换目录

**为什么不用"运行中热更"**：`brains.py` 在 import 时取值，改文件必须**重启进程**。
热更会造出"一半新 prompt、一半旧 prompt"的中间态，而 prompt 影响的是**人设**，
是最不该出现中间态的地方。

**迁移是程序化提取，不是手工转录**（`tools/p8_prompts.py`）：

1. `ast` 读出每个常量的**准确值** → 原样写 `prompts/<NAME>.md`
2. `ast.get_source_segment` 取出原字面量 → 包成 `NAME = _p("NAME", <原字面量>)`
3. 重新 `import brains`，**逐个比对 39 个取值**与迁移前是否完全相同；不等即中止

⇒ 从机制上排除了"抄错一个字"（改了人设却没人发现，是最难查的一类回归）。

**生产侧挂了卷**（`docker-compose.prod.yml`）：

```yaml
- ./prompts:/app/prompts
```

没挂上也不会坏 —— 只是退回代码默认值，而且启动日志会**说出来**：

```
P8: prompt dir=/app/prompts 来自文件=39/39 磁盘文件=39
```

> 这行是刻意加的：外置最隐蔽的失败就是"悄悄退回默认值"，
> 不打印的话你改完文件、重启、发现没生效，会先怀疑自己改错了地方。

**改 prompt 的正确姿势**：改 `/opt/dzmm/prompts/<NAME>.md` → `docker restart dzmm-bot`。
`brains.py` 里的字面量从此只是兜底，**别再改它**（改了不生效，除非把文件删掉）。

#### 迁移机制（`tools/p8s4_move.py`）

不能靠手工剪切粘贴，理由和 P8 第 3 步不同、而且更严重：

> 搬走的函数如果偷偷引用了 `bot.py` 的某个模块级全局，
> 搬出去之后 **import 不会报错**，只在**真正调用时** `NameError`。
> 也就是说一半的错要等到线上有人发那条指令才炸。

三道闸门，任一不过就不写盘：

1. 源文件里每个函数名/常量名、每段待删文本都**唯一存在**
2. 组装出的新模块里，被搬函数引用的每个模块级名字都必须有来源
   （兄弟函数 / 头部 import / 内置）——**未解析依赖直接中止**
3. 改写后的 `bot.py` 必须仍然 `ast.parse` 通过
   （这条是补的：import 锚点按名字匹配时曾把 import 插进函数体，直接语法错误）
4. 搬完重新 `import bot`，逐个用 `inspect.getsource` 比对源码文本与搬之前一致

需要改文本时不能在函数体里偷偷改，只能在 slice 里**声明**（例如
`_ACTIVE_CID` → `ctx.get_active_cid()`），工具会逐条打印出来，
而"搬完比对"以**声明改写后**的文本为基准 ⇒ 仍然能证明"除了声明过的改写，一个字符都没动"。

#### 行为保持的保证方式

不是靠测试碰运气，而是**结构性的**：搬的是同一段源码文本，
`inspect.getsource` 逐字比对通过 ⇒ 行为不可能变。

### 一个工具链陷阱（值得单独记）

**PowerShell 5.1 的 `Get-Content` 会把含中文的 UTF-8 无 BOM 文件读少行数。**

可复现：10 行中文内容，`(Get-Content f).Count` 返回 **1**；同样的 10 行纯 ASCII
返回 10。机理是 PS 5.1 按系统 ANSI（GBK）解码，中文字节与紧随的 `0x0A`
被拼成一个双字节 GBK 字 → **换行被吃掉**。

这解释了当初 `deploy_gate.py` 为什么会被写成一团乱码，也解释了这次
"`bot.py` 到底多少行"一度出现 3039 / 3255 两个数（后者才是对的）。

**规矩**：`.ps1` 保持纯 ASCII；读写 UTF-8 文件一律用编辑工具或 Python，
**连"数一下行数"都不要用 `Get-Content`**。

## P9 · 运维后台

目标：把"要 SSH + `docker logs` 才知道的事"变成一页只读面板
（群配置、登录状态、出站队列、最近错误）。

### 访问方式

**公网直达（当前采用）**：

```
http://47.237.152.187:8090        → 账号密码登录后进面板
```

账号密码在 `/opt/dzmm/.env` 的 `DZMM_ADMIN_USER` / `DZMM_ADMIN_PASSWORD`。
`/api/summary` 是同一份数据的 JSON，`/healthz` 探活 —— 两者**都要登录**。

**仅回环 + SSH 隧道（想彻底不开公网口时）**：`.env` 里设 `DZMM_ADMIN_BIND=127.0.0.1`
并清掉密码，然后：

```bash
ssh -L 8090:127.0.0.1:8090 root@47.237.152.187   # 本地开 http://127.0.0.1:8090
```

一键脚本：`.\admin_tunnel.ps1`（会开隧道并自动打开浏览器，`-Stop` 关闭）。

### 授权：账号密码登录（不是 URL 令牌）

第一版用的是 `?token=`，**换掉了**。令牌的问题都是实际会遇到的：
会留在浏览器历史和链路日志里、**没法登出**、没有失败计数（可以无限试）、
而且它只是"持票入场"，不是"谁进来了"。

| 项 | 做法 |
|---|---|
| 凭据 | 从 `.env` 读（root 600），**不落盘任何凭据** |
| 会话 | 只存在**进程内存**里：随机 32 字节 sid，`HttpOnly` + `SameSite=Strict`，12 小时过期；**重启即全部登出** |
| 比较 | 账号与密码都走 `hmac.compare_digest`，且**都算完再比** —— 否则能从耗时枚举账号 |
| 爆破 | 连续失败 5 次起锁定，5 分钟起逐次翻倍、上限 1 小时；失败与锁定都打日志 |
| 头 | `Referrer-Policy: no-referrer` + 严格 CSP（页面无外链、无内联 JS） |
| 只读 | 唯一允许的非 GET 是 `POST /login`，它只动内存会话表与 Cookie，**不碰库也不碰文件** |

未登录时**一个字节的面板内容都不给** —— 连 `/healthz` 都返回登录页
（实测：境外主机访问 `/healthz` 拿到的是登录页）。
"忘了设密码就把面板挂到公网"被做成了**启动失败**（fail closed），不是静默裸奔。

### ⚠️ 必须配的一条：安全组只放行你的出口 IP

这是 **HTTP 不是 HTTPS，密码在链路上是明文**。所以安全组白名单不是"锦上添花"，
而是**让明文密码可以接受的前提**。实测过：8090 在只设密码、没有白名单时是
**整个世界可连**的（境外节点能打开登录页）。

```
入方向 · 自定义 TCP · 8090/8090 · 授权对象 117.129.62.15/32
```

要真正上 HTTPS 需要给机器配域名 + 证书；在拿到域名之前，
**IP 白名单是唯一能真正收紧的那一层**。

### 四条设计约束（都是刻意的）

| 约束 | 为什么 |
|---|---|
| **只读，且是结构性的** | 只有 `POST /login` 例外（不写任何持久状态）；所有 SQLite 一律 `mode=ro`；`.load_state()` 那种"读写打开、库不存在就建库"的入口**不用**。测试直接扫源码断言"每一处 `sqlite3.connect` 都带 `mode=ro`" |
| **对外的边界 = 登录 + 安全组白名单** | 容器内绑 `0.0.0.0`（必须，见下），发布由 `${DZMM_ADMIN_BIND:-0.0.0.0}` 控制。两条防线缺一不可 |
| **跑在容器内的独立进程** | 容器内是 Python 3.11 且已有拆好的 `runtime/*`，直接复用 bot 同款代码读状态，不会出现"后台照 schema 抄一遍然后漂移"。宿主只有 Python 3.6。不新增容器 —— 1.8G 内存已经被否决过一次"双容器"。`entrypoint.sh` 用 `&` 起，它挂了不影响 bot |
| **fail closed** | `PUBLIC=on` 而没有密码、或密码 <8 位 → 拒绝启动（返回码 2，容器日志一行醒目拒绝） |

### 上线过程中踩到的坑（都被预检/自查/实测抓到）

**1. 容器内绑 `127.0.0.1` → compose 发布的端口连不上。**
docker-proxy 是从**容器 IP** 转发进来的，不是回环。症状很迷惑：`ss` 显示
docker-proxy 明明在 `127.0.0.1:8090` 听着，宿主机 `curl` 却返回 000。
改成容器内绑 `0.0.0.0`，安全靠"登录 + 安全组"那两层保证。

**2. 后台是独立进程，从不 import `brains` → `prompts.stats()` 永远返回 0/0。**
一个"看着正常、其实毫无意义"的数字。生产镜像预检时发现。
本地测试当时只断言了"字段存在"、没断言数值 —— 已经补成
`total == 39 / from_file == 39 / files_on_disk == 39`。
**教训：字段存在 ≠ 数值有意义。**

另外自查时又抓到两个"面板会骗人"的问题，都已修：

- **JSON 把 set 变成了 repr 字符串**：`SCREEN_CIDS` 是 3 个群的 set，
  `json.dumps(default=str)` 把它变成 `"{'a', 'b', 'c'}"` —— 于是"筛查群数量"
  显示成 **120**（字符串长度）。现在 set 统一转 list，并且有一条测试要求
  **整个 payload 不加 `default=` 也能 json.dumps 成功**（从类型上封死不化类型）。
- **错误检测误报**：把「👻 女鬼状态超时，自动恢复」（正常自愈）和
  「告警已发: 续期脚本失败」（通知本身）都算成了错误。
  **误报比不报更糟** —— 一个天天喊"有错误"的面板会被无视，真出事那天也没人看。
  现在只认真正的失败信号，并有排除规则 + 对应测试。

**3. `.env` 行尾混用（CRLF + LF）→ "密码明明一样却 401"。**
改成账号密码登录后，正确密码也返回 401。服务端日志把真相打了出来：
`登录失败 账号='admin\r'` —— 脚本从 `.env` 读账号时把 `\r` 带上了。

根因是一个**不对称**：

| 读 `.env` 的方式 | 值尾部的 `\r` |
|---|---|
| `docker compose` | **自动去掉** |
| shell 的 `cut -d= -f2-` | **保留** |

于是"同一条配置"在容器里是 `admin`、在脚本里是 `admin\r`。
已把 `/opt/dzmm/.env` **统一成 LF**（改完逐项核对 15 个键取值完全一致），
两个写 `.env` 的工具也固定用 LF 写，并给所有读 `.env` 的脚本加上 `tr -d '\r'`。

**4. 登录测试自己踩的坑：`urlopen` 会自动跟随 303。**
登录成功返回 303 + `Set-Cookie`，但 `urlopen` 会跟着跳到 `/`，
于是拿到的是最终页面的 200、`Set-Cookie` 在中间响应里 —— 测试误判成"登录失败"。
改用不跟随重定向的 opener。

还有一个**产品 bug** 是这轮测试逼出来的：没设密码时（仅回环模式）
我把所有请求都挡在了登录页，导致隧道模式完全不可用。
现在"未配置密码 → 不要求登录"，安全性由启动闸门（PUBLIC=on 无密码则拒绝启动）保证。

### 顺带修掉的部署缺陷

`deploy.ps1` 原来是**一次 scp 传一个文件**（约 145 次连接）：
一次连接抖动就让整个上传半途而废、远端停在半更新状态（P9 第一次上传就是这么失败的），
而且 145 次顺序连接超过 120s，老是撞命令超时。

改成 **本地打一个 tar → 一次 scp → 远端解开**：123 个文件几秒完成。
没有 `tar` 的机器自动退回原来的逐文件方式。

### 第 A 期：配置层 ✅

#### 三条硬性设计

1. **文件不存在 ⇒ 完全退回代码里原来的默认值。**
   这让本期成为**零行为变化的纯重构**，也给了"配置写坏了就删掉"这条最简单可靠的
   回滚路径。
2. **配置不是状态**，刻意**不放** `state_store`：那是运行数据（玩法代码会整块
   `group_set` 覆盖、会膨胀、清理它不影响业务）。配置要可 diff、可备份、可回滚、
   **坏掉时能手工改文件救回来** ⇒ 一只人可读的 JSON。
3. **坏配置拒绝启动**，不带着半截配置跑。

#### 校验规则（都不是形式主义）

| 规则 | 防的是什么 |
|---|---|
| cid 非空且唯一 | 同一群被配两次 |
| **Bot 绑定的群必须在群清单里** | P1 那条「绑定群 ≠ 目标群就拒绝启动」断言的推广 —— 防**误发** |
| **两个 Bot 不能绑同一个群** | 否则无法决定走哪个通道 |
| persona 必须存在 | 配错名字要到运行时才发现 |
| Bot 必须有 token 或 token_env | 配了等于没配 |

密钥**不进这个文件**：Bot 用 `token_env` 指向 `.env` 里的变量名（也支持内联
`token`，不推荐）。

#### 去掉一个设计冗余

原来设计里 `groups[].bot` 和 `bots[].cid` 表达的是同一个关系（哪个 Bot 服务哪个群）。
两个真源迟早不一致，而"面板显示的绑定"与"实际生效的绑定"不一致正是运维后台
最不该犯的错 ⇒ 只留 `bots[].cid`，群侧从 bots **派生**。

#### 运维方式

```bash

  --entrypoint python dzmm-bot:latest /app/tools/config_gen.py --show
```

> 跑不了 `runtime/*`。容器里是 3.11。

#### ⚠️ 三个必须知道的坑

1. **挂载前宿主机上必须先有 `config/config.json`。** bind mount 的源不存在时
   Docker 会建一个**目录**，于是 `config_store` 读不到（静默退回默认值）、
   界面写它会失败。运维后台现在会**显式报**这种"路径存在但是个目录"的状态。
2. **`config/config.json` 是服务器侧状态，绝不入库、绝不上传。** 否则一次 deploy
   就覆盖掉界面上的改动（`deploy.ps1` 已显式排除 + 注释说明）。
3. **`docker compose up -d` 不会让配置改动生效 —— 它什么都不做。**
   改的是**挂载进去的文件**，compose 判断"要不要重建"只看 compose 文件与镜像，
   看不出挂载文件变了，于是打印一句 `Container dzmm-bot  Running` 就结束。
   用户以为重启过了，其实进程还是老的。**改配置一律用 `restart`**：

   ```bash
   cd /opt/dzmm && docker compose restart dzmm-bot          # 改 config.json
   cd /opt/dzmm && docker compose up -d --force-recreate dzmm-bot   # 改 .env
   ```

   这个坑是**生产上真踩到**的：验收脚本里那一步"重启让它生效"用的就是 `up -d`，
   日志停在上一轮的启动自证行，脚本却报"重启完成"。页面上的提示语也照抄了
   `up -d`，一并改掉了（`tests/test_config_ui.py` 现在钉住页面里**不许**出现
   `up -d`）。判断是否真重启了，看 `docker inspect -f {{.State.StartedAt}} dzmm-bot`。

### 第 C 期：可视化配置页（`/edit`）✅ 已上线并端到端验收

A 期把配置挪出了代码，但改配置还得 SSH 上去编辑 JSON —— 用户明确要求
"要有一个后台可视化页面来管 bot 和群"。C 期就是这一页。

#### 做了什么

只读面板上加一个 `⚙ 配置` 入口，`/edit` 一张表管群、一张表管 Bot：

| 群表 | 含义 |
|---|---|
| 群 id / 别名 | 别名只用于显示，**不参与任何判定**（所以拿它做线上验收最安全） |
| 启用 | 取消勾选 = 完全不管这个群 |
| 静默 | 只读不回（不回复/不接指令/不筛查/不推送/不同步档案） |
| 入群筛查 / 定时推送 | 两个独立开关 |
| 人设 | 留空 = 用默认人设 |

Bot 表管 `key / 平台显示名 / 简称 / 绑定的群 / token 环境变量名 / 人设 / 启用`。
**token 不落在这个页面里** —— 只填环境变量名，值留在服务器的 `.env`。
（表单里其实支持内联 `token` 字段，但页面不渲染它，避免有人把密钥填进配置文件。）

#### 写入路径上的四道闸

1. **登录**：与只读面板同一个会话，没登录进不来（第一版曾把这个页面整个漏在登录之外）。
2. **CSRF**：与会话绑定的随机 token；`SameSite=Strict` 的 cookie 再挡一层。
3. **校验后写**：交给 `config_store.save()`，校验不过**一个字都不写** ——
   不是"写了再回滚"。
4. **备份 + 审计 + 回滚**：每次保存前自动备份，`config_audit.log` 记一行
   "谁在什么时候改了什么"，页面上能把备份一键回滚回去。

#### 一个刻意的设计：保存后**逐条列出改了什么**

页面上光写一句"已保存"是不够的：`/edit` 是**整表提交**，只要表单里哪个勾没带上
（客户端 bug、脚本拼 body、人为漏看），一存就会顺手把**别的群的开关也翻掉**，
而"已保存"三个字完全看不出来。所以保存/回滚后无条件摊开本次改动清单。

这不是假想 —— 上线当天真发生了：验收脚本拼 body 时**没有判 `checked`**
（把没勾的复选框也提交了），一次"只改别名"的保存顺带把 4 个群的
静默/筛查/推送全翻成 `true`。所以：

- 页面把改动逐条列出来（`render_edit(changes=...)`）；
- 验收脚本加了两条硬断言：**只按 `checked` 提交**（一个都没跳过就直接报错退出）、
  **逐字段比对"除了别名一个字都没动"**；
- 断言"生效的开关数量与基线一致"（`静默=0 筛查=3 推送=2`）——
  文件改了、进程加载了、**真正生效的开关没变**，这条才是端到端的。

#### 配置目录迁移：单文件挂载 → 目录挂载

`os.replace` 在**单文件 bind mount** 上会失败（`[Errno 16] Device or resource busy`，
`runtime/store.py` 里对 `state.json`/`profiles.json` 早有记录）——
而备份也要跟配置放一起。所以改成目录挂载：

```
/opt/dzmm/config/config.json          ← 配置
/opt/dzmm/config/config_backups/      ← 备份（自动轮转，留 20 份）
/opt/dzmm/config/config_audit.log     ← 审计
```

compose 里是 `./config:/app/config`。顺带修掉一个隐患：**审计日志原来写在 `/app` 里，
容器一重建就没了**，现在落在宿主机上。

#### ⚠️ 重启容器会把后台会话清掉

会话只存在 dashboard 进程的内存里，`restart` 之后要重新登录。这是有意的
（重启即失效，比落盘一个会话文件更简单也更安全），页面上已注明。
验收脚本因此必须**在重启之后重新登录** —— 第一版忘了，第 6 步拿到的是登录页，
表现为"页面上没有备份可选 / 回滚返回 200 但没生效"，看着像回滚功能坏了。

#### 端到端验收（2026-09-25 22:36，`tools/p11c_check.sh`）

用"改群别名"做真实验收（别名无副作用，但走的是**完整的写路径**）：

```
0) 基线：5 个群 mute=0 screen=3 push=2，别名=认证妹子群
1) 未登录访问 /edit        -> 200 登录页 ✓（不泄漏配置）
2) 登录后 /edit            -> 200，表单渲染 ✓
3) 改别名（带秒数，保证每轮都是真改动）并保存 -> 200「已保存」✓
4) 落盘 / 备份 / 审计      ✓   逐字段比对：**只有别名变化** ✓
5) 重启（StartedAt 确实变了）✓   P11 自证行 静默=0 筛查=3 推送=2 ✓（与基线一致）
6) 重新登录 -> 回滚到上一版 -> 200「已回滚」✓  别名还原 ✓  与保存前逐字段一致 ✓
7) 最终状态：restarts=0，MEM 299MiB，异常 0
```

1. **页面教的命令是错的。** "未生效"提示原来写 `docker compose up -d dzmm-bot`，
   但改的是**挂载文件**，compose 判断"要不要重建"只看 compose 文件与镜像，
   看不出挂载文件变了，于是打印一句 `Container dzmm-bot  Running` 就结束 ——
   **用户以为重启了，其实没生效**。改成 `docker compose restart dzmm-bot`，
   并加测试钉住页面里**不许**出现 `up -d`。
2. **假改动。** 早期手写的 `config.json` 里 `bots[0]` 没有 `enabled` 字段，
   表单提交上来的是显式 `enabled=true`；不补默认值比对就会报一条假改动
   （"打开页面什么都不动点保存 → 1 项改动"），还白多一份备份 + 一行审计。
   `diff_summary` 现在两边都先补默认值再比。

#### 事故记录：错误的开关状态**没有**影响到线上

#### 缺陷：被禁用的群会从配置页上**消失**（2026-09-25 22:41 触发）

用户在页面上把 4 个群取消勾选「启用」保存后，重新打开页面 —— 那 4 个群整行不见了。

根因：`Config.as_dict()` 只序列化 `self.groups`（**生效**的那些，已按 `enabled`
过滤过），而 `/edit` 正是用它渲染表单。后果两条：

1. 被禁用的群在界面上**看不到**，也就**勾不回来**（只能重新手打 cid）；
2. 更糟：这时候在页面上改任何别的东西再保存，配置里那几行会被**整行删掉**
   （表单是整表提交，`parse_form` 只收表单里有的 cid），别名和人设一起没。

修法（都补了测试）：

- `as_dict()` 改成序列化**全部** `group_specs`（保持文件顺序）；运行期语义不变
  （`GROUPS`/静默/筛查/推送仍只看 `enabled`）。
- `section_config()` 同样列出全部群，新增 `configured_count` 与 `active` 字段 ——
  只读面板不该"看不见被关掉的群"。
- 保存前加**"旧页面"闸门**：页面渲染时把当时有哪些群/Bot 写进隐藏字段
  `__groups_seen` / `__bots_seen`；若提交里少了某个配置里存在的条目、
  而那一版页面**从来没见过**它，就整单拒绝并说清缺了哪个。
  宁可让用户刷新，也不许静默删配置。只在配置文件真的存在时生效
  （没有文件时用的是代码默认值，删不掉东西）。

#### 缺陷：被进程重启打断的出站记录永远挂着（2026-09-25 实测发现）

`OutboxSender.send()` 是**同步内联**的：入队 → 领租约 → 发 → 标记。
所以"发送途中被杀"（部署重启）会留下一条 `leased` 记录，而
**没有任何代码会再处理它** —— 没有轮询 pending 的后台 worker，
`reclaim_expired()` 写好了却**一直没有调用方**。

实测：22:30:43 发给玫瑰群的那条问候，被 22:30:47 的容器重建打断，
此后一直挂在 `leased`（`attempt_count=1`），让面板上的队列深度永远是错的。

修法：新增 `OutboxStore.abandon_interrupted(reason)`，在
`_wrap_with_outbox()` 启动时调用 —— 那一刻不可能有在飞的发送，所有
非终态记录都是上次遗留的，一律标 `failed` 并写明
「进程重启打断：未确认是否已投递，不自动重发（避免重复打扰）」。
**不重发**是刻意的：被打断时无法知道平台收没收到，重发就是重复打扰群友，
与 §8.5「平台未明确 ACK 时绝不换通道重发」同一条铁律。

## 七、关键设计

### 7.1 出站队列（本方案的核心机制）

```python
@dataclass(frozen=True)
class OutboundMessage:
    inbound_message_id: str
    text: str
    content_type: str = "text"        # text / image / share
    destination_chatroom_id: str | None = None   # 私聊时有值
    delivery_kind: str = "group"      # group / direct
    id: UUID = field(default_factory=uuid4)
    status: str = "pending"           # pending/leased/sent/failed
    lease_worker_id: str | None = None
    lease_token: UUID | None = None
    lease_expires_at: datetime | None = None
    attempt_count: int = 0
    platform_sent_id: str | None = None
    recall_after_seconds: int | None = None      # 需撤回 → 强制走账号
```

状态机：`pending → leased → sent`（ACK 回写 `platform_sent_id`）/ `failed`。
**按目标会话串行**（每 cid 一把发送锁），避免同一群两条消息抢顺序。

### 7.2 N-Bot 身份（与 DDZM-bot 的差异，需知悉）

DDZM-bot 用**一个** Bot（`DZMM_BOT_ID`）服务所有群。小小糯需要 **N 个**（一群一 Bot），理由：

- 每群独立**名字与头像**——认证群"小秘书"与玫瑰房"管家"要长得不一样，单账号做不到
- 人设串台从"靠自觉"变成**结构上不可能**（`bot.py:4280-4284` 那段 `set_persona_cid("")` 补丁就是为 2026-09-17 事故打的）
- 私有 Bot 别人加不进别的群 → 天然锁群

代价：N 套凭据（Token 只显示一次、轮换会使旧 token 立即失效）、N 个 `bot is not installed` 失败点。
**若嫌运维重，退回 DDZM-bot 的单 Bot 模型也成立**（人设靠切群），留作决策项。

### 7.3 入站幂等

`(chatroom_id, platform_message_id)` 唯一约束后入库，重复投递不重复扣币/开局/发奖。
入站过滤（照抄 DDZM）：拒绝自己发的消息、缺字段的事件、非 text 类型、重复事件。

### 7.4 唯一登录者 + 令牌桶 + 冷却

- 只有 `session.py` 能登录；其它模块**代码层面没有登录函数**
- 普通账号令牌桶；遇「请稍后再试」→ 60s 冷却并释放出站任务
- **放弃 600s 历史对账轮询**（DDZM §7.5：平台限流/验证码时额外历史调用反而危险）

### 7.5 长消息

阈值 `len(text) > 1000 or text.count("\n") > 10` → Bot API。
已实测：Bot 可发 20 行（19 换行）、单行 2000 字符。上线新上限前先在测试群用唯一 marker 试验。
