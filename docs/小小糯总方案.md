## 一、一页结论

**目标**：把小小糯从「单文件（`bot.py` 6364 行）会话自动化脚本」，改造成「DDZM-bot 范式的分层系统」，并在此过程中把**群消息通道换成官方 Bot API**。这两件事合成一个 program，不拆开做。

**最重要的一条结论**：

> **目标不是"消灭登录态"，而是"让登录态变得不关键"。**
>
> 因为私聊、撤回、图片、小说分享**注定只能走普通账号**（DDZM-bot 已实测），所以普通账号会永久存在。
> 正确的做法是：**高频、实时、易触发验证码的「群文本」交给 Bot API**；**低频、非实时的「私聊/撤回/图片/分享」留在侧车**——验证码掉线时可容忍。

**由此带来的关键简化（省掉一整块工作）**：

> **Webhook 不在关键路径上。**
> Bot API 的**发送是纯出站**（`POST /api/bot/send-message` + `X-Bot-Token`），**不需要任何公网入口**。
> 入站继续用现有 Socket.IO（DDZM-bot 的当前策略，且它明确**故意不接 Webhook**）。
> ⇒ **之前 Gate 0 卡住的「域名 / HTTPS 证书 / 80·443 / sslip.io」全部退出关键路径**，只在可选的 P10 才需要。

**形态**：**1 个 Bot（认证妹子群）** + 1 个普通账号侧车 + 出站队列；PostgreSQL 延后。

## 二、为什么必须合并成一个任务

两个计划不是并列关系，而是互为前置：

| 若分开做 | 会发生什么 |
|---|---|
| 先换传输、不做安全网 | 换完无法证明"少了个角落"——小小糯有 ~40 项功能，全凭人工比对 |
| 先换传输、不做出站队列 | 双身份发送必然重复投递（Bot 发了、账号又发一次） |
| 先重构结构、不换传输 | 把 Playwright/Socket.IO 内部打磨一遍，而它们正要被替换 —— 纯浪费 |
| 先换传输、不做 DB 化 | 出站队列需要租约/幂等/状态回写，JSON 单文件撑不住 |

**排序原则（借用 DDZM 的实践）**：**先建安全网 → 再换传输 → 最后治理结构**；且**不打磨即将被删除的代码**。

## 三、目标架构

```
                       ┌─────────────────────────────────────────┐
   平台 Socket.IO ────▶│ platform/socket_gw.py   入站（群 + 私聊）│
   message:new         └────────────────┬────────────────────────┘
                                        │ (chatroom_id, message_id) 幂等
                                        ▼
                       ┌─────────────────────────────────────────┐
                       │ core/   业务：命令路由 / 状态机 / 玩法    │
                       │         发骚·羞辱·调教·公演·剧情·投票…   │
                       └────────────────┬────────────────────────┘
                                        │ 只写入，不直接发送
                                        ▼
                       ┌─────────────────────────────────────────┐
                       │ outbound_messages（出站队列 / outbox）   │
                       │  state=pending  租约  attempt  幂等键     │
                       └────────────────┬────────────────────────┘
                                        ▼
                       ┌─────────────────────────────────────────┐
                       │ platform/worker.py  出站租约 + 路由 + 限流│
                       └───┬─────────────────────────┬───────────┘
                           │ 群文本（优先）           │ 私聊/撤回/图片/分享
                           ▼                         ▼
                  sender_bot.py              sender_account.py
                  （官方 Bot API）            （普通账号 Socket ← 唯一登录者）
                           │                         │
                           └────────► 平台 ◄──────────┘
                                        │
                            ACK → 回写 platform_sent_id
```

| 模块 | 职责 | **不应该做什么** |
|---|---|---|
| `core/` | 业务规则、命令路由、状态机 | 不碰平台 Cookie、不直接发送 |
| `runtime/` | 契约（冻结 dataclass）+ Settings | 不含业务逻辑 |
| `platform/session.py` | **唯一登录者**：浏览器 Profile / 取 Token / tRPC | 不处理业务 |
| `platform/socket_gw.py` | 入站 Socket + 过滤 + 去重 | 不决定"指令是否允许" |
| `platform/sender_bot.py` | 官方 Bot 群文本出站 | **不该有私聊/撤回接口** |
| `platform/sender_account.py` | 私聊/撤回/图片/分享出站 | 不做业务判断 |
| `platform/worker.py` | 出站租约、路由、串行、限流 | 不写业务规则 |
| `admin/` | 运维后台（群配置、登录状态、出站队列） | — |

## 四、五条铁律（不可违背）

1. **普通账号不可退休**——私聊 / 撤回 / 图片 / 小说分享只能走它。侧车永久存在。
2. **平台未明确 ACK 时，绝不换通道重发**——否则用户看到两条一样的消息（DDZM 明确列为原则）。
3. **业务代码不直接发送**——只写 `outbound_messages`，由 Worker 领租约发出。
4. **只有一处能登录**——其它模块**代码层面没有登录函数**（不是靠约定）。
5. **Webhook 与 Socket 不可同时处理同一个群**——若要接 Webhook，必须先做幂等 + 群职责划分（P10 闸门）。

## 七、关键设计

### 7.1 出站队列（本方案的核心机制）

```python
@dataclass(frozen=True)
class OutboundMessage:
    inbound_message_id: str
    text: str
    content_type: str = "text"        # text / image / share
    destination_chatroom_id: str | None = None   # 私聊时有值
    delivery_kind: str = "group"      # group / direct
    id: UUID = field(default_factory=uuid4)
    status: str = "pending"           # pending/leased/sent/failed
    lease_worker_id: str | None = None
    lease_token: UUID | None = None
    lease_expires_at: datetime | None = None
    attempt_count: int = 0
    platform_sent_id: str | None = None
    recall_after_seconds: int | None = None      # 需撤回 → 强制走账号
```

状态机：`pending → leased → sent`（ACK 回写 `platform_sent_id`）/ `failed`。
**按目标会话串行**（每 cid 一把发送锁），避免同一群两条消息抢顺序。

### 7.2 N-Bot 身份（与 DDZM-bot 的差异，需知悉）

DDZM-bot 用**一个** Bot（`DZMM_BOT_ID`）服务所有群。小小糯需要 **N 个**（一群一 Bot），理由：

- 每群独立**名字与头像**——认证群"小秘书"与玫瑰房"管家"要长得不一样，单账号做不到
- 人设串台从"靠自觉"变成**结构上不可能**（`bot.py:4280-4284` 那段 `set_persona_cid("")` 补丁就是为 2026-09-17 事故打的）
- 私有 Bot 别人加不进别的群 → 天然锁群

代价：N 套凭据（Token 只显示一次、轮换会使旧 token 立即失效）、N 个 `bot is not installed` 失败点。
**若嫌运维重，退回 DDZM-bot 的单 Bot 模型也成立**（人设靠切群），留作决策项。

### 7.3 入站幂等

`(chatroom_id, platform_message_id)` 唯一约束后入库，重复投递不重复扣币/开局/发奖。
入站过滤（照抄 DDZM）：拒绝自己发的消息、缺字段的事件、非 text 类型、重复事件。

### 7.4 唯一登录者 + 令牌桶 + 冷却

- 只有 `session.py` 能登录；其它模块**代码层面没有登录函数**
- 普通账号令牌桶；遇「请稍后再试」→ 60s 冷却并释放出站任务
- **放弃 600s 历史对账轮询**（DDZM §7.5：平台限流/验证码时额外历史调用反而危险）

### 7.5 长消息

阈值 `len(text) > 1000 or text.count("\n") > 10` → Bot API。
已实测：Bot 可发 20 行（19 换行）、单行 2000 字符。上线新上限前先在测试群用唯一 marker 试验。

## 十、风险登记册

| 风险 | 等级 | 对策 |
|---|---|---|
| 群文本**双身份重复发送** | **高** | 出站队列 + 未明确 ACK 不换通道重发 |
| 私聊/撤回误走 Bot → 功能直接失效 | **高** | 路由表硬编码；`sender_bot.py` 不该有这两个接口 |
| 拆分 `bot.py` 引入回归 | 高 | P2 安全网先行；每步可回退 |
| DB 化迁移丢档 | 高 | 一次性导入 + 条数校验 + JSON 保留 |
| N 个 Bot 凭据轮换造成中断 | 中 | 轮换流程 + 逐 Bot 灰度和告警 |
