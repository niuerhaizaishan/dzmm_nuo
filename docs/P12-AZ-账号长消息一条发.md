# P12-AZ：茶水间的长消息改成**一条**发（账号的第二条投递路）

> 屋主 2026-09-30："**为啥茶水间的运势分两段发啊**" → "不用啊 就和妹子群一样就行啊，妹子群就是一段啊"

## 1. 现象

茶水间里 `#运势` 的卡被**切成两条**发出来，认证妹子群里同一张卡**只有一条**：

```
01:43（UTC）  墨莲  186 字 → 70 字      切在 🍀 幸运行**前**
01:43（UTC）  囡囡  182 字 → 94 字      切在 📈 四维行**后**（幸运行被挤到第二条）
01:43（UTC）  沐沐糖 188 字 → 73 字      切在 🍀 幸运行**前**
```

切点还随 📜 命盘那行的长短浮动，所以第二条有时以 `————————————` 开头、有时以 `🍀` 开头，
看上去就很像"发漏了一半又补一条"。

## 2. 根因：那个 200 字上限**只属于打字那条路**

P12-AN 夹逼出来的「账号通道单条上限 200 字」（190 ✅ / 210 ❌，超了平台前端**静默不收**）
测的是 **Playwright 打字**：`keyboard.insert_text()` 逐行灌进 `<textarea>` 再按 Enter。
而账号身份其实有**两条**投递路：

| # | 路 | 身份 | 单条上限 | 稳定性 |
|---|---|---|---|---|
| ① | Playwright 打字 | 账号 uid | **200 字**（平台前端不收超限） | 稳 |
| ② | Socket.IO API（`socketio.DZMMSocket`，每次握手） | 账号 uid（同一个） | **实测 278 字一条过** | **时好时坏**（要重试 4~6 次） |
| ③ | Socket.IO API（**读消息那条长连接**，`SioSubscriber`） | 账号 uid（同一个） | **实测 277 字一条过** | **稳**（3/3，见 §4） |

认证群走的是**官方 Bot API**（10000 字），所以那边一直是一条。
茶水间没有 Bot ⇒ 之前只有 ① ⇒ 271 字的卡只能被 `_split_for_account` 切成两条。

## 3. 实测：② 真的能一条发完（自检群 `bot测试`，真发真读回）

| 探针 | 形状 | 结果 |
|---|---|---|
| 273 字 / 9 行（运势卡形状） | 一次握手 | ✅ **一条完整落地** |
| 278 字 / 9 行 | 第 4 次握手 | ✅ **一条完整落地**（9.9 s） |

失败长这样：`connect=400 {"code":1,"message":"Session ID unknown"}`
（握手拿到的 sid 没被注册）。**更坑的是：`connect` 失败时 `send` 有时也返回 `200 ok`，
而群里什么都没有** —— P12-AN 那条"假成功"就是这个坑。
⇒ **回执只能用来决定"要不要重新握手"，能不能算成功只有读回说了算。**

顺手做了 6 种握手顺序的对照（`tools/probe_socket_variants.py`，**同一张 273~282 字的卡**）：

| 变体 | 顺序 | 落地 |
|---|---|---|
| `cur` | hs → POST `40` → GET poll → POST batch（现行） | ❌ |
| `poll_first` | hs → **GET poll** → POST `40` → batch | ❌（`send=200 ok`，假成功） |
| `fresh_ts` | 每个请求各自新 `t` | ❌（connect=200 但 send=400） |
| `no_syncmode` | 去掉 `&syncMode=http` | ❌ |
| `no_poll` | 不做中间那次 GET poll | ❌（`send=200 ok`，假成功） |
| **`retry20`** | 连接没成就**重新握手重来** | ✅ **第 4 次成** |

结论：**握手顺序换不出稳定性，能救它的是"硬重试 + 每次读回"** ——
这条路本来就是"看运气"，所以设计上必须把它当"可能失败的一条快路"，而不是唯一的路。

**于是又发现第三条路**：`sio_subscribe.SioSubscriber` 为**读消息**长期维护着一条
Socket.IO 长连接（`auth={token}`、polling+websocket、断线自动重连）。
在**同一条已连上的连接**上 `emit("message:send", …)` 就绕开了整个握手环节 ——
实测（`tools/probe_live_socket_send.py`）连发 3 条 271 字 / 9 行的卡：
**3/3 全部一条完整落地，每条 2.1~2.2s**。这才是主力路径。

## 4. 修法

长消息**先走账号的 Socket.IO 两条道，都没成才退回打字切分**：

```
Sender._send_locked（> ACCOUNT_MSG_MAX_CHARS 才进这条路）
├─ ① 读消息用的那条长连接（sio_subscribe.SioSubscriber.send_text）
│     已连着、不用握手 ⇒ 实测 3/3 一次成，2.2s
├─ ② HTTP 握手那条（socketio.DZMMSocket.send_message_ex）
│     时好时坏 ⇒ 最多 8 次握手 / 25s 预算，每次读回
└─ ③ 都没成 ⇒ 退回 P12-AN 的「切 ≤190 字 + 打字」（观感=两条，不会没回复）
```

**① 读消息那条长连接**（P12-AZ 加的，主力）：

- `sio_subscribe.SioSubscriber.send_text(cid, uid, text)` —— 在**已经连着**的
  `python-socketio` 客户端上 `emit("message:send", …)`，返回自己生成的 `message_id`；
- 这条路不用握手（没有 sid 注册那一步）⇒ 不会撞 `Session ID unknown`；
- 实测（`tools/probe_live_socket_send.py`，自检群，**连发 3 条 271 字 / 9 行的卡**）：
  **3/3 全部一条完整落地，每条 2.1~2.2s**；
- `main()` 里把它装到模块级 `_LIVE_SIO`，发送侧才拿得到。

**② HTTP 握手那条**（P12-AN 时代就有的兜底）：预算 `SIO_LONG_BUDGET_SEC = 25s`、
最多 `SIO_LONG_MAX_TRIES = 8` 次握手；**每一轮都读回**（`_verify_landed`），
读到了就返回成功 —— 这也顺带**防重复**：上一轮其实发出去了，这一轮就不会再发。

短消息不碰这条路（打字更稳、也不比它慢）；`allow_fallback=False` 的发送
（私聊发骰那类）照旧只走 Playwright。

`socketio.py` 配套改动：`send_message_ex()` 把服务端回执带出来
（`(是否被接受, 说明, message_id)`），`send_message()` 仍返回 `bool`（老调用方不动）。
回执里**不带 cookie**（那行会进日志）。

## 5. 为什么读回要卡"新鲜"

`_verify_landed` 与老的 `_verify_sent` 有两处不同：

1. **窗口更大**（20 条）：茶水间 792 人，5 条窗口转眼就滚出去了；
2. **按时间卡新鲜度**：运势卡有**冷却复用**（P12-AW：一小时内重发**逐字相同**的那张卡）。
   窗口里正好躺着上一次那张时，不卡时间就会把"没发出去"判成"发出去了" → **静默丢一条**。
   判据：`sent_at >= now - 10s`；平台存的是 **UTC**（实测：本地 09:43 发的，存 `01:43`）。

取舍写在代码注释里：**宁可重复一条，不可静默丢** ——
读回接口连续 3 次都失败、或时间戳读不出来，都判"没落地"（退回去切分打字）。
重复只是难看，消失是"她坏了"。

## 8. 回滚

- 代码层：revert 本次提交 → 常规部署（回到"切两条"，其余行为不变）；
- 没有配置开关：这条路只影响**账号通道的长消息**（实际上只有茶水间），
  而且是"先试快路、失败即退回老路"，没有它也不会丢消息。

## 9. 复盘

- **"平台限制"要先问清是哪条路的限制**：P12-AN 把"账号通道 = 打字"当成了全部，
  于是"200 字"被写成了账号的属性。同一个账号还有 API 那条路，上限完全不同。
- **回执 ≠ 投递**：`send=200 ok` 在这个平台上出现三种含义（真投递、sid 失效、
  服务端吞掉）。只有群里的读回是事实。
- **探测"能不能"要带对照组**：探针① 前两轮 190/210 都没落地，差点让我得出
  "连短消息也不行"的结论 —— 其实那只是这条路在抽风；真正说明问题的是
  273 字那条**落地了**。对照组失败时，先怀疑路，再怀疑结论。
- **同一个"第二条路"也有稳和不稳两种走法**：每次重新握手的 HTTP 那条要试 4~6 次，
  而**复用读消息已经在用的那条长连接**是 3/3 —— 手里已有的连接，往往比再建一条便宜。
