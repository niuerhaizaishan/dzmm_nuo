## 一、短 / 长 控制按钮

**做法**：主界面只留「短」「长」两个按钮，强度仍由滑条决定。

| 按钮 | 强度 | 时长 | 说明 |
| --- | --- | --- | --- |
| **短** | 当前滑条值 | **400ms** | 点一下就结束，适合提示/挑逗 |
| **长** | 当前滑条值 | **1200ms** | 一下的「长」，适合剧情推进或惩罚 |
| 关 | — | — | 立刻 `Vibrate:0;` 并清掉所有计时器 |

细节：
- 两个按钮**互斥**：新的会取消上一个的自动停（沿用现在的「新指令替换旧计时器」逻辑）。
- 连点短按钮：限流 300ms 照旧；连点期间不叠加，只刷新计时。
- **「时长滑条」和「振动一下」已删除**（2026-10-25 屋主确认）：手动档位本来就是持续震，
  自定时长没有意义；要更长就拖档位、按「立即停止」。
- 房主页也有「自测 · 短 / 长」两个按钮，方便房主自己试。

**代码影响**：只改 `guest.html` / `host.html`，服务端不用动（时长仍是参数）。

## 二、预设震动方式

**关键设计**：一个「预设」= 一串短脉冲，**由房主页在本地按时序执行**，不是服务端逐步下发。
理由：房主页本来就必须在前台（BLE 的限制），时序精度由它保证；服务端只转发一次「用哪个预设」。

### 指令模型

```json
{"t":"cmd", "pattern":"triple_tap", "level":0.4, "duration_ms":null, "id":12}
```
- 有 `pattern` → 房主页按预设执行；`level` 作为整体强度系数（0~1 乘到每步上）
- 无 `pattern` → 沿用现在的单脉冲

### 七个预设（一分钟一段）

预设是"段"不是"下"：每个默认跑 **60 秒**，由**循环**构成（`step_ms` + `gap_ms` 循环到 `total_ms` 到点为止），不是把次数写死。

| id | 名字 | 单步 | 默认总长 | 观感 |
| --- | --- | --- | --- | --- |
| `tap` | 轻叩 | 50% × 300ms，间隔 400ms | 60s（约 85 下） | 细碎、像有人隔着布料敲 |
| `pulse` | 脉冲 | 70% × 600ms，间隔 300ms | 60s（约 66 下） | 规律的推进感 |
| `heartbeat` | 心跳 | 两下快（60%×150ms，间隙 100ms）+ 停顿 600ms | 60s（约 80 组） | 由慢到快的错觉，适合紧张段落 |
| `ramp` | 渐强 | 20%→100% 均分爬升，每步 500ms | 60s（120 步） | 一路加码，从头到尾都在变强 |
| `ramp_down` | 渐弱 | 100%→20% 均分下降，每步 500ms | 60s（120 步） | 收尾用，强度慢慢退 |
| `stutter` | 断续 | 80% × 150ms，间隔 150ms | 60s（200 次） | 碎、急，像被反复点断 |
| `hold` | 长震 | 100% 持续 | 60s | 最长情的一段，适合"罚"或"留白" |

规则：
- **单条上限 60 秒**（要更长就手动再来一次；没有 2 倍、没有自动续）
- 每步最小间隔 **≥90ms**（BLE 写入下限；阶段 0 实测单次写入往返 <1ms，设备端有处理间隔）
- 到 60 秒**自动停**（本地计时，不依赖服务端）
- 任何时刻「停止」= `Vibrate:0;` + 取消后续所有步，**立刻生效，不等当前步走完**
- 序列由**房主页本地**执行：断网/切后台时它自己走完并停止
- 预设表放在页面里一份 JSON（`id`/`name`/`step_ms`/`gap_ms`/`total_ms`），**服务端只透传 id 并做白名单校验**

**顺带**：机器人 `/震` 未来可支持 `/震 档位 预设名`，这次先不做。

## 二·五、强度滑条＝手动档位（**2026-10-25 晚按屋主纠正重做**）

> 纠正前的理解是错的：「滑条 × 预设系数」。屋主的原话是**只控制强度，让玩具实时按这个强度震**。

### 交互（现在的语义）

- 滑条就是**手动档位**：拖到 65%，玩具立刻以 65% 一直震；边拖边变（实时）
- 不需要点任何按钮——拖动本身就是动作
- 拖滑条＝**手动接管**：正在跑的预设立刻让位（不叠加、不换算）
- 停的三种方式：「立即停止」／拖到最左（0）／5 分钟没再调整自动停（防忘）
- **预设不看滑条**：每个预设自带每一步的强度（那是节奏的一部分，`渐强/渐弱` 全靠它）
- 「短 / 长」仍然取滑条的当前值当强度（一次性脉冲）

### 消息

```json
{"t":"level", "value":0.65}        // 控制者 → 服务端 → 房主
```
- 服务端只做两件事：范围校验（0~MAX_LEVEL）、同连接 150ms 节流；不落库、不计入"触觉事件次数"
- 房主页收到后：取消正在跑的预设 → 立刻 `Vibrate:N;` → 保持到下一次调整或停止
- 预设指令里的 `level` 服务端**强制成 1.0**（等于"不参与"），避免两套强度语义打架

### 安全

- 档位上限 `MAX_LEVEL`（默认 1.0，可用 `DZMM_SHARE_MAX_LEVEL` 收紧，不能靠滑条越过程序上限）
- 拖到 0 等于「停」（直接 `Vibrate:0;`，不等下一次步进）
- 房主页断开 / 控制者退出 / 关页面 → 照旧自动补停止

## 三、剧情自适应震动（先测试）

两条路，建议先 a 后 b：

### a) 提示词档位（可控、零模型调用）—— **先做这个**

DM 在每回合输出一行 `【震动】<角色> <强度>% <时长>ms`（v2 提示词里已经写好），小小糯解析后触发。
这就是"按剧情走"，只是强度来自提示词里固定的档位表。

**测试方法（不需要真开局）**：
1. 取一段真实 DM 记录（你给的那个样本群里有 7 条 DM 叙述，约 700 字/条）
2. 离线跑解析：抽出所有 `【震动】` 行 → 生成一条时间线（时间、强度、时长）
3. 打印时间线 + 统计（每回合触觉次数、平均强度、总时长）
4. **真机回放**：把时间线按 1× 速度依次触发（房主页在旁执行），你躺那儿感受一遍

### b) 模型自适应（更"活"）—— 之后再做

小小糯读最近 3~5 条剧情，判断「紧张度 / 节奏」，自己产出强度曲线（不依赖 DM 的行）。

| 项 | 设计 |
| --- | --- |
| 输入 | 最近 3~5 条 DM 叙述 + 本轮事件（谁触发、什么类型） |
| 输出 | 结构化：`{强度 0~100, 时长 ms, 节奏: 单发/连击/渐强}`，受档位表与上限约束 |
| 延迟 | 模型调用 ~1~3 秒（可接受，剧情是慢节奏） |
| 调用频率 | **每回合最多一次**，避免刷 token 与刷设备 |
| 失败兜底 | 模型不可用 → 退回 a 的档位（不会没反应） |
| 安全 | 仍受「每回合最多 2 次、同类 10 秒冷却、默认上限 70%、随时 /停」约束 |

**为什么先做 a**：a 不需要模型、结果可预测，能先把「解析 → 触发 → 手感」这条链验证掉；b 只是把"强度怎么定"从固定档位换成模型判断，链路完全一样。

### 2) 七个预设（各 60 秒）—— ✅ 已上线

房主页本地执行（服务端只透传 id + 总时长，白名单校验）。实现里的实际波形：

| id | 按钮名 | 每步 | 60 秒内 |
| --- | --- | --- | --- |
| `tap` | 点按 | 100%×300ms，间隔 400ms | ≈86 下 |
| `pulse` | 脉冲 | 70%×600ms，间隔 300ms | ≈67 下 |
| `heartbeat` | 心跳 | 60%×150ms→100ms→80%×150ms→停 600ms | ≈60 组 |
| `ramp` | 渐强 | 20%→100%，120 步×500ms，不留间隙 | 120 步 |
| `ramp_down` | 渐弱 | 100%→20%，同上 | 120 步 |
| `stutter` | 连抖 | 80%×150ms，间隔 150ms | 200 次 |
| `hold` | 全开 | 100% 持续 | 60 秒一口气 |

* 到 60 秒**自己停**（本地计时），任何时刻「立即停止」= `Vibrate:0;` + 丢弃后续步

* 表里的百分比就是**最终强度**，不跟滑条相乘（屋主 2026-10-25 纠正）

### 3) 强度滑条＝手动档位 —— ✅ 已上线（按纠正重做）

* 拖动＝手动接管：正在跑的预设立刻让位（不叠加、不换算）
