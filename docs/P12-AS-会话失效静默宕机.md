# P12-AS：会话失效静默宕机 142 分钟（茶水间没反应）

> 屋主 2026-09-29 18:10 在顶层茶水间 @ 了一句「下午群里发生了什么？」，
> 18:11 追问：「**茶水间你怎么没反应了**」。

## 1. 现象：不是"没反应"，是**读不到消息**

```
18:05:33 ⚠️ [4fc4a2fd] 平台读消息失败：tRPC chatroom.getMessages: Invalid authentication credentials
18:05:33 ⚠️ [4a56be71] / [bd7fe6a4] / [f4ec4c21] 同样
[sio] 连接失败: token 获取失败，300s 后重试
```

茶水间**没有 Bot、也没有 webhook**，全靠账号会话读消息 ⇒ 会话一失效，那群就彻底聋了。
上班群还能靠 webhook + Bot 通道工作，所以"只有茶水间没反应"。

## 2. 时间线（renew_token.log）

```
15:39:14 SKIP: token 未变化，无需写回      ← 进入续期窗口，回显接口原样返回旧 token
15:44:14 SKIP: token 未变化，无需写回
15:49:15 NOTE: 只读接口未授权，业务探针本身失败（error）→ 不下结论、不重登
   …每 5 分钟一条 NOTE，一直到 18:09（共 29 条）…
18:11      （人工）docker exec headless_relogin.py → 登录成功，读消息恢复
```

**142 分钟里没有任何一次重登尝试、也没有一条告警**（`check_health.log` 全程"巡检正常"）。

## 3. 四个原因（前三个都已修）

### ① 分类器认不出平台的真实错误串（直接原因）

```python
# 旧
if "未授权" in msg or "unauthorized" in low or "401" in low:
    return "unauth"
```

平台回的是 `Invalid authentication credentials` —— **三个关键词一个都不匹配**，
于是被判成"探针自己失败（error）"。

### ② "不下结论"没有期限（放大成 142 分钟的元凶）

P12-AJ 为了避免误杀，规定"探针失败 → 不下结论、不重登"。方向是对的，
但**"永远不下结论" = 永远不恢复**：会话死了两个多小时，循环还在每 5 分钟温柔地写一行 NOTE。

### ③ 告警判据只看"死没死"

`check_session_state()` 只在 `probe == "unauth"` 时判 `dead`；而这里是 `error`
⇒ `dead=False` ⇒ 巡检一路"正常"。**用户能感知的量是"多久没回话"，不是"会话死没死"。**

### ④（未修，留给你定）这套"续期"其实依赖服务端自己轮换 token

回显接口 `/api/auth/token` **续不了期**（P12-AJ 的结论）。观察到的 `OK: token 续期成功`
是"抄到了服务端较新的 token"——也就是说**每小时真正续命的是服务端自己**。
这次那一小时它没轮换 ⇒ 必然过期。要不要在窗口内**主动触发浏览器续期**
（`renew_token_browser.py`，会带来每小时一次浏览器活动/验证码风险）？
这是行为口径问题，没敢自己定。

## 4. 修法（P12-AS，已上线）

| # | 改动 | 效果 |
|---|---|---|
| 1 | `UNAUTH_MARKS`：把 `invalid authentication` / `invalid credentials` / `jwt expired` / `invalid_grant` / `not authenticated` / `403` 等都算未授权 | 今天这种 401 会在 **15:49 当场**判 `unauth` → 立刻重登（142 分钟 → 约 1 分钟） |
| 2 | `RELOGIN_AFTER_MIN = 20` + `session_state.bad_since` 计时器：连续 20 分钟没验证通过 → 先浏览器续期，不行就写 `emergency` 交 entrypoint 重登 | "不下结论"有了期限；网络抖动仍不会过度反应（20 分钟内照旧不下结论） |
| 3 | 巡检新增 `session_unverified` 告警：连续 20 分钟没验证通过就喊人 | 今天这次会在 **16:09** 就告警，而不是等人来问 |

`bad_since` 的维护放在 `_write_session_state()`：`probe == "ok"` 时清空、
否则沿用旧值（不重复刷新）。读它的三处仍然**只认 `unauth` 为死**（P12-AR 定的规矩）。

## 5. 补发（屋主的原始诉求）

那条 @ 是 18:10:04 发的，会话 18:11 才恢复。**恢复后 bot 也不会自动补**：
它按 `last_id` 定位"该处理哪些消息"，而 `last_id`（掉线前）已经滚出 100 条窗口 ⇒
走"只处理最新一条"的兜底 ⇒ 那条 @ 被跳过（这是设计，不是 bug）。

写了 `tools/send_missed_recap.py` 补发，踩了三个坑，都值得记：

1. **直接往 `outbound` 表插一行 ≠ 会发出去**。`OutboxSender` 是**发送期的包装器**
   （bot 调 `sender.send()` 时才入队+投递），**不是轮询 worker** —— 插进去的行
   永远躺在那儿（第一版就这么干了，盯着队列看了一分钟才发现没 worker）。
   另起 Playwright 也不行：会和 bot 抢 `pw_profile`（`profile appears to be in use`）。
   ⇒ 唯一安全的"代为说话"通道是 **Socket.IO**（`DZMMSocket.send_message`，纯 HTTP）。
2. **Socket.IO 是间歇性抽风的**：438 字的回顾切两段，第 1 段成、第 2 段连着 3 次重试
   全失败 ⇒ 群里留了**半截消息**。改成"每段各自硬重试 + 每段读回校验"，
   再用 `--skip 1` 只补没落地的尾段。
3. **`recap_absent` 有副作用（写冷却）**：dry run 跑一次就把窗口记进 `recap_ts`，
   紧接着 `--send` 就拿到"这一段刚给你说完呢～"这种冷却话术，差点当成补发内容发出去。
   现在工具会先摘冷却、dry run 结束再放回。

最终群里是完整的两段（`18:21:43` 头段 + `18:22:24` 尾段），并把 `last_id` 推到那条 @ 上
（防止 bot 以后重读历史再答一遍）。

## 6. 验收

- `tests/test_renew_session_probe.py` 19 → **23 条**：平台真实错误串必须判 `unauth`、
  真网络错仍判 `error`、"不下结论"超期必须动手（<20 分钟不许动手）、恢复后计时器清空、
  "连续没验证通过"要告警。
- 全量套件 0 失败；上线后 md5 一致；`session_state.json` 已带 `ok_at`/`bad_since`；
  茶水间恢复投递（`⏱️ [4fc4a2fd] 投递 3.7s 来源 sio`）；巡检无误报。

## 7. 复盘

- **"没反应"要先分类：读不到 / 不回 / 发不出**。这次是**读不到**（会话失效），
  而上一轮 P12-AN 是**发不出**（200 字上限）。两者的日志线索完全不同，
  混在一起查会浪费很久。
- **安全阀必须有期限**："宁可不动，避免误杀"在**有限时间内**是对的；
  一旦没有上限，它就退化成"永远不修"。凡是"暂缓动作"的分支，都要配一个计时器。
- **告警判据要贴着用户的感受**：`dead`（会话死没死）是我们内部的模型，
  "多久没回话"才是屋主的体验。今天这条告警如果按后者写，16:09 就响了。
- **错误串分类是脆弱契约**：平台的文案会变（中文/英文、tRPC 包装、大小写）。
  分类器要按"语义关键词集合"写，并且**必须有兜底**（认不出时按不可用处理并告警，
  而不是安静地"不下结论"）。
- **"插数据库就会有人发"是个想当然**：任何队列都要先问一句"到底谁在轮询它"。
  这次靠盯队列一分钟发现了，代价是一条永远不会被发的记录。
