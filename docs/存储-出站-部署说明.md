## 一、存储层：`runtime/store.py` + `state_store.py`

### 形状

- 一个 SQLite KV：`kv(scope, key, value(JSON), updated_at)`，`scope ∈ {group, profile, meta}`。
  **不是关系表** —— value 是整块 JSON（现有代码到处 `state[cid]["任意键"]`，关系化等于重写业务）。
- `state_store.py` 是**唯一入口**，函数名与旧 JSON 时代完全一致：
  `load_state/save_state`（整 scope）、`group_get/group_set`（单群单键）、
  `top_get/top_set`（顶层键，如骰子局 `dice_game`）、
  `get_profile/upsert_profile/load_profiles/save_profiles`。
- 库文件：`data/store.db`（挂载在 `./data` **目录**上，所以 `os.replace` 可用 —— 单文件
  bind mount 上会 EBUSY，这是当年 JSON 后端"写一半被 kill 就清零"的根源）。

### 三条硬规则（违反就出事）

1. **可跨线程，但必须串行**：`Store` 用 `check_same_thread=False` + `threading.RLock`。
   ⚠️ 2026-09-27 的事故就是缺这一条：工作线程一碰就抛 `ProgrammingError`，
   被 `except: pass` 吞掉后退回 JSON 文件 ⇒ 同一个群的状态被劈成两半
   （主线程读 sqlite、工作线程写 `state.json`），表现成"`/结束` 永远静默"。
2. **写状态要"只写本群"**：`save_state({cid: gs})`（= `bot._save_group`）。
   整 scope 落盘在按群并行下会**互相覆盖**（详见 P12-AA）。
3. **降级必须吼**：`state_store` 里所有"退回 JSON"的分支都会打一次
   `⚠️ state_store: sqlite 不可用…`。静默降级 = 分叉，分叉 = 查两小时。

### 一次性导入与开关

- 首次创建库时 `import_json()` 把老的 `state.json` / `profiles.json` 导进来一次，
  靠 `meta.json_imported` 幂等。⚠️ **读失败不再写这个标记**（P12-AA）：否则瞬时读失败
  会被永久记成"迁移完成"，旧数据静默留在 JSON 里、再也不重试。
- 回滚开关：`DZMM_STORE=json` 立刻退回 JSON 读写（JSON 文件一直保留不删）。

### 对账与善后工具

```bash
python tools/probe_store_split.py       # 对比 sqlite 与 state.json 的分叉（只读）
python tools/merge_json_into_store.py --dry-run   # 把 JSON 那一半并回 sqlite（先看计划）
python tools/audit_runtime.py           # 容器内看存储/队列/热加载现状
```

## 二、出站队列：`runtime/outbox.py`（+ `routing.py` / `transport_bot.py`）

### 数据流

```
业务代码 → OutboxSender.send(text, cid)        ← 有 dry 旁路：dry 模式不落库
   ├─ enqueue(chatroom_id, text)  → outbound 表（status=pending）
   ├─ lease(oid, worker_id)       → status=leased（带租约，默认 120s）
   ├─ RoutingSender.send(...)     → 群文本走官方 Bot API；图片/私聊/需撤回走账号通道
   └─ mark_sent / mark_failed（失败写明原因）
```

`outbound` 表保留**全文**，所以它是"到底发出去了什么"的唯一权威记录
（排"消息被截断/丢了一条"就靠它）。

### 状态与"要不要重发"（铁律）

| status | 含义 | 会不会再发 |
| --- | --- | --- |
| `pending` | 刚入队，没人领 | 会被领 |
| `leased` | 正被某个 worker 发 | 租约过期后可被回收重领 |
| `sent` | 发送成功（有 `platform_sent_id`） | 不会 |
| `failed` | 失败，`last_error` 写明原因 | **只有 `[rejected]` 会自动重试** |

- **`rejected`**（平台明确拒绝，确定没送到）⇒ 后台 `retry_worker` 会 `revive` → 重发，
  最多 `retry_max` 次。
- **`ambiguous`**（不确定送没送到，最常见的就是 `sender 返回 False`）⇒ **绝不重发**
  （重发就是重复打扰群友）。这条与 DDZM 接入指南 §8.5「未明确 ACK 不换通道重发」一致。
- 进程重启打断的记录：启动时 `abandon_interrupted()` 标成 `failed` 并写明
  「进程重启打断：未确认是否已投递，不自动重发」—— 如实记录不确定，而不是猜。

### 看它有没有丢东西（P12-AB 起）

- 主循环每 30 分钟一行：`📤 出站队列：pending=x failed=y；最近失败 …（群/字数/正文片段/原因）`。
- 健康巡检每 5 分钟看一次库（**只读连接** `mode=ro`，绝不锁生产）：失败**条数增长**就告警
  （按"增长"而不是"有失败"，否则失败的记录会永久刷屏）；积压 > `OUTBOX_PENDING_MAX`(20) 也告警。
- 手工看：

```bash
python tools/probe_outbox_texts.py     # 真正发出去的消息（长度/行数/结尾）
python tools/outbox_report.py          # 队列状态汇总（若有）
```

### 已知边界

- `OutboxStore` 现在有锁 + 可跨线程（P12-AA）；但它只保证**单进程内**安全 ——
  多写者场景要串行化，靠的是 `OutboxSender` 的**每群一把 asyncio.Lock**（保证同群顺序）。

## 三、部署：`deploy.ps1` + `Dockerfile` + `docker-compose.prod.yml`

### 一条命令做了什么

```
.\deploy.ps1 -Action deploy
 [1/3] 远端整树备份 → backup-code-<时间戳>.tar.gz（排除 data/novels/日志/**凭据与 PII**）
       并只保留最近 10 份
 [2/3] 上传代码：白名单 .py/.sh/.yml/.js/.css/.png/.jpg + prompts/*.md
       + Dockerfile / requirements.txt / .dockerignore
       ⚠️ 上传前有**完整性闸门**：关键文件在不在、prompts ≥30、文件数 ≥100、
          不满足就中止且一个文件都不传（防 2026-09-27 那次"只传了 42 个文件的半更新"）
 [3/3] 远端 docker compose build dzmm-bot && up -d dzmm-bot
```

其它动作：`upload`（只传代码）、`compose`（应用 `docker-compose.prod.yml` + 校验 + 重建）、
`exec -Cmd "…"`、`status`、`logs`、`diff`（本地/远端 md5 对账）、`rollback`（回到最新备份）、`sync`。

### 镜像里有什么 / 没什么（P0，2026-09-27）

- `build: .` ⇒ 构建上下文是服务器 `/opt/dzmm` **整棵树**，`Dockerfile` 是 `COPY . .`。
- **必须有 `.dockerignore`**：否则 `.env`、`.env.bak-*`、`.dzmm_token.json`、`state.json`、
  `profiles.json`（成员 PII）会被烤进镜像层。`deploy.ps1` 的闸门现在要求这个文件必须上传。
- 验证（应全部 No such file）：

```bash
docker run --rm --entrypoint sh dzmm-bot:latest -c 'ls /app/.env /app/.dzmm_token.json /app/state.json /app/profiles.json'
```

### 容器资源（P0）

```yaml
mem_limit: 1300m     # 宿主只有 1.87G，容器内常驻 5 个 chromium
shm_size: 512m       # Docker 默认 64MB —— chromium 崩溃的经典原因（启动参数里没有 --disable-dev-shm-usage）
logging: json-file max-size=10m max-file=3
```
宿主另有 2G swap（`/etc/fstab` + `vm.swappiness=10`）。

### 上线前后怎么验证

```bash
# 部署前：在**当前镜像**里跑一遍闸门（导入/存储/会话锁/热加载/人设/提示词/多 Bot）
scp tools/deploy_gate.py root@HOST:/tmp/dg.py
ssh root@HOST "docker cp /tmp/dg.py dzmm-bot:/tmp/dg.py && docker exec dzmm-bot sh -c 'cd /app && GATE_ROOT=/app TEMP=/tmp python /tmp/dg.py | tail -2'"
# 期望 ALL CHECKS PASSED（2026-09-27 为 119 项 OK / 0 项 !!）

# 部署后
.\deploy.ps1 -Action status      # 容器状态 + 健康日志尾巴
.\deploy.ps1 -Action diff        # 本地与远端每个文件 md5 对账
.\deploy.ps1 -Action logs        # 最近日志
```

### 回滚

```bash
.\deploy.ps1 -Action rollback    # 展平最新 backup-code-*.tar.gz 并重建
# 或：git revert <commit> && .\deploy.ps1 -Action deploy
```

## 四、变更这套东西时的三条纪律

1. **改存储/状态先想"并行下谁写谁"**：写状态用 `_save_group`，读可以整 scope。
2. **改投递先想"这条到底送到没有"**：不确定就 `ambiguous`，绝不自动重发；
   新增失败必须能被状态行或巡检看见。
3. **改部署先想"半更新会怎样"**：需要新文件就加进白名单与闸门的 `$need`，
   并确认 `.dockerignore` 不会把它挡在镜像外。
